# Clubs and events

The social layer. A club is a group with an owner, members, events, and a feed of admin updates. Phase 1 (shipped) is web-only with one-off events. Full phasing in `roadmap.md § Clubs and events`.

The top-level "Social" sidebar item hosts the club browse UI as one of three tabs — see `decisions.md § 61`. The `/clubs` top-level URL is a thin redirect to `/social?tab=clubs`; club sub-routes (`/clubs/[slug]`, `/clubs/new`, `/clubs/[slug]/events/*`, `/clubs/join/[token]`) are unchanged.

> **Events are running-specific today.** The editor + detail page assume a *run* (route, distance, pace, race mode, results leaderboard, certificates). A proposed generalisation — typed events (`run`/`ride`/`class`/`social`) with self-hiding athletic fields, so a club can host a yoga or pilates class, plus optional paid registration (Stripe Connect, payouts to the host not the club) — is specced (not built) in [club_events.md](club_events.md).

## Surfaces (web)

### Missing club: "Set it up"

There is no open source of running-club data to seed a directory from (issue #1151), so a club a runner searches for is often simply not on Threkir yet. When the **Browse** search finds nothing, the empty state says so and offers two ways forward (#1151 step 5):

- **Set up your club**: web links to `/clubs/new?name=<searched name>`, and the create form starts with that name filled in (`prefilledClubName` in `lib/social/club_setup.ts`: trimmed and capped at the 80-code-point club-name limit). Android opens the same `showClubFormSheet` the FAB opens, with `initialName` set. An empty unfiltered Browse offers the same link without a name.
- **How to create a club**: web links to `/help/create-a-club`. Android opens the in-app guide (`openGuide(context, 'create-a-club')`).

The offer only shows once a load has settled with no results. The loading skeleton and the load-error card (with Retry) never show it, because a failed search tells the runner nothing about whether their club exists. A signed-out visitor never sees web Browse (`/social` is auth-gated), but the set-up link is a plain URL: following it signed out goes through the layout guard to `/login?return_to=/clubs/new?name=…` and returns to the prefilled form after sign-in. Mobile has no signed-out Browse (`SocialScreen` shows `SignInRequiredState`). Pinned by `tests-e2e/clubs/missing-club.spec.ts`, `lib/social/club_setup.test.ts` and the `missing club` group in `clubs_screen_test.dart`.

### Club photo gallery

The **Photos** tab is a member-contributed gallery for the club (roadmap row 8, migration `20270301_001`, decisions §190) — distinct from the per-event photo gallery (which tags `run_photos` to an event occurrence). Backed by the `club_photos` table + the private `club-photos` Storage bucket, re-keying the `route_photos` shape to club membership:

- **Upload** is open to **any active member** (`club_photos` INSERT gate: `owner_id = auth.uid() AND private.is_club_member(club_id)`) — not just admins. Bytes are EXIF-stripped client-side before upload (web `stripExifFromFile`, mobile `stripImageExif`); the Go worker `club_photo_process` re-strips + writes a 512w thumbnail server-side (defence in depth).
- **Visibility** tracks the club: a **public** club's gallery is readable by anyone (incl. logged-out viewers); a **private** club's only by active members / the owner. The SELECT policy joins `club_photos → clubs` on `is_public OR owner OR private.is_club_member`, so flipping a club private propagates within the signed-URL TTL.
- **Delete** is photo-owner OR club admin (a moderation primitive — an owner/admin removes anyone's photo). **Caption edit** is photo-owner only.
- **Surfaces**: web `ClubPhotos.svelte` (`/clubs/[slug]?tab=photos`); mobile `widgets/club_photos.dart` mounted on `club_detail_screen.dart` (byte-identical iOS twin). Pinned by `rls_club_photos_test.sql` (17 pgtap assertions) + `clubs/photos.spec.ts` (Playwright) + `club_photos_helpers_test.dart`.
- **Prod gate**: a privacy-boundary surface — the RLS is fail-closed and pgtap-pinned, but a privacy / storage audit is a pre-prod deploy gate (decisions §190).

### Event detail capabilities

The `/clubs/[slug]/events/[id]` page carries the event's RSVP, results, and logistics features (web-first):

- **Recurring instance picker.** For recurring events, an instance picker above the RSVP row lets the user pick which occurrence they're RSVPing to / submitting results for; it previews the next 8 occurrences with a "Show all N upcoming" expander covering the full year (previously a hardcoded 6 over a 120-day window left weeks 7+ unreachable — persona #40).
- **Capacity + waitlist** (persona #42, migration `20261018_001`): when `events.capacity` is set, the `enforce_event_capacity` trigger demotes an over-capacity "going" RSVP to `waitlisted` (the "I'm in" button shows "Waitlisted" + a "Full · N on waitlist" note), and `promote_event_waitlist` auto-promotes the earliest-joined waitlisted attendee per instance when a going slot frees — except on a cancelled occurrence (an `event_exceptions` row), which promotes nobody (migration `20270725000001`, decisions § 1832). Capacity is per `(event_id, instance_start)`; `capacity` NULL = unlimited.
- **Cancel one occurrence** (persona #39, migration `20261019_001`): an event organiser can call off a single instance of a recurring series via "Cancel this occurrence" (optional reason) — it writes an `event_exceptions` row (audit: `cancelled_by` / `cancelled_at` / `reason`), the instance drops out of the live picker (RSVP replaced by a "This occurrence was cancelled" banner), and a `notify_event_cancel` trigger fans out an `event_cancel` notification to every going / maybe / waitlisted attendee of that instance. Organisers can reinstate by deleting the exception. The rest of the series is untouched. **Every listing surface subtracts the cancellation too** (decisions §620): `social/event_occurrence.ts#nextLiveInstance` picks each event's next occurrence that is still on, so the Events tab, the feed's next-event card and the dashboard's next-RSVP card advance to the following occurrence instead of advertising a called-off one — matching what the server-side reminder job (`enqueue_event_reminders`, `20261130_001`) has always done. A **cancelled occurrence beyond the next one used to be irreversible**: the picker hides it and the page landed elsewhere, so the reinstate control under the banner was unreachable. Organisers now get a "Cancelled occurrences" list of every cancellation still ahead (`upcomingCancelledOccurrences`), each row with its own Reinstate. `/social` Discover needs no subtraction: `search_public_events` returns the *series* and the card shows a cadence label ("Every week · Sat"), never a particular occurrence's date.
- **Finisher certificate** (persona #44): each finished + organiser-approved leaderboard row exposes a "Certificate" button that renders a certificate SVG client-side (`lib/runs/finisher_certificate.ts`) and downloads it as a PNG via the shared `lib/format/svg_raster.ts` rasteriser — no server-side PDF service. **Mobile parity (Android + iOS twin):** the same eligible rows on `event_detail_screen.dart` show a certificate action that opens `widgets/finisher_certificate_card.dart` — a native landscape card mirroring the SVG, captured via `RepaintBoundary` and shared to the OS share sheet (`share_plus`); `lib/finisher_certificate.dart` is the pure TS↔Dart parity twin of the web shaping (eligibility + time/distance/ordinal formatting).
- **Bulk results import** (persona #43, migration `20261028_001`): an organiser-gated "Import results CSV" panel parses a chip-timing CSV (bib / name / time, optional status) via `lib/runs/event_results_csv.ts` and upserts finishers through `bulkImportEventResults` keyed on `(event, instance, bib)`. Because most race finishers have no account, `event_results` is now account-optional (surrogate `id` PK, nullable `user_id`, `bib` + `finisher_name`); bib-only rows rank alongside account rows and render on the leaderboard by their printed name (web + mobile read parity), with certificates available. The import action is web-only per `decisions.md § 24`.
- **Results CSV export** (persona round-5 parkrun-owner): the organiser results-action row also exposes a "Download results CSV" button when there are results. `resultsToCsv` (in `lib/runs/event_results_csv.ts`) serialises the leaderboard to a header subset (`rank,bib,name,time,distance m,status`) the importer round-trips — re-importing an exported sheet parses cleanly. Web-only, organiser-gated.
- **Approving bib-only results** (persona round-5 event-organizer): when auto-approve is off, a race_director approves results from the leaderboard. Account-linked rows go through the `(event, instance, user_id)`-keyed `approve_event_result` RPC; bib-only rows (`user_id` NULL) are unreachable by that RPC and instead use `approveEventResultById`, a row-id-keyed UPDATE gated by the `event_results_update_self_or_director` RLS policy (audit columns written client-side from the signed-in director). Both surface the same Approve / Unverify controls.
- **Claim an imported result** (persona #43, migration `20261030_001`, organiser-approve per `decisions.md § 95`): a logged-in runner taps "This is me" on a bib-only row (`claim_event_result` RPC → `requestEventResultClaim`), and an event-organiser approves it from a "Result claims" queue under the leaderboard (`decide_event_result_claim` → `decideEventResultClaim`), which attaches their account to the row and auto-rejects competing claims. Claims live in `event_result_claims`; unapproved rows stay on the leaderboard by printed name.
- **Photo gallery** (persona #49, migration `20261025_001`): a Photos section aggregates every attendee's photos tagged to this event occurrence (`run_photos.event_id` + `event_instance_start`); event-tagged photos are readable by anyone who can see the event even when the underlying run is private. Any signed-in user gets an "Add photo" control (persona round-5 runner-social-group — previously race-only, which hid it on non-race group runs): when they have a finisher result here it attaches with zero extra clicks to their own `event_results.run_id`; otherwise they pick which of their runs the photo belongs to. **Organiser photos, moderation, integrity (#1150, migration `20270807000001`, decisions § 1905):** the picker (`fetchRunsForEventPhoto`) offers only runs that **started inside the occurrence's photo window** — `[occurrence − 2 h, occurrence + 24 h)`, the `event_photo_window` parity pair — because an insert trigger (`run_photos_event_integrity`) refuses any other run, and refuses an `event_instance_start` that is not a real occurrence of the series (`private.is_event_occurrence`, the SQL port of `expandInstances`). A **photo steward** — a club owner / admin / event organiser, or the event's `host_user_id` (`private.is_event_photo_steward`; the page asks `can_steward_event_photos` since the host column is not client-readable) — gets an **Add event photo** control that posts with **no run** (`run_photos.run_id` null), from two hours before the occurrence onwards, and a **Hide** action on every photo (`set_event_photo_hidden`; reversible, so it rides the undo bar, and the steward keeps the tile badged with **Restore**). A hidden photo leaves the gallery for everyone but its owner and the stewards — the gallery reads through `event_gallery_photos`, which applies that rule even to a photo on a public run (decisions § 1906) and returns nothing to a viewer who cannot see the event (§ 1909); an attendee's hidden photo stays on their own run, because a steward moderates the event page, not the runner's run — a steward never deletes another person's photo. Every viewer can **Delete** their own photo from the gallery (undo bar). A gallery load failure renders an error with retry, not the empty state. Host photos ride the same bucket, EXIF strip, `photo_process` thumbnail job, Art 20 export (`run_photos.json` by `owner_id`) and Art 17 drain as run photos. Mobile mirrors all of it in `widgets/event_photos.dart`. Pinned by `event_occurrence_photos_test.sql` (26 pgtap assertions), `event_photos_privacy_test.sql` (38, the refusal side), `event-photos-organiser.spec.ts` + `event-photos-nonrace.spec.ts`, and `event_photos_test.dart`.
- **Meetup map + directions** (persona #10, migration `20261027_001`): when the organiser set `meet_lat` / `meet_lng`, active club members see a static map pin + a "Get directions" button that opens the point in their maps app (`geo:` on Android, Google Maps universal URL elsewhere). The coordinates are read via the `get_event_meet_point` SECURITY DEFINER RPC (the raw columns are revoked from all client roles to avoid leaking organiser home addresses — see `api_database.md § clubs`); non-members and logged-out viewers see only the text `meet_label`.
- **Add to calendar** (persona round social-group): every upcoming, non-cancelled event exposes an "Add to calendar" button that downloads an RFC 5545 `.ics` for the chosen occurrence (the picked recurring instance, else `starts_at`). `lib/social/event_ics.ts#buildEventIcs` builds a single-VEVENT VCALENDAR client-side — UTC `DTSTART` (no VTIMEZONE), `DTEND` derived from `duration_min` when set, TEXT escaping + 75-octet line folding per spec, `SUMMARY`/`DESCRIPTION`/`LOCATION` from the event's own fields, the `/share/event/[id]` canonical as `URL`, and a stable per-occurrence `UID` so re-importing updates rather than duplicates — downloaded via the shared `lib/format/svg_raster.ts#downloadBlob`. Available to logged-out viewers too. The `.ics` **text builder** is web-only per `decisions.md § 24` and owes no Dart twin — a download is a browser concern. **Mobile mirrors the capability natively** (shipped 2026-08-19, `decisions.md § 692`): `event_detail_screen.dart` offers the same "Add to calendar" for the occurrence on screen, handing the event through `lib/calendar_intent.dart` over the `run_app/calendar` channel to `ACTION_INSERT` on `CalendarContract.Events` (Android, `CalendarBridge.kt`) or `EKEventEditViewController` (iOS, `CalendarBridge.swift`), so the runner confirms the save in their own calendar app — no calendar permission on Android, write-only access on iOS. Withheld for a past or called-off occurrence. Until then this line claimed mobile "hands off to the OS calendar via native intents", which described an intention rather than shipped code (swept 2026-08-13).
- **Add the whole series to calendar** (decisions §599): a *recurring* event additionally offers "Add whole series" beside the per-occurrence button (which relabels to "Add this occurrence"). `buildEventSeriesIcs` emits one VEVENT carrying an `RRULE` translated from `recurrence_freq` / `recurrence_byday` / `recurrence_until` / `recurrence_count`, plus one `EXDATE` per cancelled occurrence (`event_exceptions`), so the member's calendar maintains every future occurrence itself. The series is written on the **event's own wall clock** (`decisions.md § 1919`): `DTSTART;TZID=<events.timezone>` and `EXDATE;TZID=…` carry local readings, a `VTIMEZONE` derived from the platform tz database (`lib/social/ics_timezone.ts`) defines the zone, BYDAY restates the stored `recurrence_byday` codes (the organiser's local weekdays), BYMONTHDAY is the local day-of-month, UNTIL stays UTC, and the length travels as `DURATION`. So a New York Wednesday 21:30 series lands in the calendar on Wednesdays at 21:30 on both sides of the DST change. DTSTART anchors on the first local date carrying a stored weekday (RFC 5545 requires it to be a member of the recurrence set — `starts_at` need not be, e.g. a Tuesday-created Saturday series); an `until` + `count` pair resolves to whichever binds first, since an RRULE may carry only one. A legacy series with no stored zone is written in the viewer's zone, the clock the page expands it on. **Fail-closed:** a series the RRULE grammar cannot state exactly returns null and the button is not rendered at all — a monthly series whose local day is past the 28th (the app clamps a missing day-of-month to the month's last day and `BYMONTHDAY` skips the short month instead), a zone the platform does not know, and a series starting on the second pass of a fall-back hour (a TZID reading names the first pass). The series has its own UID so it neither overwrites nor is overwritten by a single occurrence. **Mobile carries the series too** (`decisions.md § 692`): "Add whole series" sits beside the per-occurrence action and sends the same recurrence as an RFC 5545 **RRULE value** — the one grammar both platforms already speak, stored verbatim in `Events.RRULE` on Android and mapped onto an `EKRecurrenceRule` on iOS. `calendar_intent.dart#buildRrule` mirrors every refusal above (monthly past the 28th withheld, `until` + `count` resolved to whichever binds first), and the rule is the stored codes read in the event's zone through the Dart `timezone` package, with the zone handed over beside it — `Events.EVENT_TIMEZONE` on Android, `EKEvent.timeZone` on iOS — so the phone expands it on the event's local weekdays rather than its own (`decisions.md § 1919`). The button renders only when the rule agrees with the app. **What mobile cannot mirror is `EXDATE`:** neither `ACTION_INSERT`'s extras nor `EKRecurrenceRule` carries exception dates, so the phone names the called-off occurrences ahead in a note under the button instead of silently keeping them — the same fail-loudly-rather-than-disagree stance § 599 takes for the rule itself.
- **Members-only events** (migration `20270113_001`, decisions §148): an event in a **public** club can be marked members-only via `events.is_public` — a "Members only" toggle in the event editor on **both web (`EventEditor`) and mobile (`event_form_sheet`)** (shown only for public clubs; a private club's events are already members-only via the club gate). A members-only event is readable only by the club's members/admins/owner, is excluded from `/social` Discovery, and its attendees / results / event-tied posts / pricing all inherit the same gate (the `events` SELECT policy is the single source of truth; the delegating surfaces inherit via their `exists(… from events …)` subqueries). Both web and mobile event-detail show a "Members only" badge. Default is public.
- **Edit an existing event** (web, issue #335): `EventEditor` is dual-mode — an organiser edits a live event via an "Edit event" button on `/clubs/[slug]/events/[id]` (gated on `isEventOrganiser`) that opens the editor with `existing={event}`, prefilling every descriptive field; save routes through `updateEvent(id, patch)` (RLS `is_event_organiser` gates the `events` UPDATE, no migration needed). Edit covers the fields an organiser fixes typos in — title, description, date/time, meeting point, category, class discipline/gym-template, route/distance/pace, capacity, members-only; the **structural** controls (recurrence, paid pricing, session-plan attach) stay create-only in the editor, each keeping its own instance-aware write path on the detail page. The date and time are read and saved on the **event's own clock** when it has a stored `timezone` (`lib/social/event_start_fields.ts`, `decisions.md § 1919`): an organiser editing a New York series from London sees Wednesday 21:30, not Thursday 02:30, a change of an hour is an hour in New York, and `timezone` itself is never rewritten; the hint under the inputs names the zone. A legacy row with no stored zone keeps the editor's clock. Switching an event that already has `race_sessions`/`event_results` to a **non-athletic** category warns first via `ConfirmDialog` (the athletic surfaces gate on `isAthleticCategory`, so the switch hides the leaderboard/race controls and orphans those rows) — fail-safe: it warns whenever that check can't be made. Web-only (mobile event editing is read-only per [club_events.md](club_events.md)); no Dart twin.


### Roles and permissions

| Action | owner | admin | event\_organiser | race\_director | member |
|---|---|---|---|---|---|
| Change club settings | yes | yes | | | |
| Remove / change member roles | yes | yes | | | |
| Create / edit / delete events | yes | yes | yes | | |
| Add attendees to events | yes | yes | yes | | |
| Arm / start / end a race | yes | yes | | yes | |
| Approve / reject results | yes | yes | | yes | |
| Post to the event/club feed | yes | yes | yes | yes | yes |
| Submit own race result | yes | yes | yes | yes | yes |
| RSVP | yes | yes | yes | yes | yes |

**Client gates must match these helpers, not `is_club_admin`.** Mobile's club events tab gated its create affordance on `isAdmin`, which excludes the one role that exists to run events — the server admitted the write and web allowed it, so `event_organiser` worked everywhere except mobile. Use the `isEventOrganiser` / `isRaceDirector` getters (`ClubView`) whose names match the SQL helper governing the action.

SQL helpers (`20260428_001_role_permissions.sql`): `is_event_organiser(club_id)` matches `owner | admin | event_organiser`; `is_race_director(club_id)` matches `owner | admin | race_director`. Both are `security definer` + pinned `search_path`. RLS policies on `events`, `event_attendees`, `race_sessions`, `event_results`, and `club_posts` reference these helpers rather than `is_club_admin` for the actions they govern. Admin-only actions (settings, member management) continue to use `is_club_admin`.

Admins can change any non-owner member's role from the Members tab on the web club page via a dropdown. The `setMemberRole(clubId, userId, role)` helper in `data.ts` and the `club_members` UPDATE policy (which requires `is_club_admin`) enforce this.

### Club-owned routes

A route can belong to a club via `routes.club_id` (nullable FK, added in `20260520_001_club_owned_routes.sql`). When set, the route survives admin churn — any club admin can edit it, any member can read it regardless of `is_public`. `user_id` stays as the *uploader* (audit trail), not authority. Two RLS policies layer on top of the existing user-owned and public-readable policies: `"club members read club routes"` (SELECT) and `"club admins write club routes"` (ALL).

Surfaces:
- The **Routes tab on `/clubs/[slug]`** lists `routes where club_id = <this club>`. Admins get a "New route" button (links to `/routes/new?club=<id>` so the new row inherits `club_id`) and a "Transfer from My routes" modal that flips `club_id` on a personal route via `setRouteClubId(routeId, clubId)`. Each row has a remove affordance that returns the route to the original uploader's library (`setRouteClubId(routeId, null)`).
- **`EventEditor` route picker** (`/clubs/[slug]/events/new` and the in-club modal) shows two `<optgroup>`s: "This club's routes" and "My routes". The picker dedupes by id so a saved-but-not-yet-transferred route doesn't appear twice.

Companion table: `saved_routes (user_id, route_id, saved_at)`. RouteExplorer's bookmark icon inserts a reference here instead of cloning the row, killing the duplicate-public-routes problem the previous "save to library" flow caused. The `/routes` "My routes" tab unions personal `routes` with `saved_routes` so bookmarks still appear in the user's library view. RLS scopes saved_routes rows to `auth.uid() = user_id`; the underlying route is gated independently by routes RLS (public + own + club-member). See `docs/architecture/decisions.md § 30` for the design rationale (and why we deliberately leapfrog Strava's user-only-ownership model here).

### Club links

A club can publish a website + socials row ("Visit our website"):
`clubs.website_url` / `instagram_url` / `strava_url` / `facebook_url`
(migration `20270131_001`). Each column is constrained to an `http`/`https`
scheme by a DB CHECK so a stored `javascript:`/`data:` URL can never reach a
rendered anchor; clients additionally drop non-http(s) values
(`normaliseClubLink`, web `data.ts` ↔ mobile `social_service.dart`) and render
the row with `rel="noopener noreferrer nofollow"` + `target="_blank"`. The four
columns are explicitly `grant select`-ed (the `clubs` SELECT lockdown,
`20260801_001`, denies new columns by default). Edited via the admin-only
`ClubEditor` (web, now dual-mode create+edit) / `club_form_sheet` (mobile,
dual-mode), rendered in the club header on web `/clubs/[slug]` + mobile
`club_detail_screen`.

## Data model

Tables: `clubs`, `club_members`, `events`, `event_attendees`, `event_exceptions`, `club_posts`, `event_results`. `event_results` is **account-optional** since `20261028_001` (persona #43) — surrogate `id` PK, nullable `user_id`, `bib` + `finisher_name` for imported non-account finishers, an additive `event_results_insert_organiser` policy for bulk import, and a CHECK requiring an account OR a bib+name; see `api_database.md § event_results`. Full definitions + RLS in `api_database.md § clubs / club_members / events / event_attendees / club_posts`. `clubs.requires_activity_waiver` + `club_members.activity_waiver_ack_at` (`20261023_001`) back the optional activity-risk waiver: an admin can require it at create time, and a member's acknowledgement timestamp is stamped on join (parkrun persona #45; per-event RSVP waiver is a follow-up). Since `20270801000001` the database enforces it on every join path (§ 1864): the self-join INSERT policies refuse a waiver club's row without `activity_waiver_ack_at`, and `join_club_by_token` refuses with `activity_waiver_required` until the caller passes `activity_waiver_ack => true`, which the web invite page and the phone (its invite screen and the club page's Join button) ask for in an acknowledgement step before joining. `event_exceptions` (`20261019_001`) is the per-instance cancellation/audit table — `(event_id, instance_start)` pkey + `cancelled_by` / `cancelled_at` / `reason`; organiser-only writes via `is_event_organiser`, readable with the parent event. Phase 1 migration: `apps/backend/supabase/migrations/20260416_001_clubs_and_events.sql`. Phase 2 migration: `20260417_001_phase2_social.sql` — adds recurrence columns on `events`, `instance_start` + composite pkey on `event_attendees`, `join_policy` + `invite_token` on `clubs`, `status` on `club_members`, `parent_post_id` + `event_instance_start` on `club_posts`, and the `join_club_by_token` RPC.

Narrow client-side unions in `apps/web/src/lib/types.ts`:

- `ClubRole = 'owner' | 'admin' | 'event_organiser' | 'race_director' | 'member'`
- `RsvpStatus = 'going' | 'maybe' | 'declined' | 'waitlisted'`
- `MembershipStatus = 'active' | 'pending'`
- `JoinPolicy = 'open' | 'request' | 'invite'`
- `RecurrenceFreq = 'weekly' | 'biweekly' | 'monthly'`
- `Weekday = 'MO' | 'TU' | 'WE' | 'TH' | 'FR' | 'SA' | 'SU'`
- `ClubWithMeta = Club & { member_count, viewer_role, viewer_status }` — returned by `browseClubs`, `fetchMyClubs`, `fetchClubBySlug`
- `EventWithMeta = Event & { attendee_count, viewer_rsvp, next_instance_start }` — returned by the event fetchers. `next_instance_start` is the next occurrence that is still **on** (cancelled ones subtracted) and is **null** once a series has none left — a stale date read as "the next one" is exactly how a cancelled occurrence kept being advertised, so the absence is modelled rather than papered over with `starts_at`. `viewer_rsvp` and `attendee_count` are scoped to that occurrence, falling back to `starts_at` for a past event so it still reports who attended; per-instance RSVPs use `fetchEventAttendees(eventId, instanceStart, opts?)`.

Roster reads are **paginated** so a club with hundreds of members / a large event doesn't refetch the whole roster on every view (mirrors `fetchFollowers` / `FOLLOW_PAGE_SIZE`). Both `fetchClubMembers(clubId, opts?)` and `fetchEventAttendees(eventId, instanceStart, opts?)` take `{ limit?, offset? }` defaulting to `ROSTER_PAGE_SIZE` (50); the Members tab and the event attendee list render page 1 plus a "Load more" affordance (`hasMore` = page came back full). The event page's exact going/maybe/declined/waitlisted counts (RSVP pills + capacity/waitlist math) come from `fetchEventRsvpSummary(eventId, instanceStart)` — a status-only scan independent of the paginated display roster, so the counts stay exact past page 1.
- `ClubPostWithAuthor = ClubPost & { author_display_name, author_avatar_url, reply_count }` — returned by `fetchClubPosts`. Reply bodies come from `fetchPostReplies(parentId)`.

The enrichment fields are joined client-side in `data.ts` rather than through a Postgres view — small fan-out, fewer moving parts, and it means RLS governs everything.

### Recurrence expansion

**Event times are absolute instants.** `starts_at` / `recurrence_until` / `instance_start` are `timestamptz`, and a client must serialize them with `toUtc()` before writing. Mobile's create sheet builds a LOCAL `DateTime` from its pickers, and a bare `toIso8601String()` emits an offset-less string that Postgres reads in the session's zone (UTC) — so every mobile-created event was stored off by the creator's offset. `instance_start` is worse than a display error: it is an exact-match key for attendee rows, so a naive string simply misses. Every server-bound instant in `social_service.dart` now goes through `toUtc()` (a no-op when already UTC). The create sheet also stamps `events.timezone` with the device IANA zone (`deviceIanaTimeZoneOrNull`, null when the platform cannot name one), as web stamps the browser zone — without it every mobile-created series expanded in each viewer's own zone (`decisions.md § 1919`).

Recurring events are stored as a single row (`recurrence_freq`, `recurrence_byday[]`, `recurrence_until`, `recurrence_count`). `apps/web/src/lib/social/recurrence.ts#expandInstances` walks the pattern client-side and returns the next N instance datetimes within a window. Per-instance attendee counts and RSVPs are queried by `instance_start` (which is ISO — the same value `expandInstances` returns). Monthly recurrence uses the day-of-month of `starts_at` and ignores `byday`; an empty or null `byday` on a weekly / biweekly series means the weekday of `starts_at`. Discover's day filter (`search_public_events` `p_byday`) reads it the same way, on the event's own clock, and never lists a monthly series under a weekday ([decisions § 1921](../architecture/decisions.md)). Every recurrence field is read in the event's own `timezone` (decisions § 1918): the weekday chips, the biweekly week count, the day-of-month and the time of day are the organiser's wall-clock, so a Wednesday 21:30 New York run stays on Wednesdays at 21:30 on both sides of a DST change; a wall-clock in a spring-forward gap moves forward and one in a fall-back overlap takes the earlier instant. The database answers the same question (`private.is_event_occurrence`, `private.event_occurrences`). A legacy event with no `timezone` still expands in each viewer's own zone. Cancelled occurrences (`event_exceptions` rows) are filtered out client-side — `expandInstances` itself is pure and doesn't know about exceptions, so `social/event_occurrence.ts` layers the subtraction over it (`nextLiveInstance` for the listings' `next_instance_start`, `isOccurrenceCancelled` for the dashboard's next-RSVP card, `upcomingCancelledOccurrences` for the organiser's reinstate list) and the event-detail page subtracts the cancelled `instance_start`s from its picker.

### Live race mode

Organisers can turn an event instance into a live, server-coordinated race: every RSVP'd attendee's watch / phone shows an "armed" screen, the organiser presses GO, and a recording the racer has started — before GO or after it — joins the race and times itself off the server's `started_at`, so finisher rows populate the leaderboard without anyone submitting manually. Nothing starts a recording on its own: the racer taps Start.

**Tables** (`20260425_001_race_sessions.sql`):

- `race_sessions` (`event_id`, `instance_start`, `status ∈ {armed, running, finished, cancelled}`, `started_at`, `started_by`, `finished_at`, `is_auto_approve`). Admin-only writes via `is_club_admin`; anyone who can see the event reads.
- `race_pings` (append-only, `user_id`, `lat`, `lng`, `distance_m`, `elapsed_s`, `bpm`). Writes allowed only while the parent `race_sessions.status = 'running'`; reads follow the parent event's visibility.
- `event_results.organiser_approved` + `organiser_approved_by` / `_at` columns. The trigger `event_results_set_approval_default` flips a new result to `organiser_approved = false` if the parent `race_sessions.is_auto_approve` is off; otherwise it's approved on insert.
- `approve_event_result(event_id, instance_start, user_id, approve)` security-definer RPC so admins can approve pending rows without needing a direct update policy.

**Realtime**: `race_sessions`, `race_pings`, and `event_results` are all published on `supabase_realtime` so the organiser panel, spectator page, and leaderboard all update without polling.

**Surfaces**:

- Web event page: admin race-control panel (Arm → GO → End), `is_auto_approve` checkbox before arming. Attendees see a "Race armed" / "Race LIVE" banner with live elapsed. Approval buttons on pending rows for admins.
- `/live/event/{id}/{instance_start}`: public-ish spectator page. Live MapLibre map with each runner as a colour-coded dot + recent trail (latest 30 ping samples from `fetchRecentRacePings`), Realtime-subscribed to `race_pings`. Below the map: live-ranked list of runners on course (distance, pace, elapsed), plus the finisher leaderboard. On a multi-course race both are split by course: the finisher boards by each result's `course_id`, the on-course board by each runner's RSVP'd course (`fetchAttendeeCourses`, read under the same club-visibility gate as `race_pings` and refreshed with each ping batch), with runners who picked no course in a trailing "Other" board and positions counted within each board (`social/event_courses.ts#groupRunnersByCourse`). **The on-course board is fetched per-runner-latest** via the `latest_race_pings` RPC (`DISTINCT ON (user_id)`, served by the `race_pings_by_race_user` index) rather than folded from the capped recent-ping window, so a slow back-of-pack runner whose newest ping has aged past that window is never dropped from the board. Rows are ordered furthest-first with a deterministic tie-break (`runs/race_leaderboard.ts#compareLeaderboard`: distance desc → elapsed asc → user_id) so ranks don't jitter between refreshes. **Refetch coalescing**: the `race_pings` INSERT subscription is filtered only by event + instance, so it fires once per ping from every runner (~N/5s for an N-runner field). The handler routes through `runs/live_refetch.ts#CoalescingRefetcher` — a trailing-edge debounce (`DEFAULT_REFETCH_DEBOUNCE_MS = 750`) collapses a ping burst to one recent-pings + leaderboard-RPC fetch, an in-flight guard never stacks a concurrent refetch, and a monotonic sequence guard discards a stale out-of-order resolution so the board can't flicker backward (issue #324). **Privacy**: the page is anon-accessible and the URL is shareable, so a runner's real `display_name` is shown only to a friend (a one-way follow edge in either direction, or the runner viewing their own broadcast) via `social/runner_handle.ts#shouldRevealDisplayName`; anon and signed-in non-followers see the anonymous `Runner #XXXX` handle, fail-closed. Mirrors the `/live/[id]` solo-page contract (decisions §, persona-hunt Round 3 Privacy #5). Bib-only imported finishers have no account, so they keep their printed name.
- Mobile (Android and iOS — one byte-identical Dart codebase, so the iOS race UI is this one): `lib/race_controller.dart` handles the **participant** side — polls for the current user's armed/running races, shows a banner on the Run tab idle screen, pushes pings at 10s cadence while recording, auto-submits an `event_results` row on stop. A recording joins its race through `attachIfRaceRunning`, called at Start and again on every race change, so one started while the race was still armed joins at GO, as Wear's `raceToBind` does; a recording already joined is never re-joined, including one whose race the host has ended. Its chip time is capped at the gun time, so the wait on the line before GO is not counted ([decisions § 1861](../architecture/decisions.md)). A submit that fails (the common case being a finish line with no signal) is persisted to `SharedPreferences` under `race_pending_results` and replayed by `drainPendingResults()` off the 60 s session poll — `submitEventResult` upserts on `(event_id, instance_start, user_id)`, so a replay is idempotent. Each entry carries the `user_id` of the account that recorded it, and only that account's entries are sent — the upsert files a row under whoever is signed in, so another account's entries stay queued untouched, an entry with no account (queued before this) is dropped rather than guessed at, and sign-out clears the queue as Wear's does ([decisions § 1858](../architecture/decisions.md)). A result the server refuses outright — PostgREST 400 / 403 / 404 / 422, i.e. a CHECK, the closed result window, RLS or a missing row, read off the SQLSTATE by `isRetryableRaceResultFailure` — is dropped instead of queued or retried, matching Wear's predicate of the same name; a rate-limit refusal is the one 400 kept, because it clears by itself. `detachRecorder()` drops the hosting state either way, so without the queue the finisher's official time was lost outright (decisions §560). **Courses + auto-finish (decisions § 1843):** `attachRecorder` resolves the racer's course (their `event_attendees.course_id`, else the only course) and builds a `RaceFinishDetector` (`race_finish.dart`) on that `event_courses` row's `finish_lat` / `finish_lng`, gated on its `distance_m` — the route is never fetched ([decisions § 1845](../architecture/decisions.md)). A course with no finish point or no distance, or a course-less event (gated on the event's own `distance_m`), has no auto-finish and finishes by hand. A course read that fails, or a multi-course race the runner picked no course for, races ungated with no `course_id` — never on the event's own distance, which is not their course (`fetchEventCourses` throws on a read error rather than answering an empty list). Each fresh, unpaused fix goes to `offerFix`; the closest in-zone fix (≤ 30 m, ≥ 90% covered) becomes the finish, the recorder stops itself and submits `finish_method = 'auto'`. Stop before that is a pause with Resume race / Finish race (`manual` at ≥ 90% covered, else a DNF with no method), timed at the instant Stop was pressed rather than the later tap ([decisions § 1857](../architecture/decisions.md)). The gun time is the finish fix plus the device-to-server clock offset minus `started_at`, the offset sampled off each `race_pings` insert's returned server `at` (round-trip midpoint, shortest round trip wins); chip time is the finish minus the runner's own Start on the device clock. When the session goes `finished`/`cancelled` before this runner has an outcome, the client shows "Race ended", keeps recording the run, and submits nothing (the server marks the DNF) — unless the runner had already pressed Stop and is on the Resume / Finish choice, in which case their Finish is still filed (§ 1857). The pending-result queue carries `finisher_status`, `course_id`, `gun_time_s`, `chip_time_s`, `finish_method` and the owning `user_id`. A late start (> 5 min after GO, or a first fix > 200 m from the course row's `start_lat` / `start_lng`, checked once both the first fix and the course have landed) is a run-screen banner only; a course whose start point is null — no route, or clipped away by the route owner's privacy zone — checks the time arm alone, and the route is never read for it (§ 1845). Event detail lists the courses, asks for one when Going on a multi-course race, lets a going racer change it, and groups results per course with gun / chip time and a Manual / Host badge — a device's automatic finish wears none, as on web ([decisions § 1862](../architecture/decisions.md)). A result the director has not approved shows no place (`…`) and a **Pending** pill. **Organiser Arm / Fire Go / End** controls now also live on Android (`SocialService.armRace / startRace / endRace` + the race-control card on `event_detail_screen.dart`, gated on `ClubView.isRaceDirector`), with live state updates via the existing `subscribeToEvent` realtime channel extended to `race_sessions`. They match web's: Cancel only while armed (the server refuses running → cancelled, and `raceEndPatch` stamps `finished_at` only on `finished`, which the temporal CHECK requires — § 1863), and End's confirmation states how many racers it will mark DNF (`fetchRaceDnfPreview` → `race_pending_dnf_count`). A race director's result row carries an actions menu — Approve on a pending row, Unverify on an approved one (not their own), and Edit (time + status, `editEventResultAsHost` with web's `hostTimeEditPatch` rule) — through `approve_event_result` for an account row and by row id for a bib-only one.
- Wear OS: `RaceSessionClient.kt` + `RunViewModel.observeRace` poll every 30s, surface a "RACE ARMED" / "RACE LIVE" caption above the Start button, and push pings while recording. Once a recording is bound to a running race, the watch reads the runner's chosen course (`event_attendees.course_id` → the `event_courses` row's `finish_lat` / `finish_lng` and `distance_m`; the route is never read, § 1845) and feeds every fix to `RaceFinish.kt` (the Kotlin half of the `race_finish` parity pair); reaching the finish stops the run and upserts `event_results` with `finish_method = 'auto'`, `course_id`, `gun_time_s` and `chip_time_s`. Stop before the finish pauses; on the paused screen Resume continues and the held button becomes **Finish** — a manual finish at ≥ 90 % of the course, a DNF short of it (no course, or a course with no `distance_m`: no auto-finish and an ungated manual finish; a course with no finish point: manual finish gated on its distance). The running screen shows the gun clock, which keeps running through a pause; a host End while running shows "Race ended" and no result is sent. Each fix is timed on the device clock (from its `elapsedRealtime` age, never its GPS time), and gun time is corrected by a server-minus-device offset sampled off each ping's server-stamped `at`, the shortest round trip winning — the phone's source (§ 1859). A Finish on the paused screen is timed at the Stop that paused it; a host End that lands after that Stop leaves the Finish on offer and files it (a Resume instead drops the race), and a DNF row carries no gun time, chip time or method with `duration_s` the elapsed recording (§ 1855, § 1857, § 1860). Results go through a DataStore queue (`RaceResultStore.kt`) replayed off the 30 s poll, so a finish with no signal is not lost. Participant-only: no RSVP, course picker or organiser controls on the wrist — use web or the phone.

**Courses, gun time and the finish rule** (`20270727000001`, [decisions § 1842](../architecture/decisions.md)). A race can have one or more courses (`event_courses`: name, route, distance, order, and a server-derived finish point). The flow: the host builds the courses in the event editor (the route + distance fields are the **main** course; "Add a course" adds alternatives, each with its own name, route and distance, reorderable and removable; a save deletes, then updates, then inserts every new course in one statement, so a save that fails part-way never half-inserts and a retry repeats nothing unsafe, and a write RLS filtered to no row is reported rather than taken for success — § 1854), a racer picks a course when they RSVP (required on a going / waitlisted RSVP once an event has more than one course — the web RSVP shows a "Your course" select and refuses "I'm in" without it), the host presses GO, the racers run, and each racer's device records the finish.

- **GO is server time.** `race_sessions.started_at` is stamped `now()` by the database on the move to running, whatever the host's device sent.
- **Finish rule (clients implement it — mobile + Wear).** A racer is *finished* when they are within **30 m** of the course's finish point (`event_courses.finish_lat` / `finish_lng`) **and** their covered distance is at least **90 %** of the course `distance_m`. The finish time is the timestamp of the **closest-approach sample** to the finish point within that pass, not the first sample inside 30 m. `gun_time_s` = finish time − `race_sessions.started_at`; `chip_time_s` = the device's own recorded duration, capped at `gun_time_s` for a recording started before GO (§ 1861). Clients write `duration_s = gun_time_s` when the session has a `started_at`, else the chip time, with `finish_method = 'auto'`. A racer who stops is **paused, not finished**; pressing "Finish race" before 90 % files a **DNF** — no finish method, no `gun_time_s` and no `chip_time_s`, since there is no finish to time, and `duration_s` is the recording's elapsed seconds, the same shape the host's End files ([decisions § 1855](../architecture/decisions.md)); a racer's own Finish after 90 % that the rule did not catch is `finish_method = 'manual'`. A course with no route has no finish point, so its racers finish by hand.
- **Finish point.** Copied from the route's last waypoint when the course gets its route — racers read it from the course row and never need the route, which they may not own and which a non-owner sees privacy-clipped. Attaching a route therefore publishes its finish to everyone who can see the event, so the organiser may only attach a route they can see.
- **Write window.** A racer's own result on a raced occurrence is refused only once the race finished more than 24 h ago — so a finish queued with no signal still lands when the phone reconnects, and an armed or cancelled race takes a runner's own result like an occurrence with no race ([decisions § 1849](../architecture/decisions.md)); devices file a gun time only once there is a `started_at`. Results upsert on `(event_id, instance_start, user_id)`, so a resumed racer's later finish replaces an earlier one. Clients send `course_id` / `gun_time_s` / `chip_time_s` / `finish_method` only when known; a result with no course takes the racer's RSVP'd course (or the event's only course) server-side.
- **Ending the race** files a host DNF (`finish_method = 'host'`, the racer's last ping's distance and elapsed) for every attendee who pinged the race but filed no result. The End dialog, web and phone, states how many first (`race_pending_dnf_count`).
- **Cancelling** is a pre-start action: armed → cancelled only. A running race can only be ended (`race_sessions_enforce_transition` refuses running → cancelled), and web and phone offer Cancel only while armed ([decisions § 1863](../architecture/decisions.md)).
- **Leaderboards are per course.** `recompute_event_ranks` partitions by course (an event with no courses ranks as one field, as before). The web results card, the phone's results list and the spectator page show one board per course, the gun / chip split, and a **Manual** or **Host edited** badge — a device-detected finish wears none, so an unbadged time is a measured one (§ 1862).
- **Organiser edits.** A race director can edit any result's time and status from the results card, on web or the phone (on web an organiser can for bib-only rows too); the edit moves the gun time with the ranked time on a row that has one (a chip-only row, like a web "Submit my time", stays chip-only: an edit is not a gun reading) and is stamped `finish_method = 'host'`.

Platform status: web ✓ (editor, RSVP course pick, per-course boards, End preview, host edit, spectator); the phone (one Dart codebase for Android and iOS — the iOS race UI is the shared twin, not a port) and Wear OS race against this contract, the phone also as race director; the Apple Watch is a participant relay without auto-finish — see [parity.md](../product/parity.md). The paid-registration path does not carry a course yet: a paid seat is written by the Stripe webhook with no course, and the racer then picks one from the RSVP select.

**Not wired yet** (deferred follow-ups):

- Remote auto-start of the recorder on the `running` signal, on any device. The racer taps Start; a recording started while the race is armed joins it at GO (phone, Wear OS), but nothing starts one. Plumbing the permission flow + countdown into a remote trigger is per-platform engineering.
- Apple Watch auto-finish. The wrist shows Race armed / Race LIVE (`RaceBannerView`), pings while it runs and relays one finisher time through the phone at Stop, but it does not read the course, detect the finish or file gun / chip time or a finish method — see [parity.md](../product/parity.md).
- The late start is shown on the run screen only (a banner on the phone, a caption kept under the race clock on Wear OS); it is not carried on the result.

### Event results

`event_results` (`20260424_001_event_results.sql`) is a per-`(event_id, instance_start, user_id)` leaderboard. Each row carries `run_id` (nullable — manual entries and DNF / DNS don't need a run), `duration_s`, `distance_m`, `finisher_status ∈ {finished, dnf, dns}`, and a server-maintained `rank` that a trigger (`recompute_event_ranks`) rewrites on every insert / update of `duration_s`, `finisher_status` or `course_id` and on delete — **within the result's course** since `20270727000001` (a NULL course is one bucket). Non-finishers never get a rank (null). Race provenance: `course_id`, `gun_time_s`, `chip_time_s`, `finish_method ∈ {auto, manual, host}` — see § Live race mode for who writes what. The web "Submit my time" on a raced occurrence writes `finish_method = 'manual'` with the run's duration as the chip time (web has no recorder, so no gun time); outside a race it writes none. RLS: anyone who can see the parent event can read; users can write their own row; club admins / owners can edit or delete any row on their club's events.

`runs.event_id` is a convenience FK added by the same migration — stamped when a user picks a run from the Submit-my-time flow, so the run-detail page can back-link to the event it was part of. The column is nullable and not required for a run's existence.

Clients:
- Web: `apps/web/src/lib/core/data.ts#fetchEventResults / submitEventResult / removeEventResult / fetchRecentRunsForPicker`. Results card lives on `/clubs/[slug]/events/[id]` under the RSVP / updates section; a `Submit my time` button opens a run picker with the user's 20 most recent runs plus explicit "Record DNF" / "Record DNS" options.
- Android: `SocialService.fetchEventResults / submitEventResult / removeEventResult / fetchRecentRuns` + `_ResultsSection` / `_SubmitTimeSheet` on `event_detail_screen.dart`.

### Realtime

`club_posts`, `event_attendees`, and `club_members` are published on the `supabase_realtime` publication (migration `20260418_001_social_realtime.sql`). Both web and Android club / event detail surfaces subscribe via `postgres_changes` and debounce reloads at 250ms so a burst of changes (a cascading delete, a multi-member update) triggers one enriched refetch rather than N. Payloads are ignored in favour of a fresh fetch — RLS governs the subscription, so the payload's visibility would need re-validation anyway, and the REST enrichment path is already the source of `ClubWithMeta` / `EventWithMeta` shapes.

Subscriptions unmount cleanly: the web pages call `supabase.removeChannel` in `onDestroy`; Android screens call `SocialService.unsubscribe(channel)` in `dispose`.
