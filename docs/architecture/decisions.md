

## 2301. Backfills in unmerged migrations run as private functions so pgTAP can pin them

2026-11-04, PR #1280. A one-shot backfill can't be pinned by pgTAP, because the migration has already run by the time the suite starts. The DM conversation and `published_from_plan_id` backfills are therefore `private.backfill_*()` functions, revoked from every client role; the migration calls each once and the suite calls the same body again on fixtures. The DM backfill is set-based (a mapping table and one `UPDATE … FROM` on equality keys, instead of one UPDATE per pair, which scanned the table once per pair under `SHARE ROW EXCLUSIVE`) and raises `23502` if any message is left without a conversation, so the follow-up VALIDATE migration can't be stranded half-applied. **Rejected:** copying the statement into the test, because the copy would drift from the migration without failing.

## 2302. The dev basemap fallback is imported dynamically and guarded on the build output (amends § 2299)

2026-11-04, PR #1280. § 2299 said the production build drops the module because `import.meta.env.DEV` is false there, but `maplibre.ts` imported it statically, so only the bundler's dead-code removal kept it out. `maplibre.ts` now runs `await import('./dev_basemap_fallback')` inside the DEV branch; the top-level await is there so the `setStyle` patch exists before any surface builds a map. `scripts/check_web_dev_only_code.mjs` in `build-web` fails if the `[dev-basemap]` marker appears in any client chunk, and also fails if the module stops carrying that marker; it was checked both ways (fails on a forced static import, passes on the real build). Installing is idempotent: the prototype keeps the original `setStyle` and the current check under `Symbol.for` stamps, and each map keeps its state and one set of listeners. A settle that arrives during a check sets a flag that runs one more check afterwards.

## 2303. A heard race distance snaps within the rounding of the unit the runner wrote it in (amends § 2292)

2026-11-04, PR #1280. The 80.5 m mile tolerance applied to metric figures too, so a stated 50.06 km became 50 km. The extractors now report the unit the runner wrote (`ultra_distance_unit`, and a per-race `distance_unit`). `snapStatedDistanceM` takes it: half a tenth of a mile (80.5 m) for `mi`, half a tenth of a km (50 m) for `km` or anything unreadable, still landing on a whole km or a whole mile. So 31.1 mi still reaches 50 km and 160.9 km still reaches 100 miles, but 50.06 km is kept. The unit is read from the text rather than the client's preference because a runner can type either unit, and this way no client changes.

## 2304. A coded database error is classified by its code, not by words in its message

2026-11-04, PR #1280. `errorCopyKey` and both `classifyAuthError` rails used to check message substrings before codes. A unique-constraint error (23505) whose constraint name contained "rate limit" showed "too many requests", and a 22023 "listing not found" showed "not found" instead of "invalid". The message is now read only when there is no code, or the code is `P0001`, plus the RPCs' `not authenticated` under `42501`. `errorCopy` also logs a scrubbed, length-capped message, because console calls become Sentry breadcrumbs once a reader consents and server text can quote row values.

## 2305. Route-photo bytes no row references are erased by a gated server sweep, closing the § 2293 gap

2026-11-04, PR #1280. § 2293 left two ways for route-photo bytes to outlive their rows: a client sweep that never ran (tab closed, offline), and a club admin deleting a club route someone else uploaded photos to, whose folder the admin cannot touch. Both kept personal data invisibly until account deletion. Migration `20271106000020` follows the export reap (§ 1144): SQL decides what is orphaned and the Go worker erases through the Storage API, because a `storage.objects` row delete leaves the bytes behind (§ 1049). `route_photo_orphan_paths` (service role) returns `route-photos` objects that no `route_photos` row references as `storage_path`, as `thumb_512_path`, or as the upload behind a mobile placeholder row. A statement-level AFTER DELETE trigger queues one `route_photo_orphan_sweep` job per statement with the deleted paths, so the normal case is erased within the worker's poll interval. A nightly cron at 04:43 queues the backstop over objects last written more than 24 hours ago. The grace covers the seconds-long web upload-then-insert and worker thumb-then-PATCH windows (the mobile window is covered by the placeholder check); it is measured from the last write so a worker outage cannot shorten it, and it is a constant so no payload can ask for zero. The worker deletes in batches of 100, at most 20 batches a run, fails a job whose "deleted" path is still listed rather than spinning, and logs counts only. Deleting live photos is the failure mode, so everything is gated on `private.feature_flags` `route_photo_orphan_sweep` (absent = off, the worklist empty): opening it is a deploy-time item for the CISO / Security Analyst in deployment.md, not missing code. The client sweep stays as the uploader's immediate path. Pinned by `route_photo_orphan_sweep_test.sql` (15) and `handler_route_photo_orphan_sweep_test.go` (10).
