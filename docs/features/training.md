# Training plans

Runna / Garmin-Coach parity. Web-first in v1. The data model is shared so the Android app and the structured-workout execution loop can land without a schema change.

## Plan editor (web)

The plan detail page now supports inline workout edits. Hovering a day-tile reveals an edit button (`apps/web/src/lib/components/WorkoutEditor.svelte`) that opens a side-drawer: kind, distance, target pace (single value or a start → end progression for phase-based pace bumps), tolerance, zone label, and notes. Backed by `updatePlanWorkout` in `data.ts`. The editor (web) and the edit pencil + long-press (mobile `workout_edit_sheet.dart`) are offered only to who the `plan_workouts` update policies admit: the plan's owner, or the athlete's active coach on a non-template plan (`isActiveCoachOf`, web `data.ts` / mobile `TrainingService`, the same test as `private.is_active_coach_of`). Anyone else reading the plan, such as a library or template viewer, opens the read-only workout page instead. The mobile sheet takes distance and pace in the runner's unit, clears a target whose field is emptied, and switching a day to rest clears every target, as web does.

**Moving a workout to another day** (issue #1186, [decisions.md § 2073](../architecture/decisions.md)). For the plan's owner the editor opens with a **Day** field listing the other days of the workout's plan week that it may move to: not a past day, not past the plan's end, and not a day held by a completed workout or a race (`workoutMoveDays` in `training/plan_move.ts` ↔ `plan_move.dart`). A day that already has a row is labelled "(swaps with …)": saving calls `move_plan_workout`, which gives that row the moved workout's old day, so on a generated week, where every day holds a row, Thursday's rest day takes Tuesday when the tempo moves to Thursday. The move is saved before the other fields. A completed workout keeps its day and is not offered the field. Mobile mirrors it as **Move to another day** in the plan owner's workout edit sheet, which opens a day list (`widgets/workout_move_sheet.dart`) and calls `TrainingService.moveWorkout`. Moves never leave the plan week, so no week's target volume changes. The per-day uniqueness (`plan_workouts_one_per_day`) is deferrable for exactly this; see [api_database.md](../backend/api_database.md).

For structured kinds (`tempo`, `interval`, `marathon_pace`, `race`) the editor also exposes a Structure block: warmup distance, a Repeats / Steady mode toggle, and cooldown distance. Repeats mode edits the count + per-rep distance + per-rep pace + recovery distance + recovery pace (`easy` / `jog`); Steady mode edits distance + pace. The block writes the `plan_workouts.structure` jsonb in the canonical `WorkoutStructure` shape from `training.ts` so the read-side on `/plans/[id]/workouts/[wid]` renders the new values without translation. Flipping kind to an unstructured kind (easy / long / recovery / rest) clears `structure` to `null`.

Migration `20260420_001_plan_editor.sql` adds:
- `plan_workouts.pace_zone` — free-text label (E, T, I, MP, etc.) for UI colouring
- `plan_workouts.target_pace_end_sec_per_km` — for pace progressions (null = flat pace)
- `training_plans.source` — `'generated' | 'imported' | 'manual'`
- `training_plans.rules` — jsonb array of plan-wide guidance strings rendered in the hero

Week-level and plan-level editing (`updatePlanWeek`, `updatePlanMeta`) are exposed in `data.ts` but aren't wired to the UI yet — a plan-meta drawer is the natural follow-up.

## Coach chat (web)

A Claude-powered second-opinion chat embedded below the week grid on the plan detail page (`apps/web/src/lib/components/CoachChat.svelte` + `src/routes/api/coach/+server.ts`).

**What it does**: critiques adherence, answers "should I run tomorrow?", explains what a workout is designed for, flags red-flag patterns in recent runs.

**What it explicitly doesn't do** — captured in the system prompt and `decisions.md #12`: generate new plans, prescribe medical or nutrition changes, invent stats it doesn't have in context. Building a plan with AI help is the separate plan assistant below, and changing one is AI plan edits; the chat links to both rather than doing either.

**Architecture**:
- Server endpoint `POST /api/coach` — runs per-request (`prerender = false`), reads the caller's Supabase JWT to scope context pulls via RLS.
- Context = user profile + active (or specified) plan + `plan_weeks` + `plan_workouts` + last 20 runs, serialised as JSON. Phase 4 adds the Tier-1 cross-modality slice: a bounded `recent_lifts` array (capped per-session gym summaries) + a `nutrition_7d` daily-average rollup (gated on the Art 9 health-consent, like DOB/HR). Both self-hide when nothing is logged — see [multi_modal.md § Cross-modality](multi_modal.md#cross-modality-touches-tier-1--ship-with-phase-4-this-is-the-headline).
- **Prompt caching at two breakpoints**: (1) coach system prompt, (2) first user message carrying the context dump. Subsequent chat turns hit the cache for ~95% of input tokens. `cache_control: { type: 'ephemeral' }` on both blocks. The UI surfaces `cache_read` / `cache_creation` / `input` / `output` token counts below the composer for verification. **The ephemeral cache only hits on a byte-identical prefix**, so the volatile `now_iso` timestamp is the LAST field of the serialised context (`buildContext`) — leading with it busts the cache on every message (issue #390, pinned by `context_cache.test.ts`).
- Model: `claude-sonnet-5-5` (`COACH_ANTHROPIC_MODEL` in `providers.ts`), with extended thinking off (`thinking: { type: 'between_tools' }`, effort `low`) so the output cap is spent on the reply, and a `refusal` stop treated as a mid-stream failure. Output tokens: 768 (free tier) / 2048 (Pro tier). Context window: 30 runs (free) / 75 runs (Pro) — `maxRunsLimit` in `apps/web/src/lib/coach/types.ts`.

**Deploy requirement**: the endpoint runs as a Node 24 Lambda Function URL behind the prod CloudFront distribution (see [`apps/web/deployment.md`](../../apps/web/deployment.md) and [decisions.md § 53](../architecture/decisions.md#53-web-app--domain-on-aws-s3--cloudfront--lambda--route-53-not-vercel-or-cloudflare-pages)). The static SvelteKit build (under `adapter-static`) does not serve `/api/coach`; CloudFront routes that path to the Lambda. `ANTHROPIC_API_KEY` is sops-encrypted in the private estate repo at `../infra-secrets/threkir/<env>.sops.yaml` — never in this public repo (see [`infra/README.md`](../../infra/README.md)). Terraform reads it at apply time and encrypts it, with the other coach credentials, into one KMS ciphertext bag on the Lambda's environment; the handler decrypts the bag once per cold start under the execution role (`apps/web/src/lib/core/lambda_secrets.ts`, decisions § 1671), so the key is never a plaintext env var. Missing key returns 503.

## AI plan assistant (web)

A "Describe the plan you want" box at the top of the `/plans/new` wizard (`PlanEditor.svelte`). The runner types something like "sub-2 half on 14 March, 4 days a week, last 5k was 26:30"; the box fills the wizard's own fields, and the deterministic generator builds the plan from them exactly as it does for a hand-filled form. **The model never writes a workout, distance, pace or weekly volume** ([decisions.md § 1930](../architecture/decisions.md), superseding § 12 in part).

- **Endpoint** `POST /api/coach/plan-request` — handler `apps/web/src/lib/training/plan_request/handler.ts`, dev wrapper `src/routes/api/coach/plan-request/+server.ts`, prod routed inside the coach Lambda (`lambda/coach/src/index.ts`, segment `plan-request`). One non-streaming `claude-opus-4-8` call with forced tool use (`extract_plan_inputs`), 12 s timeout; refusal or a missing tool call returns 422.
- **Trust boundary** `validatePlanInputs` (`plan_request/inputs.ts`) clamps or drops every field: goal race whitelisted (default half), or an ultra: `ultra_distance_km` past the marathon and at most 400 km becomes `custom` plus `goalDistanceM` and selects the wizard's matching Ultra entry, with an out-of-band distance dropped rather than clamped (decisions § 2069); race date must be after today and within two years, goal time dropped unless it is under 10 hours and its pace is 2:30 to 15:00 per km for the distance (an ultra's runs to the race goal cap at up to 20:00 per km), recent 5K kept only between 12:00 and 59:59, days per week 3 to 7 (default 4), weeks 4 to 24, walk-run forces the 5K goal and drops the goal time. Fields it had to default are returned as `assumptions` and listed under the filled form.
- **What the client does with it**: sets the fields, routes a race date through `racePlanPreset` (the same arithmetic as the race calendar's "train for this race" link, so a too-soon or past date is refused with the same reason), and fills the recent 5K **without** ticking "this reflects my current fitness". The runner still confirms that, so an extracted time cannot anchor paces on its own. The ramp check then grades the generated plan as usual.
- **Consent**: requires AI disclosure **v3** (`AI_DISCLOSURE_VERSION_PLAN_AI`, migration `20270816000001`); an older acceptance gets the standard `ai_disclosure_required` 403 and the box links to `/coach` to accept.
- **Cost**: one AI Coach message from the same daily counter (`increment_coach_usage`; free 2/day, Pro 10/day), refunded on any provider failure. Over the cap the box shows the daily-limit message; the manual form keeps working on every failure path.
- **Prod gate**: `PUBLIC_AI_PLAN_ENABLED` (default off) hides the box, and the box also needs `PUBLIC_COACH_ENABLED`. The endpoint has its own server half: it answers 503 before auth unless `AI_PLAN_ENABLED` is truthy (the dev route reads `PUBLIC_AI_PLAN_ENABLED`; the coach Lambda reads `AI_PLAN_ENABLED`, a `coach_config_keys` entry set in the estate sops file), so a direct POST cannot spend the key while the feature is off. Flipping it on in prod waits on owner + counsel sign-off of the § 12 liability surface and the v3 disclosure copy.
- **Ways in**:
  - **From a new Coach chat.** While the assistant is on, the suggestions include "Build me a half marathon training plan" (no plan yet), "Build me a beginner plan to run my first 5K" (no runs yet) and "Help me plan my next race" (has a plan). Asked for a plan in any words, the Coach still writes no workouts: `planHandoffAddendum` (`coach/system_prompt.ts`) tells it to answer in a few sentences with one `[Build this plan](/plans/new?describe=…)` link, whose description combines the request with facts from the context (a recent 5K only if a run shows one). With the assistant off, the same addendum points at `/plans/new` plainly. The Coach reads the flag server-side (`CoachConfig.aiPlanEnabled`, from `AI_PLAN_ENABLED` on the Lambda), so the prompt never advertises a box that is not there.
  - **From the link.** `/plans/new?describe=<text>` (capped at 600 characters) opens the training wizard, prefills the box, runs the fill once, and then drops `describe` from the URL so a reload does not spend another Coach message.
  - **From `/plans`.** A "Describe a plan with AI" link in the toolbar and the empty state goes to `/plans/new?type=training#ai-plan`.
  - **On mobile.** `PlanNewScreen` has the same box (`plan_request_client.dart` calls the same endpoint), gated on the `ai_plan` field of `/app-capabilities.json` (`coachEnabled() && aiPlanEnabled()`). The Coach screen shows the same suggestions and opens a tapped `/plans/new?describe=…` link in `PlanNewScreen` with the box prefilled and run.
- **Coach links.** Before this, the Coach's markdown sanitiser allowed only `https` / `http` / `mailto`, so the `/runs/<id>` links its prompt asks for were rendered as plain text. App paths beginning with a single `/` are now kept and open in place (no forced `target=_blank`, which SvelteKit treats as external); `//host` and the other spellings a browser resolves off-site are still refused.

## AI season request (web + mobile client; endpoint only so far)

The first step of multi-race season planning ([#1181](https://github.com/Absence0760/threkir/issues/1181)): a plain-English description of a season ("Richmond Marathon Nov 14, Two Oceans Apr 4, Comrades Jun 13 is the big one") becomes a validated race list the runner confirms before anything is generated. The season builder then chains one generated plan per A race from the confirmed list. **The model only lists races — it never writes a workout, a volume or a plan** (decisions § 12, § 1930). The confirmation UI is not built yet; the endpoint and both client wrappers are.

- **Endpoint** `POST /api/coach/season-request` with `{ request, today }` — handler `apps/web/src/lib/training/season_request/handler.ts`, dev wrapper `src/routes/api/coach/season-request/+server.ts`, prod routed inside the coach Lambda (segment `season-request`, 16 KB body cap). One non-streaming `claude-opus-4-8` call (the plan assistant's model) with forced tool use (`extract_season_races`, no extended thinking), 20 s timeout, description capped at 1,500 characters. `today` is trusted within a day of the server's UTC date (`resolveToday`, shared with the plan assistant). Answers `200 { races: SeasonRace[], assumptions: string[] }` (`season_types.ts`); refusal or a missing tool call is 422. A 200 can carry an empty list when every race was dropped — the assumptions then say why.
- **Trust boundary** `validateSeasonRaces` (`season_request/races.ts`), in order: an entry with no usable name is dropped; the date must be a real `yyyy-mm-dd` after today and at most two years out — a date up to a year in the past is a year-less date resolved to this year, so it moves forward a year, and anything else (today included) is dropped; distance 5 to 400 km inclusive, dropped (never clamped) outside it, and snapped to the exact standard road distance when within 0.5 % of one; goal time kept only at 2:30 to 20:00 per km (wider than the wizard's, because a 100-mile goal is mostly walking); duplicates (same date and distance within 1 %, or same name and date) merge, keeping the stronger stated priority and any goal time; sorted by date (longer first on a shared day) and capped at 12, keeping the earliest; a race with no A/B/C becomes **B**, and when no race is A the longest becomes **A** (the later one on a tie, since a season builds toward its end).
- **Assumption keys** (one localized line each): `race_dropped_invalid`, `race_dropped_date`, `race_dropped_distance`, `race_date_next_year`, `goal_time_dropped`, `race_duplicate_merged`, `races_capped`, `priority_default`, `priority_a_assigned`. Web renders them through `seasonAssumptionMessageKey` (`training/season_request_labels.ts`, keys `planEditor.seasonAssumption*`); mobile through `seasonAssumptionLabel` (`season_request_client.dart`, ARB keys `planNewSeasonAssumption*`).
- **Clients**: web `requestSeasonRaces` (`training/season_request_client.ts`, transport in `season_request_transport.ts` with the session and fetch injected so it is unit-tested); mobile `requestSeasonRaces` (`season_request_client.dart`, through `postPlanAssistantRequest`, the transport it now shares with the plan assistant). Both send the payload hash, refresh the JWT once on a 401, map statuses to the plan assistant's `PlanRequestError` kinds, and refuse a 200 body outside the contract (a malformed race, an unknown assumption key, more than 12 races) as `unavailable`.
- **Consent, cost and gate**: the plan assistant's rails unchanged — AI disclosure **v3** (it sends the same kind of description, goal races with dates and target times, for the same purpose of filling the planner's own fields), one AI Coach message (`spend_coach_usage_slot`, refunded with its ticket on refusal, a missing tool call or a provider error), and the same `PUBLIC_AI_PLAN_ENABLED` / `AI_PLAN_ENABLED` flag pair (503 before auth while off).

## AI plan edits (web)

**Adjust with AI** in the Adjust plan dialog on `/plans/[id]` (owner, non-template plans). The runner types a change such as "move my long run to Saturday" or "make next week easier"; the page shows the suggested changes as a before/after diff and saves nothing until **Apply AI-suggested changes**. **The model picks operations, never values** ([decisions.md § 1979](../architecture/decisions.md), superseding § 1930 in part).

- **Endpoint** `POST /api/coach/plan-edit` with `{ plan_id, request, today }` — handler `apps/web/src/lib/training/plan_edit/handler.ts`, dev wrapper `src/routes/api/coach/plan-edit/+server.ts`, prod routed inside the coach Lambda (segment `plan-edit`). The handler reads the plan itself under the caller's JWT; the body never carries it. One `claude-opus-4-8` call with forced tool use (`propose_plan_edits`, no extended thinking), 15 s timeout, request capped at 400 characters.
- **Operations** (`plan_edit/ops.ts`): `move_workout` (another day of the same plan week), `swap_days` (two workouts in one week), `scale_week` (factor 0.5 to 1.1, never above 1 in a taper or race week), `mark_recovery`, `skip_workout`. The model sees the open weeks with short references (`W1`…), day, type and size — no ids, notes or paces. `validatePlanEditOps` drops any reference it did not hand out, any done / skipped / past / race / rest target, a date outside the target's week or the plan, a second operation on one target and anything past 12 operations, and reports how many it dropped. A request the operations cannot express (a new workout, a pace) comes back `unsupported`.
- **Apply + grade** (`plan_edit/apply.ts`): a `move_workout` onto a day that already has a row trades days with it (on a generated week that is usually a rest day), and is dropped when that day holds a race or a completed workout; the page saves every date change together through `reschedule_plan_workouts` before the other fields, because a swap passes through an occupied day (decisions § 2073). recovery is `recoveryWorkoutPatch` + `recoveryWeekVolume` (`plan_bulk_ops.ts`), the same as the week's button; scaling skips structured sessions. `planEditLoadCheck` bands each open week's planned volume against the four weeks before it (ACWR edges from `coach_load.ts`, the runner's recent weekly volume before week 1). A week newly in the **high** band rejects the set; a week newly **elevated**, or two hard sessions newly on adjacent days, needs a second confirmation. Saved through `updatePlanWorkout` / `updatePlanWeek` / `markWorkoutSkipped`.
- **Consent**: AI disclosure **v4** (`AI_DISCLOSURE_VERSION_PLAN_EDIT_AI`, migration `20270825000001`, § 1980); an older acceptance gets the `ai_disclosure_required` 403 and the page links to Settings → Account.
- **Cost**: one AI Coach message from the shared daily counter, refunded on a refusal, a missing tool call or a provider error; the consent check, the plan read (404 not yours, 409 nothing to change) come first so they spend nothing (§ 1981).
- **Prod gate**: `PUBLIC_AI_PLAN_EDIT_ENABLED` (default off) hides the option and also needs `PUBLIC_COACH_ENABLED`; the endpoint answers 503 unless the coach Lambda's `AI_PLAN_EDIT_ENABLED` (a `coach_config_keys` entry) is truthy. **Pre-deploy sign-offs:** owner + counsel on the liability surface (a model proposing changes to a saved plan); counsel / CISO on the v4 disclosure copy and the privacy policy's Anthropic description — the copy one gates the deploy carrying the migration, not just the flag flip.
- **From the Coach**: with the server flag on, `planEditHandoffAddendum` makes the Coach answer a plan-change request with one `[Adjust my plan](/plans/<id>?adjust=…)` link to the plan in its context. `/plans/<id>?adjust=<text>` opens Adjust with AI prefilled, runs it once and drops the parameter.
- **Mobile**: web-only (§ 24). A Coach plan-edit link tapped on the phone opens the web plan page in the browser (`coachPlanAdjustWebUri` in `coach_screen.dart`).

## Engine: `apps/web/src/lib/training/training.ts`

Pure TypeScript, no deps, 100% tested under `apps/web/src/lib/training/training.test.ts` (86 tests, run with `npx tsx --test src/lib/training/training.test.ts`).

- **VDOT from race** — Daniels' published formula: `vo2 = -4.6 + 0.182258v + 0.000104v²`, `pct = 0.8 + 0.1894393·e^(-0.012778T) + 0.2989558·e^(-0.1932605T)`, `VDOT = vo2 / pct`.
- **Riegel equivalence** — `t2 = t1 × (d2/d1)^1.06` for projecting a recent 5K to the goal-race distance.
- **Recent-5K recency gate** — both wizards (`PlanEditor.svelte`, `plan_new_screen.dart`) only pass the entered 5K time into `generatePlan` once the runner ticks a "reflects my current fitness" confirmation. An entered-but-unconfirmed time is treated as absent so paces come from the goal time, or the cautious default without one, and the warning shows only once the time is complete — a returning runner typing an old PR otherwise gets paces that are too fast (comeback persona #24, fail-closed default).
- **Training paces** — 5 intensity zones (easy / marathon / tempo / interval / repetition) computed as multipliers of goal pace. See `pacesFromGoalPace` in the source.
- **Pace fallback disclosure** — when neither a recent 5K nor a goal time is given, `resolveTrainingPacesWithMeta` falls back to a conservative ~10:00/km goal pace **and** returns `isFallback: true`, surfaced on the plan as `pacesAreFallback`. Both wizards render "Estimated paces — add a recent run or a goal time for personalised targets." so the placeholder isn't presented as a real prescription (persona round-5 runner-comeback). The numbers stay usable — the plan generates either way.
- **Plan generator** — `generatePlan({ goalEvent, goalTimeSec?, recent5kSec?, startDate, daysPerWeek, weeks? })` → `{ weeks, paces, vdot, endDate, goalDistanceM, pacesAreFallback }`. Phase breakdown 30/40/20/10 base/build/peak/taper with the final week always 'race'. The shares are allocated by largest remainder over the non-race weeks — with the taper's first week reserved before the split — so the phase weeks always sum exactly to the total and no total starves the taper (flooring each share independently left 10- and 5-week plans with no taper at all). Step-back every 4th week (every 3rd for masters 50+ — see below). Long run grows with volume, capped at ~35% of the week. With **no fitness anchor** (no goal time, no recent 5k) the peak volume is scaled to 0.6× so a no-info plan doesn't open with a punishing week 1 (#23); `limitToDays` trims auto-generated filler days (easy **and** recovery) so the active-day count actually honours `daysPerWeek`. Per-week volume budget: a phase's `weeklyKm` = `round(peakVolumeKm × mileageFraction)` (fractions 0.35 race / 0.55 taper / linear-ramp base+build+peak). The week reserves a quality slot only for a phase that actually fills it (`allocateQualityKm` yields none in the race phase and no second quality session in base/taper), so empty slots don't inflate the easy-run count. In the **race week** the Sunday slot is the race itself (`goalDistanceM`), which stands in for the long run and is charged against that week's budget — so shakeout easy days are only added while the light race-week budget supports another 3 km run (a half/marathon race week is the race plus at most a token shakeout, not a second peak, #326). Every other phase still emits the full `daysPerWeek` (persona #23 promise).

### Ultra distances (issue #1181)

Any goal distance **longer than the marathon** (`isUltraDistance`, strictly > 42 195 m) takes its own branch of `generatePlan` (web `training.ts` ↔ Dart `training.dart`, output-identical). Both wizards offer 50 km, 56 km (Two Oceans), 90 km (Comrades) and 100 mi (`ULTRA_PRESETS`) plus "Other ultra distance", each stored as `goal_event = 'custom'` with the distance in `goal_distance_m`, and an editable distance field so a Comrades runner can enter the year's 86-90 km. There is no new `goal_event` value: the generator keys off the distance, and the season planner calls it with nothing but a distance (decisions entry pending). The road plan is untouched — a custom goal at or under the marathon still builds the road shape, pinned by captured volumes in both suites. The method follows Koop, *Training Essentials for Ultrarunning*:

- **Plan length** — `ultraDefaultWeeks`: 16 weeks below 60 km, 18 below 80 km, 20 below 120 km, 24 above. `racePlanPreset` sizes a race off every rung to it (`defaultPlanWeeks('custom', distanceM)`). A requested length is always honoured, so a race date the season planner fixes stays in the race week.
- **Phases** — the last week is the race, the `ultraTaperWeeks` before it taper (3 from 80 km, 2 below, never more than a quarter of the training weeks), and the rest split base / build / peak 35 / 45 / 20 by largest remainder (`ultraPhaseFor`).
- **Volume** — the peak continues from the marathon's 1.8× at 0.4 km per extra race km, capped at 120 km before the training-day and anchor factors (`peakVolumeKm`). Build weeks ramp 0.6 → 1.0 of peak with the road step-back cycle (`ultraMileageFractions`), and the ramp limit `ULTRA_MAX_WEEKLY_RAMP` = 1.10 is held on what the weeks actually **emit**: each build week's budget is capped at 110 % of the previous build week's emitted volume, long runs round down to the quarter hour, easy days are floored on the week's total, and a week only fills the easy days its budget holds at the 3 km floor. So no build week ever prescribes more than 10 % over the one before it (step-back weeks excluded) — a few low-volume ultra weeks therefore run one easy day short of `daysPerWeek`, the opposite trade from the road plan's persona #23 promise. An easy day is capped at 2 h.
- **Long runs by time on feet** — every ultra long run carries `target_duration_seconds` and **no pace target**; its `target_distance_m` is the duration at easy pace (to 100 m), so week volumes and the opening-week ramp check stay honest. Sunday takes 35 % of the week (32 % on a back-to-back weekend), capped by `ultraLongRunCapSec`: 3.5 h below 60 km, 4 h below 80 km, 5 h below 120 km, 6 h above.
- **Back-to-backs** — from 80 km (`ULTRA_BACK_TO_BACK_MIN_M`), build and peak weeks that are not step-backs put a second long run on Saturday (24 % of the week, capped at 60 % of the Sunday cap) ahead of the next week's Sunday long run. That weekend replaces the week's second quality session rather than stacking three hard days.
- **Quality** — base tempo, build/peak intervals plus a tempo (8 km at peak, where the road plan rehearses marathon pace — an ultra has no goal pace to rehearse), and a short tempo in every taper week, so intensity stays while volume falls to ~45 % of peak the week before the race.
- **Training zones** — anchored at the goal's **marathon equivalent**, `ultraMarathonEquivalentSec` = goal × (42 195 / distance)^1.15 (`ULTRA_RIEGEL_EXPONENT`): zone multipliers of a 100-mile goal pace would put tempo slower than a marathon jog. A recent 5K anchors through the marathon the same way, and the VDOT shown is the marathon equivalent's.
- **Pasted plans** — a Markdown import recomputes each week's phase through `planPhaseFor(week, total, goalDistanceM)`, the same rule, so a pasted ultra plan tapers as the generator's would (JSON imports keep the phases they carry).
- **Race day** — the `race` workout carries the goal time as `target_duration_seconds` and no pace; `planRaces` already reads a race's goal from that column, and the race goal cap is `RACE_GOAL_MAX_HOURS` (999 h), which both wizards' goal-hours fields now take.

## Own training-load ramp (`self_load.ts` ↔ `self_load.dart`)

ACWR and its injury-risk bands arrived with the coach roster and, until 2026-08-14, only a *coach* ever saw one: `/coaching` classifies other people's athletes through `coach_load.ts`, and `plan_ramp.ts` grades a hypothetical plan with the same edges. The runner opening their own `/dashboard` — who in most cases has no coach at all — was never told their last seven days run well above their own month's average.

`selfLoad(runs, nowMs)` closes that. It **composes** `acwr` / `injuryRiskBand` / `loadTrend` rather than re-deriving any of them, so the band edges cannot drift from the ones a coach sees, and it reuses `recentRunVolume` from `plan_ramp` (which grew `acuteM` in the same traversal, so the two halves of the ratio can never be reduced from different run sets). Surfaced as `LoadRampCard.svelte` beside the other dashboard analytics cards, scoped to the same `filteredRuns`, and as `widgets/load_ramp_card.dart` on the mobile dashboard.

Four things about it are deliberate:

- **It is not the readiness ring.** `readiness.ts` scores *today* (form + sleep + resting HR) — "should I run hard this morning". ACWR scores the last month's ramp — "have I built too fast to keep getting away with it". A runner can be fully recovered today and still in the spike zone that surfaces as an injury weeks later.
- **It grades distance, not the roster's `km × 10` stress proxy.** That proxy is linear in distance, so the quotient is identical and duplicating the constant would only add a place for it to drift. A unit test pins the equality, so making the roster's stress non-linear fails there rather than quietly splitting the runner's band from their coach's.
- **It counts DNF distance, where the roster excludes it.** Per [decisions § 592](../architecture/decisions.md), nothing rewrites `distance_m` when the flag is set, so the load was absorbed; dropping a 100 km DNF from the acute window would *under-report* a spike, and under-reporting is the failure that hurts for a safety signal.
- **It refuses a thin history.** Below `MIN_ACTIVE_WEEKS` of the chronic window the ratio is arithmetic on noise, so the card self-hides rather than showing a zero that would read as "safe". `shouldSurfaceSelfLoad` is a type predicate on web, which narrows the band to the four the card has copy for — an unlabelled band is a compile error, not a missing-key render. Dart cannot narrow a field's enum through a bool, so the Dart twin returns a plain bool and the card's exhaustive `switch` carries the same guarantee.

15 mirror tests each in `self_load.test.ts` / `test/self_load_test.dart`; the web surface is pinned by `tests-e2e/dashboard/load-ramp.spec.ts` (spike → high, steady → optimal, thin history → no card) and the mobile one by `test/load_ramp_card_test.dart`. **Mirrored onto the phone 2026-08-18** together with `comeback`, since the two share the reduction and the gate — see [decisions § 609](../architecture/decisions.md) + § 670.

## Comeback load (`comeback.ts` ↔ `comeback.dart`)

That last refusal is right, and it is also silent in the case that most warrants a signal. A runner back from three months off, logging a 30 km first week, has `activeWeeks = 1` → `insufficient` → no card at all. The threshold is not wrong; **ACWR is the wrong instrument** for that runner. It asks "how does this week compare with the month you just trained", and a comeback runner has no such month.

`comebackLoad(runs, nowMs)` asks the question their history *can* answer: how does this week compare with the weeks they were running **before the break**. Their own pre-break average is real data; the near-empty month is not. Surfaced as `ComebackCard.svelte` directly beside `LoadRampCard` on `/dashboard`, on the same `filteredRuns`, and as `widgets/comeback_card.dart` beside the load-ramp card on the mobile dashboard — where one conversion of the runner's runs feeds both, so the two windows can never come from different run sets.

- **It fires only where `selfLoad` is silent.** The same `activeWeeks < MIN_ACTIVE_WEEKS` gate, read the other way round, so the two cards are mutually exclusive **by construction** rather than by the dashboard remembering to choose. A unit test sweeps a set of histories and asserts the two predicates are never both true; a Playwright case asserts `load-ramp` has count 0 on a comeback dashboard.
- **A break is `kLayoffResetDays` (28), reused not redeclared.** That is already the point at which `training_load.ts` writes the runner's fitness EWMAs down to zero — a break big enough to erase their modelled fitness is the same break this card is about, and two numbers for one idea would drift.
- **A base older than `LAYOFF_MAX_DAYS` (365) grades nothing.** A year-plus-stale average describes a body that no longer exists, and grading a return against it would produce a *reassuring* number for a runner effectively starting over. Over-reporting safety is the failure that hurts, so the card goes quiet rather than encouraging.
- **`RETURN_WEEK_SHARE` is 0.5, one flat line rather than a curve.** The widely-taught return-to-running shape is to resume at around half of what you were doing and rebuild. It is deliberately not decayed by layoff length: a decay function would invent precision the evidence does not carry, and a runner can reason about "half".
- **A week with no running is not graded.** An "easing in" verdict off zero kilometres would read as praise for not running, so `acuteM <= 0` returns `insufficient` — which also means the card never nags someone still on their break.
- **The pre-break base clears the same evidence bar.** `MIN_ACTIVE_WEEKS` of the four windows before the break must carry a run, so a single session before a layoff is not a base to come back to. Both sides of the comparison are reduced through `plan_ramp`'s `volumeSample`, so the current week and the pre-break base can never come from different run sets.

21 unit tests in `comeback.test.ts` — including two that pin a clock-skewed stamp grading identically to an honest one, since an unclamped future timestamp opens a phantom gap that reads as a break the runner never took; the web surface is pinned by `tests-e2e/dashboard/comeback.spec.ts` (steep → called out + no ratio card, gentle → easing in, no base → no card) and the mobile one by `test/load_ramp_card_test.dart`, which pins the mutual exclusion at the render layer too. 21 mirror tests each since the 2026-08-18 Dart port (§ 670).

## Opening-week ramp check (`plan_ramp.ts` ↔ `plan_ramp.dart`)

`generatePlan` sizes every week from the goal race, the training days and the fitness anchor — it never reads the runner's history. So a runner averaging 20 km a week could generate a marathon plan (4 days/week, goal time entered) whose **week 1 asks for 38.0 km**, and nothing in the wizard said a word. The opening step is the one a plan is most likely to injure someone on.

`planRampCheck(openingWeekM, peakWeekM, recentVolume)` grades the plan against the runner's chronic base, and **reuses the coach roster's ACWR policy rather than inventing thresholds**: a plan week *is* an acute (7-day) load, the trailing-28-day average *is* the chronic base, so the band edges come from `injuryRiskBand` in `coach_load.ts` and cannot drift from the coach roster's. **The thresholds are shared; the inputs deliberately are not** — this check counts running only (cycling excluded), counts a DNF'd run (the flag is post-hoc; `distance_m` is still what the legs covered), and stays silent below three active weeks, where the roster RPC applies no `activity_type` filter, excludes `is_dnf` runs, and needs no minimum history. So the two surfaces can reach different verdicts over the same 28 days. Why these thresholds, why the two directions grade different weeks, why the check stays silent without ~28 days of consistent history, and why this is *not* the [§ 144](../architecture/decisions.md#144-plan-generator-v2-adaptive-rescheduling-ships-as-a-trend-gated-suggestion-only-layer-over-the-shipped-re-plan-engine-the-fitness-signal-phase-is-ciso-gated) CISO-gated fitness-signal phase: [decisions.md § 592](../architecture/decisions.md#592-a-plan-wizard-that-never-looks-at-what-the-runner-already-runs-and-the-two-directions-of-wrong-volume-are-not-one-question).

**The two directions are graded off different weeks, deliberately.** *Too much* is a question about the first step, so `elevated` / `high` come from the **opening** week. *Too little* is a question about the whole plan, so `under` comes from the **peak** week: every well-formed plan opens far below its own peak (the generator's week 0 is 0.6×), so grading "under" off the opening week would tell a runner already training at the plan's peak volume that the plan is too light for them — exactly backwards. A 55 km/week runner building the marathon plan above has an opening ratio of 0.69 and a peak ratio of 1.07, and correctly hears nothing. Safety wins the tie if a hand-edited plan ever inverts the two.

- `recentRunVolume(runs, nowMs)` buckets runs into four **rolling** 7-day windows counted back from now (not calendar weeks — a partly-elapsed calendar week under-reports and would drag the average down for no reason). Cycling is excluded, matching `goals.ts` / `fitness.ts`; treadmill runs count, because they are real load even though they are barred from anchoring fitness.
- **The check stays silent below `MIN_ACTIVE_WEEKS` (3 of the 4 windows carrying a run).** ACWR needs ~28 days of *consistent* history to mean anything, and without the gate a runner with one 3 km jog in a month divides a C25K opening week by a 0.75 km/week base and is told their beginner plan is a high injury risk.
- `shouldSurfaceRampNote` decides visibility. `matched` renders nothing — a note that fires on every plan is one a runner learns to skip. `under` is an optimisation nudge rather than a safety one, so it is withheld from a beginner walk-run plan (that runner deliberately asked for the gentlest on-ramp); the `elevated` / `high` warnings still show there.

Surfaced in `PlanEditor.svelte`'s preview pane, above the week outline, each verdict quoting the week it was graded on beside the runner's average (`planEditor.rampUnder` / `rampElevated` / `rampHigh`). It recomputes as the wizard's inputs change, so dropping a training day or shortening the goal race shows the ramp easing live. The 28-day volume read is its own guarded mount effect — a failure leaves the wizard and its preview untouched and the note simply doesn't appear (fail-closed: no base, no claim).

**Mirrored on mobile** (`plan_ramp.dart`, a registered parity pair): `plan_new_screen.dart` renders the same note in the same place — inside the preview card, above the week outline — off `TrainingService.fetchPlanRunHistory` (one read of the runs since `kLayoffMaxDays` plus the four-week base, which also feeds the break detection and the goal check), an L4 best-effort read that returns null on any failure so the note self-hides rather than grading against a base it doesn't have. Keys are `planNewRampLabel` / `planNewRampUnder` / `planNewRampElevated` / `planNewRampHigh`, translated from the matching web locale so the two surfaces cannot drift.

34 unit tests in `plan_ramp.test.ts` and 34 in `plan_ramp_test.dart`; the web wiring is pinned by `tests-e2e/plans/ramp-vs-recent-volume.spec.ts`, the mobile wiring by the `opening-week ramp note` group in `test/plan_new_screen_test.dart`.

`recentRunVolume` / `volumeSample` and the two constants live in this module on both platforms, not in a private copy: `self_load` and `comeback` import them from here on BOTH platforms — the 2026-08-18 Dart port landed at the identical module boundary rather than copying the reduction (§ 670) — so there is one definition of "this row is running volume" per platform and the three helpers cannot reduce different run sets.

## Multi-distance race-time predictor (`race_predictor.ts` ↔ `race_predictor.dart`)

A richer surface over the Riegel + VDOT engine, distinct from the single-distance plan-detail `RaceDayPanel`. `predictRaceLadder(efforts)` projects the **whole standard ladder** (5K / 10K / Half / Marathon) in one pass and grades each rung's confidence independently, so a runner sees a high-confidence 10K and a clearly-flagged low-confidence marathon side by side.

Two improvements over "best single run, one distance":

1. **Recency-weighted anchor.** Each qualifying effort is Riegel-equivalenced to a common reference (10K), then the anchor is the **recency-weighted** best — the equivalent time is divided by an exponential half-life decay (`ANCHOR_RECENCY_HALFLIFE_DAYS = 30`) so a recent strong effort outranks a stale PR (a fitness that has moved on isn't anchored to last spring's parkrun). The ladder then projects from the chosen anchor's **actual** distance + time, so every rung is an honest Riegel equivalence, not a weighted fabrication.
2. **Per-distance confidence.** Each rung reuses `predictionConfidence` from `training.ts` with the SAME thresholds the single-distance panel uses, so the grade a runner sees here matches the plan panel for the same distance.

Pure — reuses `riegelPredict` + `predictionConfidence` so the numbers can't drift from the engine. Returns `null` on an empty pool (the caller hides the surface — fail-closed, same as the Fitness card). **Surfaced on web** via `RacePredictorCard.svelte` on `/dashboard` (below the training-load chart), gated by the same `qualifyingRuns` filter the Fitness card uses (recording / reliable import, ≥ 1.5 km, sane duration, not treadmill — so it never anchors to a belt estimate). TS↔Dart parity pair, 11 mirror tests each; the Dart twin is ported for a future mobile surface (no mobile card today — see followups.md #11). Backlog #11.

## Train for a race on the calendar (`race_plan_preset.ts` ↔ `race_plan_preset.dart`)

The race calendar (`/races`) and this generator were two shipped features that never spoke: a runner could find their goal race and, months later, import the result, but nothing carried them from a race date to a plan built around it. `racePlanPreset({ raceDateIso, distanceM, todayIso })` closes that, and the whole job is the three pieces of arithmetic in between:

- **A Sunday start.** `generatePlan` hard-anchors day 0 of the start week to the Sunday long run (see `plan_start.ts`), so any derived start date must be a Sunday or every day-role shifts.
- **Race day inside the final `race` week.** The generated plan's last week spans `[start + (weeks-1)*7, start + weeks*7 - 1]`. Anchoring that week to the Sunday **on or before** race day puts race day inside it whatever weekday the race falls on — a Saturday race and the Sunday before it produce the same plan.
- **Weeks capped at the goal's default.** `min(weeks available, defaultPlanWeeks(goal, distanceM))` — a distance off every rung sizes as a custom goal, so an ultra takes its ultra default — so a marathon eight months out gets the standard 16-week build starting in four months, not a 32-week grind. This is why the start date is derived backwards from race week rather than forwards from today.

Spans are counted in whole UTC epoch-days, not by millisecond difference — a window crossing a DST transition is 167 or 169 hours and would shift the anchor by a week (the same trap `plan_week.ts` documents).

It **refuses** rather than proposing when it can't do the job: `past` (race day has been and gone, or is today), `too_soon` (fewer than `RACE_PLAN_MIN_WEEKS` = 4 whole weeks remain — the wizard's own `min` on the week field), or `invalid` (unusable date). `RaceCalendarCard` hides the CTA on a refusal; `/plans/new` honours it a second time — a link can go stale in an open tab or arrive hand-edited — and renders a note saying why the dates are the usual defaults rather than ignoring the link in silence.

`goalEventForDistance` matches the four standard rungs within 2 % (listings round — "21.1 km"). Anything else, a 50k or a 10-miler, returns `null` and claims no goal event: snapping a 50k to the nearest rung wouldn't be an imprecise label, it would be a plan for a different race. The dates are still preset, and a distance past the marathon preselects the wizards' matching ultra entry (or "Other ultra distance" with the race's distance) — web via `PlanEditor`'s `initialGoalDistanceM`, mobile in `_applyRacePreset`.

The link carries the **race's facts** (`/plans/new?raceDate=&raceDistance=&raceName=`), not the derived dates, so the wizard re-derives against today and a bookmarked link can't resurrect a start date that is now in the past. `PlanEditor` receives them as `initialName` / `initialStartDate` / `initialWeeks` beside the existing `initialGoalEvent`. Mobile has no URL — the races screen pushes the wizard directly — so it passes the same facts as `raceDateIso` / `raceName` / `raceDistanceM` props and `PlanNewScreen` re-derives them, keeping one home for the arithmetic and the refusal note reachable rather than theoretical (§ 671).

**Mirrored onto the phone 2026-08-18** (§ 671): `RacesScreen`'s card runs the same helper and shows a "Train for this race" action only when a plan can be built, exactly as `RaceCalendarCard` gates its CTA. 18 mirror tests each in `race_plan_preset.test.ts` / `test/race_plan_preset_test.dart`; web wiring pinned by `tests-e2e/races/train-for-this-race.spec.ts`, mobile wiring by `test/races_screen_test.dart` + `test/plan_new_screen_test.dart`. See `decisions.md § 606`.

## Race-day goal feasibility (`race_day.ts` #goalFeasibility)

The plan-detail `RaceDayPanel` (shown within 21 days of the goal race) used to short-circuit to the runner's goal time whenever one was set — recent fitness was ignored, so a runner never learned whether the goal they typed months ago is still in reach. It now **always** computes the fitness-derived Riegel projection off the best qualifying recent effort (≥ 1 km, last 90 days) and, when a goal time is set, grades the goal against it via `goalFeasibility(goalSec, predictedSec)`:

- `ahead` — projection faster than goal by more than `GOAL_ONTRACK_BAND` (2 %)
- `on_track` — projection within ±2 % of goal (inside the day-to-day noise of a single-effort Riegel projection, so a rounding-scale gap doesn't cry off-pace)
- `behind` — projection slower, but within `GOAL_FARBEHIND_BAND` (8 %)
- `far_behind` — projection slower by more than 8 % (a materially out-of-reach goal, ~+17 min on a 3:30)

The panel renders the verdict + the signed delta (`X faster` / `X slower`) as a coloured pill under the predicted-finish line, hidden entirely when there's no goal or no qualifying effort to check against. Pure — reuses `riegelPredict` from `training.ts`, no new numbers. **Web-only** (the panel + `race_day.ts` are web-only — no mobile race-day surface); 9 unit tests in `race_day.test.ts`, wiring pinned by `tests-e2e/plans/race-day-feasibility.spec.ts`.

## Several races per plan (`plan_races.ts` ↔ `plan_races.dart`)

A plan used to know one race: its `end_date`, with `goal_distance_m` / `goal_time_seconds`. A Comrades block that runs through Two Oceans had no way to say so, and the countdown, race-week panel and goal all keyed on the end date. Migration `20270830000002` gives a `race` workout its own `race_name` and `race_priority` (A / B / C; both only legal on `kind = 'race'`), with the race distance in `target_distance_m` and its goal time in `target_duration_seconds` (decisions § 2009).

`planRaces(plan, workouts)` lists every race, sorted by date (ties by workout id). An unset priority is **A** on the plan's end date and **C** anywhere else; the end-date race takes the plan goal for a missing distance or goal time, and a plan with no race workout on its end date gets a synthetic A race there from the plan goal, so every existing plan still has its race — unless the plan was ended early (`trimmed_at`, set by `trim_training_plan`), whose end date is the day it was cut short and whose goal race no longer happens inside it. `nextRace(races, today)` is the first race on or after today (race day counts).

- **`/plans/[id]`** — the hero relation pill, the race-week `RaceDayPanel` (within 21 days) and its distance / goal follow `nextRace`, so a B race mid-block gets its own run-in; a named race before the end date reads *Two Oceans in 12 days*. When a plan holds more than one race, a **Races in this plan** list shows each one's priority chip, name (the plan name for the synthetic race), date, distance and goal time, marking the next. Once the next race is not the A race on the end date, the hero leads with *Next race: Two Oceans* and its distance, goal time and date follow that race; the plan's A goal stays in the races list. Mobile's plan detail does the same (`_heroRace`).
- **`/dashboard`** — the plan hero's countdown, goal time and date follow the current plan's next race.
- **Workout editor** — a `race` workout gains Race name, Priority (A / B / C, or *Auto*) and Goal time inputs. Changing a workout to any other kind clears `race_name` / `race_priority` in the same write (`updatePlanWorkout` does it for every caller, since the database rejects them), and clears the goal time when the workout was a race. Mobile matches both halves: `planWorkoutPatch` clears the race name and priority on any kind change and `target_duration_seconds` when the sheet passes `fromKind: 'race'`. **A race goal time is always hours on mobile** (decisions § 2053, § 2061): `formatRaceGoalTimeS` writes `h:mm:ss` even under an hour (`0:45:00`) for the field and the race goal displays (races list, hero), and the field reads back through `parseRaceGoalTimeS`, which accepts exactly `h:mm:ss` (hours 0–999 — `RACE_GOAL_MAX_HOURS` ↔ `raceGoalMaxHours` in the `plan_races` pair, so a 240-mile race's 100-plus-hour goal fits; the web editor's hours field and the import table's `Goal` cell take the same ceiling, the import cell also refusing minutes or seconds above 59) and rejects a two-part `45:00` or `6:30` rather than guessing its unit. The shared `formatGoalTimeS` that the run screen's strategy prefill and the run-detail strategy label use still writes a sub-hour goal as `mm:ss`, so a 25-minute 5K reads `25:00` there. Before this, a 45-minute goal was prefilled as `45:00`, re-read as 45 hours by the pace-guessing parser whenever the race had no distance, and corrupted by an untouched save.
- **Import / export** — see *Paste-a-template import* below: optional `Race | Priority | Goal` columns.

### Taper and recovery around B / C races (`race_taper.ts` ↔ `race_taper.dart`)

Week phases come from position toward the end date, so they only taper for the A race. **Adjust plan → Taper around B/C races** (web + mobile; offered only while a B or C race is still ahead) runs `raceTaperProposals(workouts, races, today)` and previews the result like a re-plan; Apply writes every `raceTaperPatch` and restates each touched week's `target_volume_m` in one `apply_workout_adjustments` call, so a failure changes nothing and the page reloads (decisions § 2051, § 2062; the cycle-plan adjustment and re-plan apply go through the same RPC):

| Window | B race | C race |
| --- | --- | --- |
| Before | days −6…−3 at 65% volume (−8…−3 for a race past the marathon, so the whole weekend before it — a back-to-back long run included — eases), quality (tempo / interval / marathon pace) and the long run run easy | days −3…−1 at 80%, quality and the long run easy |
| Last 2 days | shakeout: half distance, at most 5 km, quality and long run easy | — |
| After | one easy day per 3 km raced, 4–7 days (5 with no distance); past the marathon 7 days plus one per 2 km beyond it, at most 21 — 14 for a 56 km Two Oceans inside a Comrades block, 21 for 90 km and up: quality run easy at its distance, the long run at 75% | 2 days, same rule |

Never touched: workouts before today, done (linked or ticked) or skipped, rest days, any `race` workout, workouts in `taper` / `race` weeks (the A race's own taper), and workouts an applied taper already eased. Apply stamps `plan_workouts.race_taper_applied_at` on every workout it changes (web `raceTaperAdjustments`, mobile `TrainingService.applyRaceTaper`), and the proposal skips a stamped workout, so running the taper again does not cut 65% of an already-cut 65%; clones, assignments and a duplicated week carry the stamp with the eased distance (migration `20270830000007`). A race on or before today gets no window. A workout inside two windows takes shakeout over taper over recovery, then the B race, then the earlier race. Easy, recovery and walk/run days keep their kind and only shorten.

**The whole prescription eases together** (issue #1183). `target_duration_seconds` scales by the factor the distance actually moved — the shakeout's 5 km cap included, so a 12 km / 60 min tempo becomes 5 km / 25 min — or by the rule's own factor when the workout has no distance. A walk/run day keeps its run and walk lengths (the runner's stage of the progression) and loses repeats instead: the count scales by the same factor, rounded, at least one (a single continuous run scales its run length), and its duration is restated as the rebuilt structure's total. When the kind changes (quality or long → easy) any structure goes, and its notes are cleared, as are a rebuilt walk/run's — notes that described the old session would contradict the new one, and a marker line would be stored text in a field that belongs to the runner. A note on a session that only shortens is kept. The preview shows the duration on each side of the change and a "Notes cleared" line under any row that clears them. Pinned by 15 mirror tests per twin (plus web's `raceTaperAdjustments` case), `race_taper_applied_test.sql`, `test/training_service_plan_create_rpc_test.dart`, `tests-e2e/plans/plan-races.spec.ts` and `test/plan_detail_adjust_test.dart`.

**Ending a plan early** (`trim_training_plan`) refuses with SQLSTATE `TR001` when a completed workout falls after the cut; every create and clone path shows "<plan> has completed workouts after <date>. Replace it instead, or start the new plan later." (`planEditor.overlapTrimBlocked`), and the dialog keeps offering End early because the check is server-side. A trimmed plan made longer again (a meta edit of its end date, Duplicate week) loses `trimmed_at`, so its end date reads as a race again; a shift keeps it. `create_training_plan` refuses a workout dated outside the plan's own window (decisions § 2062).

`clone_plan_template`, `clone_public_plan` and `assign_plan_to_athlete` copy the two columns; `duplicate_plan_week` copies no `race` workout at all (migration `20270830000009`): a duplicated week is training, so its race day stays free and the copy's `target_volume_m` drops the race distance. Copying the race without its name and priority, as it did before, still invented a race, because `planRaces` reads every `race` workout as one — a nameless C race seven days on, with its own countdown and taper window.

## Season planning (`season_plan.ts` ↔ `season_plan.dart`)

A season is several races: "Richmond Marathon on 14 Nov, Two Oceans on 3 Apr as a tune-up, Comrades on 13 Jun" (issue #1181). **`/plans/season`** (web, linked from `/plans/new`) and **Plan a season** on the mobile new-plan screen take the race list, let the runner confirm it, and create one plan per A race, chained back to back. The AI only reads the description into a race list (`requestSeasonRaces`, `season_request_client.ts` ↔ `.dart`); the runner edits and confirms the list (name, date, distance, A/B/C, optional goal time), and nothing is generated until they do. Every extraction failure (consent, daily limit, not understood, invalid, signed out, unavailable) leaves the list for entry by hand, with a blank A race added when it was empty. Editing any race after the preview hides the preview.

`buildSeason({ races, todayIso, daysPerWeek, recent5kSec?, gender?, age? })` is pure and returns either the plan drafts or a refusal:

- **One plan per A race**, ending on it: the generator's race workout moves from the race week's Sunday to race day (that Sunday becomes rest) and the days after race day are dropped, so `end_date` is the A race and `planRaces` reads it as the A race on the end date. The goal is the standard event when the distance is within 2 % of one (`goalEventForDistance`), else `custom` at the race's own distance.
- **Windows.** Every plan starts on a Sunday (the generator's day 0 is the long run). The first starts no earlier than the Sunday on or after today and takes the goal's default length (an ultra its own longer default, `ultraDefaultWeeks`: 16 weeks for a 56 km race, 20 for 90 km), starting later rather than earlier, exactly as `racePlanPreset` does. A later plan starts on the Sunday after the previous A race's recovery and fills the gap up to the wizard's 24-week maximum, so a season has no unplanned weeks between blocks; a gap longer than that leaves the extra weeks before the plan. Plans never overlap (`training_plans_active_no_overlap`).
- **Recovery after an A race**: one day per 3 km raced, held to 3–28 days (a week after a half, two after a marathon, two to four after an ultra). That is half the density of "a day per mile raced", because the next plan opens with its easy base phase and carries the back half of the recovery itself. The preview shows each gap with its actual length, which the Sunday snap can make up to six days longer.
- **B / C races** become `race` workouts (`race_name`, `race_priority`, distance, goal time, goal pace when there is a goal) on their own date inside the plan whose window holds them, replacing whatever the generator put there; week volumes are restated. A B / C race before the first plan, in a recovery gap, after the last A race, or on a day that already holds a race in its plan is listed as **not in any plan** and is not written — attaching it would mean moving a plan, and the runner can change its date or priority instead. The B/C mini-taper is not applied at create time; **Adjust plan → Taper around B/C races** proposes it afterwards like any plan.
- **Refusals**, each naming the races involved: an empty list; an invalid race (no name, a name over 80 characters — it becomes the plan name — an unusable date, a distance or goal time that is not positive); a race today or past; **no A race** (the builder never promotes one, because which race the season peaks for is the runner's call and the list is right there to set it); the first A race fewer than 4 weeks away; **two A races too close** for the recovery and a 4-week plan between them (never silently downgraded to B, for the same reason).

**Creating.** The drafts are written in order through the normal create path (web `createTrainingPlan` → `create_training_plan`, mobile `TrainingService.createPlan`), one transaction each. Only the first plan may overlap a plan the runner already has, so only it goes through the overlap dialog; the later windows are checked against the runner's active plans before anything is written, and one that would land on an existing plan blocks the season with that plan named. A failure part-way says which plans were created and which were not, and the button becomes **Create the remaining plans**, which resumes from the failed one (web `createSeasonPlans` in `season_create.ts`; mobile keeps the same loop in `SeasonPlanScreen`).

Pinned by 21 mirror tests per twin (`season_plan.test.ts` ↔ `test/season_plan_test.dart`), `season_create.test.ts` (4), `tests-e2e/plans/season-planner.spec.ts` (manual entry → two chained active plans with the B race in the second; the extraction-unavailable fallback) and `test/season_plan_screen_test.dart` (10).

## Loading a plan, and reading it offline (decisions § 2114)

`fetchPlan` (web `data.ts` ↔ mobile `training_service.dart`) reads a plan, its weeks and its workouts as one `training_plans` select with a `plan_weeks(*, plan_workouts(*))` embed, and orders weeks by `week_index` and workouts by `scheduled_date` on the client, because an embed is ordered per parent. Mobile's split is the pure `planDetailFromRow`.

On mobile a refresh never takes a plan or workout off the screen. Plan detail and workout detail show the full-body loader and the "Couldn't load" page only on a first load; a refresh that fails over data already showing leaves it in place under a top banner (`commonStaleOffline` when the device is offline, `commonStaleRefreshFailed` otherwise), and a first load that fails offline says offline (`authErrorOffline`). Workout detail takes the row its caller holds (`initial:`), so it draws at once and **Start** works without signal; plan detail, the Run tab and Home pass it. The active-plan overview behind Home, the Run tab and the dashboard is saved per account by `fetchActiveOverview` (`active_plan_cache.dart`) and answered from that copy when a read fails, with today's workout, the completion figure and the current week derived at read time (`activeOverviewFrom`). Sign-out clears it. Web has no offline mode and is unchanged.

## Pausing and resuming a plan

Pausing sets `status = 'paused'`; a trigger stamps `training_plans.paused_at`. Resuming goes through `resume_training_plan`, and when the pause spanned whole plan weeks the clients offer to move every week after the one the runner paused in back by those weeks (`resumeShift`, the `plan_resume` pair), so they come back as upcoming rather than missed. Whole weeks from the week after the pause, because those weeks hold no history and a 7-day step keeps each workout inside its week's window, which both clients derive from `start_date + 7 * week_index`; the pause week and week 0 never move. The confirm names the plan's new end date, and the overlap check covers it.

## Picking a plan back up after a break

Issue #1186, decisions § 2128. A runner who stops for a week or more inside an active plan is offered one calm card — **Coming back after a break** — on Home and on the plan (web `PlanBreakCard.svelte` on `/dashboard` and `/plans/[id]`; mobile `widgets/plan_break_card.dart` on the dashboard and plan detail). Owner only: a coach reading an athlete's plan never sees it, and a paused plan never shows it (resuming already moves its weeks back).

**Detection** is the `plan_break` pair (`training/plan_break.ts` ↔ `plan_break.dart`, `detectPlanBreak`): 7 or more of the runner's local days up to yesterday with no run of any kind and no plan workout done, in an active, untrimmed, non-template plan that has started, has not ended and has a week after the current one, with at least one non-rest workout scheduled in the stretch. A run today does not end the break, so the card is there on the day the runner comes back. Web reads the latest run before local midnight; mobile reads the local run store (unsynced runs included) and falls back to the recent-runs fetch, and keeps the card hidden while either is unknown.

**The options.** Each re-runs the latest N weeks up to the current one from next week and moves every later week back N whole weeks; the missed weeks stay where they were as history.
- **Repeat this week** — N = 1.
- **Push the plan back** (a plan without a race) — N chosen from 1 up to the break's whole weeks; the plan's end moves back N weeks.
- **Shorten the build** (a plan that ends on a race) — the same re-run, but race day never moves: N pre-taper weeks that have not started are dropped, build first, then base, then peak, the latest of each first (`change_plan_race_date`'s order). "Repeat this week" on a race plan drops one such week too.

The taper, anything that has started, anything done and any other race never move; a B/C race in a week that would move removes the option, and N is capped at what works (`maxWeeks`). Copies carry no completion, skip, run link or race row, and heart-rate targets only while the HR prescription gate is open and the runner has consented. Every option opens a preview (weeks run again, weeks taken out, race day kept or the new end date) and applies only on **Change plan**, through `reschedule_plan_after_break` in one transaction; a later end that runs into another active plan is refused with nothing changed.

**Keep the plan as it is** hides the card by writing `user_settings.prefs.plan_break_dismissed` = `{plan_id, from, until}` (`docs/backend/settings.md`); applying a change writes the same key inside the RPC. `isBreakDismissed` hides the card only for that plan and that break, so web and phone agree and a later break is offered again.

**The offer outranks the other plan cards.** While it shows (`breakOfferShowing`, one predicate in the pair that every host calls), Home and the plan show neither the missed-workout prompt nor the plan nudge card, and a make-up deep link (web `?makeup=1`, mobile `openMakeUp`) only opens the plan: those judge the missed weeks one workout or one week at a time, while the offer re-runs them whole. The hosts own the break state for that reason (web `breakState` in `training/plan_break_state.ts` over `loadBreakContext`; mobile `PlanBreakCard.stateFor`), and while the web reads are in flight the other cards wait rather than flash. Answering the offer lets them back: keeping the plan brings the missed prompt back; applying a change answers, in the RPC's transaction, every open non-rest workout the break covered (`missed_ack_at`), so the prompt does not then offer a make-up stretching a long run the re-run weeks restore. The plan nudge never judges a week that overlaps the break (`breakWindow` → `planNudge`'s `breakFromIso` / `breakUntilIso`), so it does not read the break as an under-run trend. Detection is auxiliary (L4): a malformed row or a failed read hides the offer and lets the other cards show. On mobile, Home knows the runner's runs once the local store holds one or the account has none; a cold store on an account that has run shows no offer.

Pinned by `plan_break.test.ts` ↔ `test/plan_break_test.dart` (17 each), `plan_break_state.test.ts`, `plan_nudges.test.ts` ↔ `plan_nudges_test.dart` (the break window case), `reschedule_plan_after_break_test.sql`, `tests-e2e/plans/break-reschedule.spec.ts` `test/plan_break_card_test.dart` and `test/dashboard_plan_break_test.dart`.

## Restarting a plan (`plan_restart.ts` ↔ `plan_restart.dart`, decisions § 2121)

**Restart plan** (web: the owner's *Adjust plan* dialog on `/plans/[id]`; mobile: *Restart plan…* in the owner-only ⋮ menu on plan detail) makes a fresh active copy of a plan the runner owns, in any status, through one RPC, `restart_training_plan`. The copy keeps every week and workout with its targets, structure, race fields, goal, rules and notes, moved by one day offset; nothing is marked done, skipped or linked to a run. In the same transaction every active plan the new dates overlap, and the source while it is active or paused, is retired as `abandoned`; a completed source stays completed, and the source's weeks, workouts, completions and run links are untouched. The client then opens the copy.

The start date follows the creation wizard (`plan_start`), generalised to the source plan's own start weekday: the default is that weekday at least a week out, and a picked date snaps forward to it. A walk-run plan (`isWalkRunPlan`, the test `create_training_plan` applies) may start any day from today and defaults to tomorrow. The confirm names the new start and end dates, says what is retired, and, for a plan whose races are behind it, where race day moves. A plan with a race on or after today is refused (`upcomingRaceIso` on the client, `RR001` from the RPC): shifting the plan would move race day off the real date, so the dialog points the runner at changing the race date or starting a new plan instead. The server checks the start against the runner's today in their stored time zone, which can run ahead of the device's date; that refusal (`RR002`) gets its own message rather than a generic failure. Templates are not restartable; a coach-assigned plan is, and the copy does not carry `assigned_by_coach_id`. Rate-limited with the other create paths (`restart_training_plan`, 20 an hour).

## First-time plan discovery

The `recent_5k_suggestion` pair (`recent_5k_suggestion.ts` ↔ `recent_5k_suggestion.dart`, decisions § 2131). A runner with no plan always has a way to start one on Home. "No plan" means the plan reads answered: no active plan (a plan that has not started yet counts as one, and keeps its "Starts in N days" card) and no paused plan (which keeps its resume card). A failed plan read offers nothing, so Home never invites someone to start a plan they may already have.

- **Web `/dashboard`:** the plan slot's existing promo ("Pick a goal race and we'll schedule the weeks", `/plans?new=1`) is the plain entry; the first-run state shows it above `DashboardFirstRun`.
- **Mobile Home:** the runless welcome (`_WelcomeEmpty`) carries a **Train for something** button, and an account with history gets a `TrainForSomethingCard` in the plan slot. Both open `PlanNewScreen`.

**The recent-5K suggestion** takes the plain entry's place when the runner has a measured 5K worth offering: "Your 5K of 24:10 on 3 Oct" with **Build a plan from it** and **Not now** (web `Recent5kPlanCard.svelte`, mobile `Recent5kPlanCard`). `pickRecent5k` chooses the fastest `runs.fastest_5k_s` (the fastest 5 km window measured inside a run) that is:

- from a run, not a walk, hike, ride or stroller run (a row with no `activity_type` counts as a run), and not a DNF;
- a time the wizard can take, 12:00 to 59:59 in whole seconds;
- from a run started in the last **56 days** (eight weeks) and not in the future;
- from a run started after the last dismissal.

Ties go to the newer run. Web reads `fastest_5k_s` off the dashboard's own run read (`DASHBOARD_RUN_COLUMNS`); mobile reads the run store's resident runs, because the summaries Home charts from do not carry it, and the newest 200 runs reach back past eight weeks for anyone running fewer than three times a day.

**Building from it** opens the wizard (web `/plans/new?type=training&recent5k=<seconds>`, mobile `PlanNewScreen(initialRecent5kSec:)`) with the recent-5K field filled in and the "this reflects my fitness today" box **unticked**, plus a note saying so. That box is the existing `recent5kConfirmed` gate, and its semantics are unchanged: until the runner ticks it, the time sets no paces, and they come from the goal time or the cautious default. A URL time the wizard cannot take fills nothing.

**Not now** stamps `plan_suggestion_dismissed_at` (UTC) in the universal settings bag ([settings.md](../backend/settings.md)), so web and phone agree. Only a run started after the stamp can bring the suggestion back, so a newer measured 5K re-offers it, even a slower one, and the one waved away does not. A refused write says the suggestion may come back. While the settings bag is unknown (web: no server read and no cached copy; mobile: no settings service yet), no suggestion shows and the plain entry does, because an unknown answer must not re-show a suggestion the runner dismissed. A failed runs read leaves the dashboard on its own load error; the suggestion's own computation failing hides only the suggestion.

## Pace derivation — why multipliers, not Daniels tables

Daniels' official training paces are derived from VDOT via the same implicit equation used for VDOT itself. There's no closed-form inverse; real implementations lookup the paces in a published table. For v1 we anchor training paces on goal pace directly (`easy = 1.22 × goal`, `tempo = 0.97 × goal`, etc.) — these multipliers land within ~5 s/km of the Daniels tables across the 3:00-5:00/km goal band, which is well inside the tolerance band a plan runner expects.

If pace accuracy is ever the user-visible complaint, swap `paceFor` for a Daniels-table lookup — the public surface of `training.ts` stays the same.

## Finishing a plan (`isPlanFinished`, the `plan_current` pair)

**Changing the race date** (issue #1186, decisions § 2120). The plan owner's **Adjust plan → Change race date** on web (a date field beside Shift dates) and **Change race date…** in the plan detail ⋮ menu on mobile (a date picker) move the plan's race to a new day. Offered only for an active or paused plan whose last week is a race week, that was not ended early, and whose race is still ahead (`planRaceDate`), so a walk-run plan never shows it. `raceDateChange` (`training/plan_race_date.ts` ↔ `plan_race_date.dart`) re-anchors in whole weeks so every workout keeps its weekday role: the plan's race week becomes the plan week holding the new date. An earlier race drops pre-taper weeks that have not started, build first, then base, then peak, the latest of each first; a later race repeats the last base or build week before the peak (before the taper once the peak has started), as `build` weeks. The taper and race weeks are never dropped, and no started week, completed workout or other race moves; a B/C race in a week that would move refuses the change (`in_the_way`) rather than moving a real race date. A day too close to keep the taper even with every droppable week cut is refused naming the earliest day the plan can reach; `racePlanPreset` supplies the past / invalid refusals. Inside the race week the race moves to the new day (the run on that day takes the race's old day while that day is ahead, else goes), the days after race day are dropped and the plan's `end_date` becomes race day — the shape the season planner writes. The confirm names the new date and how many build weeks are added or cut, and says the taper stays. A later end is checked against the runner's other active plans before the confirm and refused (web names the plans in the way). A repeated week carries its heart-rate targets only while the HR prescription gate is open and the runner has consented. Applied by `change_plan_race_date` in one transaction. Pinned by `plan_race_date.test.ts` ↔ `test/plan_race_date_test.dart` (11 each), `change_plan_race_date_test.sql`, `tests-e2e/plans/race-date-change.spec.ts` and `test/plan_detail_race_date_test.dart`.

Nothing writes `completed` when a plan's end date passes — there is no cron, trigger or client job, by design: a runner who ran their race and one who stopped in week 3 look the same to a clock. An `active` plan whose `end_date` is before the runner's local today is **finished** (`isPlanFinished` in `training/plan_current.ts` ↔ `plan_current.dart`; the end day itself is still inside the plan), and `pickCurrentPlan` keeps showing it as their plan until the next one starts. Finished plans ask the runner to file them: `FinishPlanPrompt.svelte` on the dashboard plan hero (in place of the today/rest block) and under the `/plans/[id]` hero for the owner, and on mobile `FinishPlanCard` in Home's race-countdown slot (where `NextRaceCard` hides once the race has passed) and under the plan detail header. **Finish plan** runs `finishPlan` / `TrainingService.finishPlan`, an update to `completed` scoped to `status = 'active'` so a plan paused or abandoned elsewhere is never relabelled. While a plan is finished the week lead stops offering its sessions (it is handed no plan, so it says nothing rather than "No more sessions scheduled"), and the Run tab's plan chip reads **Finish plan** and opens the plan. A finished plan never blocks a new one: the overlap check is by date window (§ 2008), and nothing new starts before today. Replacing an overlapped plan writes `abandoned`, never `completed` (decisions § 2075, § 2078).

## Data model

Migration: `apps/backend/supabase/migrations/20260419_001_training_plans.sql`. Three tables:

- `training_plans` — one per user-plan; `vdot`, `goal_distance_m`, `goal_time_seconds`, `status`, `current_5k_seconds`. **Plans chain** (decisions § 2008): a user may hold several `active` plans as long as their inclusive `[start_date, end_date]` windows do not overlap, enforced by the exclusion constraint `training_plans_active_no_overlap` (an overlap raises 23P01, which `dbError` maps to a readable `PlanOverlapError`; on mobile `planWriteError` maps it to `ActivePlanExistsError`, which resume, create and — since a duplicated week pushes the end date back seven days into a possibly queued plan — **Duplicate week** each surface as their own message). So a Two Oceans + Comrades block can be queued to start the day after a marathon block ends without closing it. Every surface that shows "the" plan picks it with `pickCurrentPlan` (`training/plan_current.ts` ↔ `plan_current.dart`, and coach_roster_summary in SQL): the plan covering today, else the latest-ended, else the next to start, with the plan after it surfaced as *Up next* on the dashboard and as *Upcoming* on `/plans`. Every create path writes through one RPC that resolves overlaps in the same transaction as the insert (decisions § 2050): `createTrainingPlan` / mobile `createPlan` call `create_training_plan`, and the clone RPCs take the same `p_overlap`. `'refuse'` (the client default) fails with 23P01 when anything overlaps, `'replace'` retires the overlapped plans as `abandoned` (not `completed`, which is kept for a plan the runner finished; decisions § 2075), `'trim'` ends each the day before the new start through `trim_training_plan` (only when each starts before it — `canTrimOverlap` in the `plan_overlap` pair — and never when the plan has completed workouts after the cut, which refuses with SQLSTATE TR001; both name every plan the trim would end and the date, § 2061; the mobile dialog's *End early* choice names them all too); a failed insert rolls the resolution back. On web the wizard, a starter plan, a club template and a public-library clone all ask the server to refuse first and, on a refusal, show the shared `PlanOverlapDialog` naming the plans in the way as read at that moment (`attemptPlanCreate` in `training/plan_overlap.ts`), so a plan created after the form opened is named rather than replaced. Mobile checks first through `confirmPlanOverlap` and passes `refuse` when nothing overlapped; a failed lookup there shows an error and creates nothing. `resumePlan` refuses only when another active plan overlaps the paused one. **Shift dates** runs `shift_training_plan` (one transaction; decisions § 2052) after `planShiftImpact` (`training/plan_shift.ts`) checks the shifted window against the runner's other active plans: onto a plan queued after it, the confirm becomes *Also move <plans> by N days* and passes `p_shift_following` so every later active plan moves the same number of days; onto the plan before it, the shift is refused with a message naming that plan. A 23P01 that still reaches a shift, a week duplication or a resume is shown as the localized `planDetail.planOverlap` / `planDetail.resumeBlocked` copy. The dashboard and the coach athlete page show a plan load error rather than the no-plan state when the overview read fails, and the AI coach picks the current plan by the runner's local today (sent as `today`, trusted within a day of the server's UTC date, as plan requests do).
- `plan_weeks` — 8–16 rows per plan; `phase`, `target_volume_m`, `notes`, `week_index`.
- `plan_workouts` — one row per day: the generator writes seven per week, rest days included as `rest` rows (`plan_workouts_one_per_day` holds it to at most one per day; an imported or hand-built week may have fewer); `kind`, target distance / duration / pace / tolerance, free-form `structure jsonb` for intervals. `notes` is free text the runner or a coach owns: the generator leaves it null on every road-plan workout and both clients render the structure from localized keys (decisions § 2085; migration `20270908000001` cleared the English sentences older generators wrote). Only the ultra generator still writes advice notes, on time-on-feet long runs and race day. Completion is encoded by **two** fields: `completed_run_id` (set by the auto-matcher when a tracked run lands) and `manually_completed` (boolean, set by the calendar editor's "Mark as done" when the user ran without recording). Read sites should treat the workout as done if either is truthy — the shared helper is `isWorkoutCompleted(wo)` in `apps/web/src/lib/training/training.ts`, and its Dart twin `isWorkoutCompleted(PlanWorkoutRow)` in `apps/mobile_android/lib/training.dart` is the only place mobile decides "done" (workout detail, plan rows, calendar, week strip, Today card, runner menu, coach view). On both workout-detail screens a hand-marked done workout shows "Mark not done" in place of Unlink, behind a confirm whose copy names the mark rather than a run. A third, orthogonal field `skipped_at timestamptz` (migration `20270125_001`, null = not skipped) records a **deliberately skipped** session — distinct from a not-yet-done debt. The helper is `isWorkoutSkipped(wo)` (web) / `isWorkoutSkipped(skippedAt)` (Dart twin). Skip and done are mutually exclusive: `markWorkoutSkipped` / `setSkipped` clears completion, and completing clears the skip. A skipped workout **leaves the progress-ring denominator** (it's neither done nor outstanding) and **does not trigger the missed-long-run make-up callout**.

### `plan_workouts.structure` shape

```ts
{
  warmup?:   { distance_m?: number; duration_s?: number; pace: 'easy' };
  repeats?:  {
    count: number;
    distance_m?: number;          // distance- OR time-based (one of these)
    duration_s?: number;
    pace_sec_per_km: number;
    recovery_distance_m?: number;
    recovery_duration_s?: number;
    recovery_pace: 'easy' | 'jog' | 'walk';
  };
  steady?:   { distance_m?: number; duration_s?: number; pace_sec_per_km: number };
  cooldown?: { distance_m?: number; duration_s?: number; pace: 'easy' };
}
```

Kept as `jsonb` because the execution loop (Phase 2 — mobile-primary) will grow the schema (lap markers, HR targets, rep numbering cues) and a migration per revision is overkill for a v1 shape that's still settling. Each step is **distance- or time-based**: `distance_m` wins when both are present, else `duration_s` is used (the runner's `expandWorkoutSteps` already reads either). `recovery_pace: 'walk'` marks a walk break.

### Where the runner starts from, and a runner back from a break (issue #1186, decisions § 2090)

Both wizards open on **Where are you starting from?** A runner who has never run gets the walk-run plan and none of the race fields; one building up picks a distance but no goal time (a hidden goal time is not applied); one training for a race sees everything. A walk-run plan has no weekday roles (sessions at offsets 0/2/4, or 0/3 on two days a week, no long run), so it is exempt from the Sunday start (`planStartAllowed` / `alignPlanStart` / `defaultPlanStart` in the `plan_start` pair): it may start today and defaults to tomorrow, and a starter picked from `/plans/new`, the empty plans list or the mobile ready-made sheet starts on its own default (`starter_labels.ts` ↔ `plan_labels.dart`). Each starter says what it asks (`starterSummary`, read off the plan the generator builds: "9 weeks · 3 days a week · 30–45 min a session").

`returningFromBreak` (the `comeback` pair) reads a break of 28 to 365 days the runner is in, or one that ended inside the last four weeks, with at least three active pre-break windows. When it finds one, the wizard says so and eases the plan in with `capReturnRamp`: week 1 at most half the pre-break weekly average, each later week at most 10 % above the most any earlier week prescribed (so a step-back week holds the climb rather than letting the next week jump), sessions scaled down to the 100 m so a week never runs past its cap, speed sessions in those weeks turned easy, sessions the cap would take under 3 km dropped to rest, until the first week whose own schedule fits. The runner can turn it off or switch to walk-run intervals. A runner with fewer than three active weeks and no break gets a note that the plan could not be checked against recent training, with the same walk-run offer. With no confirmed recent 5K the paces come from the goal time, so `goalAheadOfRecentRuns` (the `race_predictor` pair) warns when the goal is more than 10 % faster than the runner's recent qualifying efforts project, and stays silent on a low-confidence projection.

### Walk-run (beginner / C25K) — persona #22, decisions §91

`generatePlan({ beginnerWalkRun: true })` produces a 9-week C25K-style plan: the goal stays a 5k, but every session is a `walk_run` workout of **timed** run/walk intervals (warmup walk → `count ×` (run `duration_s` / walk `recovery_duration_s`) → cooldown walk), graduating to a single continuous ~25-minute run in the final week. The progression table is `WALK_RUN_PROGRESSION` (mirrored in `training.ts` and `training.dart` — keep in lockstep). The wizard exposes it as a "New to running? Use a walk-run plan" toggle on web (`PlanEditor`) and mobile (`plan_new_screen`). On web, enabling the toggle also switches the goal to 5K when it was set to a longer distance (the default is a half) — a brand-new runner is not training for a half (persona round-5 runner-new); it's a one-shot on enable, so the runner can still re-pick 10K and a deliberate 5K choice is never clobbered. Beginners train 2 or 3 days/week; both wizards offer only those, since the generator caps run days at 3 (`WALK_RUN_MAX_DAYS_PER_WEEK`). `walk_run` workouts carry an estimated `target_distance_m` so the auto-match-from-run path still links them; the live recorder announces "Run"/"Walk" on interval transitions (see workout_execution.md).

The beginner plan's week count comes from `walkRunDefaultWeeks()` (= the progression length, 9), not `defaultPlanWeeks('distance_5k')` (= 8) — `PlanEditor`/`plan_new_screen` size `weeks` from it when the toggle is on. The generator also floors `totalWeeks` at the progression length so an explicit shorter `weeks` can never truncate the final graduation week (persona round-5 runner-new — the old web path forced 8 and silently dropped graduation). That final week's phase is `graduation` (the `plan_phase` enum's sixth value, labelled "Graduation week"), **not** `race` — a beginner walk-run plan has no goal race, so `race` ("Race week") implied one the runner never signed up for (issue #273). Only the standard generator's final week is `race`; `graduation` is walk-run-only.

### Masters recovery calibration (50+) — persona #30, decisions §93

`generatePlan({ age })` applies a masters recovery calibration when `age >= 50` (`isMastersAge`, mirrored in both twins). It does **not** touch pace — only recovery density: the first quality session moves from Tuesday (48h after the Sunday long run) to **Wednesday** (72h), the second from Thursday to **Friday**, and volume steps back every **3rd** week instead of every 4th (`isStepBackWeek(i, masters)`; week 0 is never a step-back). Age is read from `user_profiles.date_of_birth` on mount by both wizards (`PlanEditor` on web, `TrainingService.fetchViewerAge` → `plan_new_screen` on mobile) — no new wizard field. Null/unset age → the standard schedule. Why spacing and not slower paces: no validated age × VDOT pace table exists, and the gap masters athletes actually hit is hard-day frequency, not intensity — see decisions §93.

## Marking a workout as done

Two paths land in the same UI state (the green check on the calendar, the progress-ring counter ticking up):

1. **Auto-match from a saved run.** A trigger on `runs` (`private.match_runs_to_plan_workouts`, migration `20270901000001`, [decisions § 2079](../architecture/decisions.md)) links every run write, from any client or server import, the same way: a run carrying `metadata.plan_workout_id` links that workout first at any distance; otherwise each workout on the runner's **local** day (the `time_zone` pref) in an `active`, non-template plan takes the closest run that reaches 75% of its target distance (or target duration, for a duration-only walk-run session), with no upper bound. Rest, skipped and hand-ticked workouts are never touched, rides never match, a later run that is closer takes the workout from an earlier one, and deleting the linked run hands the workout to the next closest run that day. Only links the matcher made can move: a hand relink stays put, and a run the runner unlinked is never put back on that workout. Wrong matches are manually clearable via the "Unlink" control on the workout-detail page. A matching failure raises a warning and never blocks the run insert (auxiliary effect per the layered-resilience contract).
   A workout done a day or two early or late is never linked silently. Run detail asks instead (owner only): `plan_workout_link_candidates(p_run_id)` (migration `20270901000002`) returns the open workouts of the active plan within two local days either side of an unlinked run that it reaches 75% of, nearest day first, and the prompt reads "Did you do Thursday's planned workout early?" (or "late?"). Yes links it through the ordinary owner update, which the matcher never moves; "Not this one" records the answer (`dismiss_plan_workout_link`) and moves on to the next candidate, so the question is not asked again on the next visit. A workout the runner already took this run off is not offered again either. Web `RunPlanWorkoutPrompt.svelte`, mobile `RunPlanLinkPrompt`.
2. **Manual mark from the calendar editor.** The "Mark as done" button in `WorkoutEditor.svelte` calls `markWorkoutCompleted(id, null, { manual: true })`, which sets `manually_completed = true` and stamps `completed_at`. The same button toggles back to "Mark not done" — clearing both flags — when the workout is already completed via the manual path. If a workout already has a linked run, the button is disabled with a tooltip pointing the user at the workout-detail page's Unlink flow so the run/workout link is severed deliberately.

A session marked done without a linked run also counts as activity outside the plan: the dashboard's This Week card, the week lead and the Goals section's distance and run-count targets all read it through one helper, `markedDoneTally` in `goals.ts` / `goals.dart`, with its target distance standing in for the unrecorded distance ([decisions § 1813](../architecture/decisions.md)).

A workout done through a linked run that went well past its target reads **"Done · +3 km"** wherever a done workout carries a status line: Home's today card, the plan's today card and week rows, and the workout itself, on web and mobile. The matcher already counts any run of 75% of the target or more, with no upper bound (pinned by `match_runs_to_plan_workouts_test.sql`), so running long never stops a session counting; the extra is said only when it clears both 1 km and 10% of the target (`workoutOverrunMetres` in the `plan_nudges` pair), in the runner's unit, whole units unless a tenth says something (`overrunDigits`), with no verdict on it. A hand tick has no distance to compare and stays plain "Done". The distances behind linked workouts are read by run id (`fetchRunDistances` web / `TrainingService.fetchRunDistances` mobile), not from the 50-run window plan detail holds, so an older week keeps its figure; a failed read leaves "Done" ([decisions § 2126](../architecture/decisions.md)).

## Home's plan card (`plan_nudges.ts` ↔ `plan_nudges.dart`)

The re-plan proposals behind **Adjust plan** come to the runner on Home (issue #1186, [decisions § 2125](../architecture/decisions.md)). The rules are the shipped ones (§ 144) — `planNudge` only decides when one is worth a card, at most one at a time, first undismissed wins:

1. **Running less than planned** — the adaptive re-plan's 2-of-3 under-run trend (`adaptiveReplanRemaining`, the same bar), and only when it has a change to propose. "You've run less than planned in 2 of the last 3 weeks." Review opens the plan with the adaptive preview up.
2. **A big week** — the last completed week ran more than 20% over plan and `replanRemaining` eases next week's shorter runs to 85%. Review opens the plan with the re-plan preview up.
3. **Running on rest days** — a run on a day the plan schedules nothing but rest, in 2 of the last 3 completed weeks that schedule anything ([decisions § 2127](../architecture/decisions.md)). Those runs already count toward the week; the card says so and offers no change.

Review lands on `/plans/[id]?review=adaptive|replan` (mobile `PlanDetailScreen(openReview:)`), which runs the plan page's own proposal exactly as the Adjust plan option would — accept and decline are the existing preview's — and leaves the URL. Review and Dismiss both file the occurrence, keyed `<plan>:<kind>:<last completed week index>`, in the universal `plan_nudges_dismissed` pref ([settings.md](../backend/settings.md)), so it is gone on every device until the next week closes; filing on Review stops an accepted make-up or ease-off from being proposed again on top of itself. A dismissed proposal stays behind Adjust plan. No card for a paused, finished, abandoned, template or not-yet-started plan, and Home only ever shows the viewer's own plan, so a coach never sees one. Home's check is P1 only — it passes no fitness snapshot, which both fitness-gate guards pin — so with the P2 gate on, a card can open a preview the plan page then holds for fatigue. `buildReplanWeeks`, in the same pair, is the one builder of the engine's input that Home and plan detail share. A failure building the card costs the card, never Home. Web: `PlanNudgeCard.svelte` under the dashboard's plan hero, pinned by `tests-e2e/plans/plan-nudges.spec.ts`. Mobile: `widgets/plan_nudge_card.dart` under Home's today card, pinned by `plan_nudge_card_test.dart`, `plan_detail_review_test.dart` and `dashboard_screen_test.dart`.

## Skipping a workout

Separate from "done" and from a passive miss, a runner can **deliberately skip** a session — a deload day, an ease-off after over-running, or the session the missed-long-run advice recommended dropping. The "Skip" control on both `WorkoutEditor.svelte` and the workout-detail page (`markWorkoutSkipped(id, true)` web / `TrainingService.setSkipped` mobile) stamps `skipped_at` and clears any completion. A skipped workout renders struck-through and off the books on the plan calendar (a `skip_next` glyph instead of the green check), drops out of the progress-ring denominator, and is excluded from the missed-long-run make-up callout — so a deliberate skip doesn't keep nagging the runner to make it up. Un-skip clears `skipped_at` and returns the workout to a plain to-do. A workout with a linked run can't be skipped until the run is unlinked (the skip control disables with a tooltip, mirroring the done toggle).

## Calendar feed

A runner can subscribe to their plan from Google Calendar, Apple Calendar or Outlook (issue #1186, decisions § 2091). Settings → Integrations (web `PlanCalendarFeedCard`, mobile `PlanCalendarFeedScreen`) creates a secret link, shows it **once**, and offers *Make a new link* (the old one stops working at once) and *Turn off*. Afterwards the card shows only when the link was made and when a calendar last read it.

- **Endpoint.** `GET /functions/v1/plan-calendar/<token>.ics`, the `plan-calendar` Edge Function, `verify_jwt = false`: a calendar app can send no header, so the URL is the credential.
- **Token.** 96 hex characters: the feed row's id (a lookup selector) and 32 random bytes of secret. Only the secret's SHA-256 is stored (`plan_calendar_feeds.secret_hash`), compared in constant time after the indexed id lookup; an unknown id, a wrong secret and a revoked or replaced feed all answer the same `404 no-store`. One feed per user; replacing it changes both halves.
- **Throttles.** A malformed path is a 404 that spends no bucket. Then 3600 reads an hour per address, before the secret is read, applied only to a caller `cf-connecting-ip` names: calendar providers poll from shared pools, and the low per-address bucket shared by every unnamed caller would let one client lock every feed out, so unnamed callers share one 20 000-an-hour bucket instead (decisions § 2100, § 2106). 30 an hour per feed after the secret matches. Both fail closed; minting is capped at 20 an hour (`plan_calendar_rotate`). A served feed is `private, max-age=300`: a revoked or replaced link can keep serving from a calendar's own copy for at most five minutes, and calendar apps poll hourly or less often, so a longer age would save nothing.
- **Body.** The current plan's non-rest workouts (with chained plans, the one `pickCurrentPlan` picks against the runner's local date, decisions § 2099) as all-day, `TRANSPARENT` entries: the localized kind, the target distance or duration, and the pace in the owner's unit. No notes, race name, plan name, route, location, link or organiser. The UID is the workout's id, so a moved workout moves rather than duplicating. `plan_calendar_feed_events` decides the projection, so nothing the SQL does not select can reach the file.
- **Not in the export, and gone with the account.** The row holds a hash and two timestamps; `on delete cascade` removes it with the account. A feed URL is a credential, and an Art 20 archive is the wrong place for one.

Shipped on web `/plans/[id]` + Android `plan_detail_screen.dart` (2026-06-12): the over/under-running adherence banner, the missed-long-run make-up/skip callout, and the owner-only Re-plan preview-and-apply flow. **The banner's baseline is the plan TO DATE (2026-09-17, decisions § 1652):** `weeklyDriftToDate` windows the planned and the actual side to the week's days that have already ended (`scheduled_date < today` on both), so a runner level with what the plan asked for mid-week is not flagged, and the week's declared `target_volume_m` is scaled by the elapsed fraction of the schedule rather than compared whole. `weeklyDrift` keeps the two-totals shape the replan engines grade completed weeks with.
- **Missed-workout prompt ("ask once")** — **Shipped on web + Android/iOS (issue #1186, decisions § 2122, § 2123).** The Today card on Home and plan detail asks about the runner's most recent unanswered miss of the last 7 days (`missedWorkoutPrompt`, the `plan_missed_prompt.ts` ↔ `plan_missed_prompt.dart` pair, built on `isWorkoutMissed`, `missedWorkoutAdvice` and `replanRemaining`): "Missed: {kind} on {day}" with **Make it up** / **Let it go**, the engine's choice marked Recommended. A long run in the build with a later long run short of it offers the make-up (the next long run stretched, capped at +15%); a long run in the taper or before a recovery week, a long run the next one already covers, and every easy, tempo or interval miss offer only Let it go — a missed quality session is still dropped, never moved. Make it up opens the re-plan preview with only that row (Home links to the plan: `?makeup=1` on web, `openMakeUp` on mobile); Apply writes the stretch and the answer together through `answer_missed_workouts`, Cancel records nothing. Let it go records the answer alone. The answer is `plan_workouts.missed_ack_at`, so a miss answered on one device is never asked on another; it is null on every copy and cleared when the workout moves to another date. Owner-only, active and unfinished plans only: never on a paused, finished or abandoned plan, a template, or a coach's view of an athlete. Web `MissedWorkoutPrompt.svelte` (`tests-e2e/plans/missed-workout-prompt.spec.ts`), mobile `widgets/missed_workout_prompt_card.dart` (`test/missed_workout_prompt_card_test.dart`, `test/plan_detail_missed_prompt_test.dart`, `test/dashboard_missed_prompt_test.dart`), SQL `tests/answer_missed_workouts_test.sql`.

- ~~**Paste-a-template import** — markdown table → weeks/workouts.~~ **Shipped on web:** `plan_serialize.ts#parsePlanMarkdown` / `parsePlanJson` load a pasted Markdown table (`| Week | Date | Type | Distance | Pace | Notes |`, pace in min/km, distance in `km`/`mi`/`m`) or a JSON export into the editable preview through the **Import a plan** disclosure on `/plans/new`. The disclosure spans the whole editor rather than the 22rem form column, so a pasted table reads one row per line. In import mode the start date is the plan's own, so the date input drops its `min=today`: a plan already under way (start date behind today) saves, matching `submit()`, which never applied the past-date check to imports. The plan page dates week N as `start_date + 7N`, so an imported plan's week numbers should count 7-day blocks from its start date. Changing the goal, start date or days per week leaves import mode and regenerates. **The table is header-aware** (decisions § 2009): when the header names its columns (case-insensitive `Week`, `Date`, `Type` (or `Kind`), `Distance`, `Pace`, `Notes`, `Race`, `Priority`, `Goal`) they are mapped by name in any order; the legacy six-column header, a header naming an unknown column, or no header at all keeps the positional reading (extra cells fold into Notes). `Race` → `race_name` (≤ 120 chars), `Priority` → `race_priority` (A / B / C, case-insensitive), `Goal` (`h:mm:ss` or `m:ss`) → `target_duration_seconds`; all three are a readable parse error on a row whose type is not `race`. **Mobile imports too** (decisions § 2053): **Import a plan** on the new-plan screen opens `widgets/plan_import_sheet.dart` — paste, **Load** to preview the weeks, workouts and races, then **Create**, which asks the same overlap question as every create path and goes through `TrainingService.createPlan`; editing the text after Load drops the preview. The parser is `plan_serialize.dart`, the Dart twin of the parse half (`parsePlanMarkdown` / `parsePlanJson`); mobile has no export, so its Markdown writer is private and exists only for the JSON path. Days per week, which the table does not carry, is the busiest week's non-rest sessions held to 3–7. Pinned by `test/plan_serialize_test.dart`, `test/plan_import_sheet_test.dart`, and on web by `tests-e2e/plans/import-export.spec.ts` and `tests-e2e/plans/plan-races.spec.ts`.
- ~~**Export as markdown / JSON**~~ **Shipped on web:** `planToMarkdown` / `planToJson`, from the Export menu on `/plans/[id]`; round-trips through the import above. The Markdown table gains `Race | Priority | Goal` columns only when some race workout carries a name, priority or goal time, so a plan without them exports the six-column table older importers read; the JSON `ExportWorkout` carries the optional `race_name` / `race_priority` / `target_duration_seconds` and `race_taper_applied_at`. **The taper stamp rides only in JSON** (decisions § 2063): `parsePlanJson` lays each workout's stamp back onto the parsed plan (matching the n-th workout of a date and kind; a value that is not an ISO timestamp with a zone is a parse error), and `create_training_plan` writes it (migration `20270830000010`), so a tapered plan re-imported is not cut by the same taper again. The Markdown table is a prescription people edit by hand and carries no stamp either way.
