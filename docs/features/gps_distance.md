# GPS distance estimator (spec v1.4)

How every recorder in the estate turns a stream of GPS fixes into a distance. One algorithm, seven ports, one set of golden vectors.

Spec v1.2 (issue #1090) keeps every v1.1 behaviour and adds: an innovation gate against outlier fixes, adaptive measurement noise, a Doppler-vs-position cross-check, a low-speed Doppler debias, a pedometer zero-velocity update, an antimeridian-safe projection, and a **smoother** (forward pass plus Rauch-Tung-Striebel backward pass, with post-hoc stop detection for tracks with no Doppler) that produces the saved and recomputed figures. Live screens keep the forward filter.

Spec v1.3 (2026-10-09) adds a **Doppler speed scale**: the forward filter learns how far the phone's Doppler speed sits from the fixes' own displacement and corrects it, because both phones measured beside a Garmin carried a bias of several percent that v1.2 integrated straight into distance (§ Doppler speed scale below).

Spec v1.4 (2026-10-15, issue #1171) stops canopy stretches losing distance (§ Canopy and gaps below): the estimator keeps fixes stating up to 50 m (the recorders gated them at 20-30 m before it ever saw them), a gap longer than the gap window is credited at least the straight line across it, and stride is learned only from credit worth learning from.

## Why it exists

Until v1, every recorder (Flutter `RunRecorder`, Wear OS `RunRecordingService`, watchOS `WorkoutManager`, the custom-watch firmware) summed the straight-line hop between consecutive raw fixes and dropped hops under a 2-3 m floor. At running pace a 1 Hz fix moves ~2.7 m, the same size as the fix error, so the summed path zig-zags across the true line and every zig-zag adds length. A field report (2026-10-08) had a 3.1 mi course recorded as 3.92 mi (+26%) on a phone while a Garmin watch read ~3.1 mi.

Reading it:

- **With Doppler** (every run recorded since v1) v1.2 never under-counts on the twisty and canopy courses (Gilgen-Ammann 2020 found sport watches under-read by up to 9% in forest and urban areas, so this was checked explicitly). The new rows that move are the biased-Doppler chipset (+18.8% to +4.2%; what remains is the ~180 s before the cross-check's verdict) and slow walking under cover (+3.8% to +2.0%).
- **Position-only** (legacy tracks, server recompute): the gate and adaptive R cut the outlier and optimistic-accuracy rows hard, and the smoother removes the stationary drift and most of the residual zig-zag. **Known limit:** on twisty position-only tracks the constant-velocity model cuts corners, and the smoother, which estimates velocity from both sides of each turn, cuts them more than the forward filter (-3.1% against -1.2% on the forest trail; -31% against -19.5% on 12 s switchbacks). The cause is `Q_ACCEL` (below), not the smoother; the durable fix is a maneuver-adaptive or per-activity process noise tuned on the corpus's tree-covered course. Until then the server recompute keeps the forward pass for a position-only track that is not a road run (Server recompute, step 3), which still under-reads a tight switchback trail, by less.
- The pessimistic-accuracy slow walk shows the debias trade-off: a platform that overstates `speedAccuracy` makes the debias subtract too much, which is why it fades out by 1.0 m/s.

## Algorithm

The reference implementation is [`scripts/gps_distance/reference.py`](../../scripts/gps_distance/reference.py) (stdlib Python, scalar float64 only). It is the spec; this page explains it. The exact per-fix order of operations is in **Porting notes** at the end.

1. **Projection.** The first valid fix fixes a local tangent plane: `x = rad(wrap(lng - lng0)) * R * cos(rad(lat0))`, `y = rad(lat - lat0) * R`, `R = 6371008.8`. `wrap(d)` maps a longitude difference into [-180, 180) (`d >= 180: d - 360`, `d < -180: d + 360`), so a run across the antimeridian is an ordinary hop instead of a 40,000 km jump (v1.2). The inverse (`unproject`) wraps the output longitude the same way.
2. **Filter.** Two independent 1-D constant-velocity Kalman filters (x and y), state `[p, v]`, covariance `[[a, b], [b, c]]`, white-acceleration process noise `Q_ACCEL = 0.6 m^2/s^3`. Stated position variance is `r_stated = max(accuracy, 3 m)^2` (missing / non-positive accuracy reads as 3 m). The variance actually used is `r = max(r_stated * rScale, 9)` (v1.2, item 5).
3. **Innovation gate (v1.2).** After the predict, the 2-D normalised innovation squared `NIS = yx^2 / (ax + r) + yy^2 / (ay + r)` (y = measurement minus prediction, ax / ay the predicted position variances) is compared with `GATE_CHI2 = 13.8155` (chi-square, 2 dof, p = 0.001). A rejected fix skips the position update only: time still advances, Doppler still updates the velocity, and it is still credited (credit comes from speed, not position). **Lock-out guard:** after `GATE_MAX_REJECTS = 5` consecutive rejections the next rejected fix re-anchors position (`p = z`, `a = r`, `b = 0`, velocity kept), so a genuine jump (a tunnel exit, a multipath state that persists) cannot lock the filter out.
4. **Adaptive R (v1.2).** Covariance matching on accepted fixes: `sample = ((yx^2 - ax) + (yy^2 - ay)) / (2 * r_stated)`, clamped to [0, 9], then `rScale = clamp(0.95 * rScale + 0.05 * sample, 1, 9)`, used from the next fix. It only **inflates**: under time-correlated GPS error the innovations look small because the error is slowly varying, not because it is small, so deflating R below the stated accuracy made the position-only bench over-count more (an `R_SCALE_MIN` of 0.5 gave +1.2% to +3.2% where 1.0 gives +0.8% to +2.3%). Multipath is biased and persistent rather than sparse, so the gate alone cannot catch it (research note 13); adaptive R is what handles a platform that is consistently optimistic.
5. **Doppler.** The chip's own speed (`Position.speed` / `Location.speed` / `CLLocation.speed`, from the carrier Doppler shift). Usable when finite, `0 <= speed <= maxSpeed`, and its accuracy (default 0.5 m/s when unreported) is `<= 1.5 m/s`. **Low-speed debias (v1.2):** when the platform reported `speedAccuracy` (`sa`), `s' = sqrt(max(0, s^2 - w * sa^2))` with `w = 1` at `s <= 0.5 m/s`, fading linearly to `w = 0` at `s = 1.0 m/s`. Why: the speed is the magnitude of a noisy 2-D velocity, Rician-distributed, so `E[s^2] = v^2 + 2 sigma^2` and at `v = 0` it is Rayleigh with mean `1.25 sigma` (it never reads zero). With isotropic error, `s^2 - sa^2` is first-order unbiased for `v^2` at speed and removes ~40% of the Rayleigh bias at a standstill. It is faded out because platforms usually overstate `sa` (Li et al. 2022 measured cm/s-to-dm/s actual error) and a pessimistic `sa` over-corrects into under-counting, the failure Gilgen-Ammann warns about; above ~1 m/s the raw bias `sigma^2 / 2v` is small anyway. When a bearing is present and `s' >= 0.4 m/s`, the speed vector updates the velocity with variance `max(sa, 0.3)^2` (unchanged), unless the cross-check has distrusted Doppler or a ZUPT applies.
6. **Doppler cross-check (v1.2).** Some chipsets carry a constant Doppler bias (Peng et al. 2023) that the v1.1 design integrated straight into distance. On each accepted fix with usable Doppler at `>= 0.8 m/s`, a bearing, no ZUPT, and a span to the previous accepted fix `<= 5 s`, the raw displacement since that fix is projected on the Doppler bearing: `u = (dx sin b + dy cos b) / span`. This is unbiased on turns, where a filtered speed cuts corners (an earlier draft compared against a position-only filter's speed and distrusted good Doppler on every twisty course). Both speeds feed EMAs (`tau = 60 s`, `alpha = min(1, span / tau)`, both seeded with the Doppler speed). After `XCHECK_MIN_S = 120 s` of compared time, the verdict flips when the disagreement holds for `XCHECK_PERSIST_S = 60 s`: distrust when `|ema_dop - ema_u| > max(0.4, 0.15 |ema_u|)`, trust again when `< max(0.2, 0.08 |ema_u|)`. While distrusted, Doppler neither updates the velocity nor earns credit, so the fix credits through the position path; the EMAs keep running so it can recover. Biases below ~0.4 m/s are not detected (the bench's correlated position noise moves the EMA by ~0.2 m/s on twisty courses).
7. **Zero-velocity update (v1.2).** Once the pedometer has reported **any** step increase this run, a fix more than `ZUPT_NO_STEP_S = 6 s` after the last increase is stationary: both axes get a velocity pseudo-measurement `0` with variance `0.1^2`, no Doppler velocity update, no cross-check sample, and **no credit**. Trusted Doppler at `>= 1.0 m/s` overrides it (a runner whose pedometer lags a restart). **Release guard:** while a pedometer ZUPT holds, the filtered position is compared with where the ZUPT started; past `ZUPT_RELEASE_M = 40 m` the pedometer is taken as stalled, the ZUPT releases until the next step increase, and that fix credits the 40+ m chord instead of its speed. That keeps a dead step sensor from freezing distance (layered resilience: the pedometer is a higher layer than GPS distance). **`ZUPT_NO_STEP_S` must be measured on device**: Android delivers step-counter events in batches that lag several seconds, so too small an N turns every batch interval into a stop.
8. **Credit.** Per fix: zero if a ZUPT applies; else `speed = debiased Doppler` if usable and trusted (floor 0.4 m/s), else `|filtered velocity|` (floor 0.8 m/s). Below the floor the fix credits **zero** — this is what kills red-light drift. Otherwise `min(speed, maxSpeed) * dt`. A ZUPT release credits its chord.
9. **Gaps.** `dt > gapWindow` re-anchors the filter at the new fix (`gapWindow = 10 s x max(1, expectedIntervalS)`). A non-increasing timestamp is ignored. The cross-check's last position and the gate streak reset at a re-anchor; the cross-check EMAs, `rScale` and the trust verdict carry across it. **v1.4:** the gap is credited a lower bound rather than nothing: `lower = hypot(z - p) - sqrt(ax + ay + 2r)` (the straight line from the filter's last position to the new fix, less the 1-sigma uncertainty of both ends), capped at `maxSpeed * dt`; when it exceeds the steps committed for the gap (item 10), the GPS credit makes up the difference. A path across a gap is never shorter than its chord, so the figure can only be short, never long.
10. **Pedometer gap fill.** `addSteps(t, cumulative)` learns a stride while GPS is good (a fix within `2 s x max(1, expectedIntervalS)`, every 50 steps, 0.4-2.5 m, EMA 0.2); while GPS is not good, steps x stride accumulate in a pending buffer (capped at `maxSpeed * dt`) that is committed only if the gap exceeds the gap window, or at `finish(t)` when the run ends in a gap. `initialStrideM` carries a stride across a pause, and on the phone across runs (the app persists the last learned stride per account and activity). v1.2 adds only the ZUPT bookkeeping (`stepsSeen`, `lastStepIncreaseT`, clearing `zuptReleased`) on every increase. **v1.4:** a fix teaches stride only when its credit is trustworthy (`learnStride` stretch, and Doppler credit with `speedAccuracy <= STRIDE_MAX_SPEED_SIGMA_MPS` = 1.0 m/s, or position credit from a fix stating `<= STRIDE_MAX_POS_SIGMA_M` = 20 m); any other fix empties the stride window and the steps that follow it are not counted. A stretch built with `learnStride = false` (Android's fused provider) uses its seeded stride and never learns one.
10b. **Accuracy cap (v1.4).** A fix stating accuracy over `MAX_POS_SIGMA_M` = 50 m is ignored outright, exactly like an invalid one. Fixes between 20 and 50 m are filtered, gated and credited like any other (their `r` comes from the stated accuracy), but stay out of the cross-check and the Doppler scale (`CHECK_MAX_POS_SIGMA_M` = 20 m): both read raw fix displacement, and canopy noise there teaches a scale, not a bias.
11. **Outputs.** `distance = gpsDistance + stepDistance`, plus `stepDistance` and `stride` for metadata, and the diagnostics `rejectedFixes`, `zuptFixes`, `rScale`, `dopplerTrusted`.

The forward estimator only decides **distance**. The track (the waypoints stored, drawn and route-matched) keeps each recorder's existing movement-gated append rule.

## Smoother (v1.2): the saved and recomputed figure

`smooth_distance(events, maxSpeedMps, expectedIntervalS, initialStrideM)` takes the run's whole event stream (fixes, step counts, finish, in arrival order) and returns:

| Output | Meaning |
|---|---|
| `distance_m` | smoothed GPS distance + step distance |
| `gps_distance_m`, `step_distance_m` | the two parts |
| `cumulative_m[i]` | per **event**: smoothed GPS credit through event `i` plus the step distance committed by then (the embedded-best cumulative) |
| `positions[i]` | per **event**: `(lat, lng)` of the smoothed position for an accepted fix, `None` for a steps / finish event or an ignored fix (the filtered line stored alongside the raw track, item 7) |
| `stopped_fixes` | how many fixes post-hoc stop detection flagged |

Steps:

1. **Accepted fixes.** The same rule as the estimator: finite `t` / `lat` / `lng`, stated accuracy not over 50 m (v1.4), `t` strictly greater than the last accepted fix. The first such fix sets the projection origin.
2. **Post-hoc stop detection, only when no accepted fix carries a finite `speed`** (a legacy track): for each accepted fix `j`, half-window `H = 20 s x max(1, expectedIntervalS)`, set A = fixes with `t_j - H <= t < t_j`, B = fixes with `t_j <= t <= t_j + H` (B includes `j`). Fix `j` is stopped when A and B each hold at least 3 fixes, the net speed `|mean(B) - mean(A)| / (meanT(B) - meanT(A)) < 0.5 m/s`, **and** the RMS distance of A plus B from their joint mean `< 10 m`. The RMS test is what keeps an out-and-back turnaround (two halves with the same mean) from reading as a stop. Means are plain sums in index order divided by the count; projected raw positions are used.
3. **Forward pass.** A fresh `GpsDistanceEstimator` replays the events, each stopped fix passed `stopped_hint = true` (treated exactly like a ZUPT: zero-velocity pseudo-measurement, no Doppler update, no credit, no release check). It records, per accepted fix: whether it is a gap anchor, whether it starts a new **chain** (an anchor or a gate lock-out re-anchor), `dt`, the predicted state and covariance per axis (after predict, before any update), the final filtered state and covariance per axis, the ZUPT flag, the usable-and-trusted debiased Doppler speed (or none), the release chord (or none) and the step distance committed so far. Stride learning uses this pass's forward credit.
4. **Backward pass (RTS)** per chain, per axis, independently. The last fix of a chain keeps its filtered state; for `k` from the second-to-last down: with filtered `(p, v, a, b, c)` at `k` and the next fix's `dt` and predicted `(pp, pv, A, B, C)`: `det = A C - B^2`, `g00 = ((a + dt b) C - b B) / det`, `g01 = (b A - (a + dt b) B) / det`, `g10 = ((b + dt c) C - c B) / det`, `g11 = (c A - (b + dt c) B) / det`, `dp = ps[k+1] - pp`, `dv = vs[k+1] - pv`, `ps[k] = p + g00 dp + g01 dv`, `vs[k] = v + g10 dp + g11 dv`. Gap segments are independent; a lock-out starts a new chain but not a new credit segment.
5. **Credit** per fix `k`: a gap anchor carries the forward pass's gap lower bound (v1.4; zero for the first fix); any other fix the release chord if it has one, else `0.5 * (eff[k-1] + eff[k]) * dt` (trapezoid), where `eff` is 0 under ZUPT / stop hint, else the recorded trusted Doppler speed with floor 0.4, else the smoothed `hypot(vx, vy)` with floor 0.8, capped at `maxSpeed`. The trapezoid uses the fix before `k` in the record, which for the first fix after an anchor is the anchor itself, whose smoothed velocity is meaningful (the backward pass reaches it).

What the smoother changes: credit stops lagging the speed it follows (both sides of each pace change are seen), stationary drift on legacy tracks goes (stop detection), and positions are smoothed (lower RMS error than the forward filter's). With trusted Doppler the credit speed is the same Doppler speed the forward filter uses, so the smoothed and forward totals differ only by the trapezoid; the benefit concentrates on position-only tracks.

**v1.3 on the same inputs** (smoothed, mean [worst]): the Doppler rows move little (sigma 3 m: 0.0% [+0.4]; Android 5 s fixes -0.3% [+1.5]), the +0.5 m/s Doppler bias falls from +3.4% to +0.8% [+1.0], and the position-only rows do not move at all (no Doppler, no scale). The cost is on twisty Doppler courses, where a chord between fixes is shorter than the arc the Doppler speed measured: forest trail +0.9% to -2.1% [-2.8], canopy switchbacks +1.0% to -1.6% [-4.6]. Urban canyon +1.1% to +0.7% [+2.2].

**Who uses which.** Live distance and live pace: the forward estimator. Saved distance at the end of a phone run, embedded bests, and the server recompute: the smoother (ports: Dart, TS, Deno, Go). The watches keep the forward filter: the smoother needs the whole run in memory, so the server re-derives a Wear OS or watchOS run's saved figure from its uploaded track automatically (Server recompute, step 0).

## Doppler speed scale (v1.3)

Two runs recorded on 2026-10-09 with a Garmin (FIT), an Android phone (fused provider) and an iPhone carried together showed both phones' Doppler speed off by several percent, steadily enough that the v1.2 cross-check (which trips only past max(0.4 m/s, 15%)) never noticed. Against Garmin's own speed: the iPhone read 0.165 m/s low on the first run and 0.04 m/s low on the second; the Android read about 0.2 m/s high on the first, and on the second high for 40 minutes and then low. The filter credits distance from Doppler, so the saved distance inherited it.

The estimator now keeps two exponentially forgotten integrals (time constant `DSCALE_TAU_S` = 600 s) over consecutive accepted fixes: the fixes' displacement projected on the span's mean Doppler bearing, and the trapezoid Doppler distance over the same span. Their ratio, clamped to 0.8-1.25, multiplies every Doppler speed the filter uses (velocity update, credit and the smoother's record). A span is only compared when both ends carry Doppler of at least `DSCALE_MIN_SPEED_MPS` (1.5 m/s; at walking pace, comparing only the readings that clear a lower floor biases the scale low — the bench's slow walk read -13% before this gate), the bearing turns less than `DSCALE_MAX_TURN_DEG` (45 degrees) across it, and it is no longer than `XCHECK_MAX_SPAN_S`. The scale stays 1 for the first `DSCALE_MIN_S` (60) compared seconds. The cross-check is unchanged and still compares the raw Doppler.

Replayed from the stored tracks (saved distance against the Garmin's):

| | Garmin | v1.2 | v1.3 |
|---|---|---|---|
| iPhone, run 1 | 5198 m | -8.2% | -4.1% |
| iPhone, run 2 | 10532 m | -2.4% | -1.1% |
| Android, run 1 | 5198 m | +7.0% | +4.7% |

The replay reproduces what each phone saved (Android run 1: +7.0% replayed, +6.9% saved), so the stored track is a faithful input. What is still open:

- **The ground truth is a watch.** The constants were chosen among variants that differ by about 2 points on these runs, which is Garmin's own error, so they were picked for the smallest worst case on the synthetic bench, not fitted to these four runs. A measured course decides them (issue #1106, continuing #1090 item 2).
- **Projection bearing.** On both phones a fix's bearing matches the chord *into* it (median 4 degrees) far better than the chord out of it (9 degrees). Projecting on the end fix's bearing instead of the span's mean read the iPhone runs better (-3.1% / +0.5%) and the bench's 5 s Android row worse (-3.7%); the measured course decides this too.
- **The Android's positions agree with its Doppler.** After 25 minutes of run 1 the fused provider's displacement read as long as its Doppler, both about 6% over the Garmin, so no scale learned from the phone's own fixes can correct it. That is item 6 (fused provider against raw `GPS_PROVIDER`), resolved by recording from the receiver ([Input source](#input-source)).

## Input source

The estimator assumes GNSS input: positions and Doppler speed measured by the satellite receiver, with errors that are noise around the truth. Android's fused provider breaks that assumption, so on Android, phone and Wear OS watch alike, the recorder takes its fixes from `GPS_PROVIDER` and uses the fused provider only as a fallback while the receiver is silent ([run_recording.md § Android location source](run_recording.md#android-location-source), decisions § 1960 and § 1984). `metadata.location_provider` (`gps` / `fused` / `mixed`) says which stream a saved run came from.

**Signal quality is recorded, not used.** Android phone and Wear OS runs save `metadata.gnss_signal`, a summary of the receiver's `GnssStatus` over the run: median and 10th-percentile C/N0 of the strongest four satellites used in each fix, median satellites used, and the share of readings with a used L5 / E5a satellite ([run_recording.md § Android location source](run_recording.md#android-location-source), [metadata.md](../backend/metadata.md)). The estimator does not read it; it identifies canopy and urban-canyon runs for the corpus and is the signal an adaptive measurement noise would start from (#1170). One shared fixture, `fixtures/gnss_signal_vectors.json`, pins the Dart and Kotlin summarisers.

**Why fused is a fallback only.** A 2026-10-15 Android run on the fused provider saved 5,952 m against about 5,390 m true (+10.4%) ([issue #1106](https://github.com/Absence0760/threkir/issues/1106#issuecomment-6196300906)). Its `speedMps` integrated to +25% over truth for the whole run, correlated with the fix-to-fix chord at only r = 0.32, and reported a `speedAccuracy` of 0.2 m/s; its positions read about 5% long even over straight 10-20 s windows. That is the shape of non-GNSS estimates, consistent with step-based dead reckoning, blended into both speed and position. The Doppler scale learns against those same positions, so it ended at 0.875 against a true ratio of about 0.80, and no tuning of the estimator can recover a bias its reference shares. The 2026-10-09 Android run 1 above failed the same way.

**The estimator on true GNSS input.** Replaying the 2026-10-09 Garmin FIT tracks (GNSS-only positions) through `scripts/gps_distance/reference.py` `smooth_distance` reads -0.2% and +0.4% against the truth estimates (5,150 m / 10,450 m), where the Garmin itself read +0.9% / +0.8%. On the synthetic bench (`scripts/gps_distance/bench.py`, spec v1.3) with honest Doppler most rows stay within about ±1%. The known weak rows (forest trail -2.1%, slow walk +2.0%, canopy switchbacks) remain the measured-course tuning job in #1106. No constant changed for this; v1.4 (below) is what changed the spec next.

## Canopy and gaps (v1.4)

Issue #1171. Three changes, one spec bump, because all three regenerate the vectors.

- **Poor fixes are weighted, not dropped.** Under canopy a receiver states 20-40 m routinely while its Doppler speed stays good. The phone recorder dropped every fix over 20 m (Wear OS over 30 m, watchOS at 30 m) before the estimator saw it, so a stretch under trees longer than 10 s became a gap and its Doppler was thrown away. The recorders now hand the estimator every fix up to its 50 m cap; the map line and the route match keep the old gate. The stored track keeps those fixes too, flagged `offTrack`, so a server replay sees the same input ([Stored track](#stored-track)); before that it held only the gated fixes, and the automatic watch-run recompute read 3.7-4.5% short under canopy. The estimator already takes `r` from the stated accuracy, and the Doppler velocity update already rides on the fix's own `speedAccuracy`, so the change is in who sees the fix, plus the 50 m cap and the cross-check exclusion above.
- **A gap credits at least its chord.** Item 9. Before, a gap with no learned stride credited 0. The phone also persists the stride per account and activity (`learned_stride_m`, device-local; [settings.md](../backend/settings.md#device-local-pairing-prefs-not-in-the-synced-bag)) and seeds `initialStrideM` from it, so a gap before a run has relearned one is still step-filled.
- **Stride is learned only where speed is the receiver's.** A stride learned on the fused provider (measured +25% fast, #1106) and carried across the source switch filled later gaps 25% long. The recorders build a fused stretch with `learnStride = false`; on iOS and watchOS every stretch learns. Item 10 also refuses Doppler stated worse than 1.0 m/s and positions worse than 20 m.

The receiver-vs-fused arbitration threshold is separate from all of this: a receiver fix counts as "delivering" only within 20 m on the phone (`RunRecorder.sourceArbitrationGateMetres`) and 30 m on Wear OS (`LocationSourceArbiter.arbitrationGateM`). Both are constructor parameters, left at the old gate until the tree-covered corpus run in #1098 decides whether canopy fixes should hold fused off. Device acceptance is that run.

**The custom watch's input.** The firmware reads the u-blox MAX-M10S directly: positions from NMEA RMC, Doppler speed from RMC's speed over ground, bearing from its course, and the horizontal and speed accuracies from UBX-NAV-PVT `hAcc` / `sAcc`, which the firmware enables itself with a UBX-CFG-VALSET that also sets the pedestrian dynamic model (`apps/custom_watch/drivers/ublox_nmea/src/ubx.rs`). NMEA alone carries no accuracy in metres; GGA's HDOP is unitless and would need a guessed per-satellite error, so it is not used. A PVT feeds `accuracy_m` / `speed_accuracy_mps` only when it is at most one second from the RMC; otherwise both are `None` and the estimator applies its floors, which is also what the Renode sim's NMEA-only feed produces (decisions § 1992).

## Stored track

PR #1164. A recorder that runs the estimator stores **every fix the estimator took**, in recording order, and flags the ones that failed its track gate with `offTrack: true`. The server's replay of the stored track (`distance_recompute`, [Server recompute](#server-recompute)) then sees exactly the live input; before this the watches stored only the fixes inside their 30 m gate, so a canopy stretch replayed as a gap credited its chord where the wrist had credited its Doppler (`reference.py` + `bench.py`, 1850 s with canopy half of every 180 s: 3.7-4.5% short).

| Recorder | Stored off the line (`offTrack: true`) | Line readers that skip them |
|---|---|---|
| Phone (`RunRecorder`) | a fix past the 20 m accuracy gate and within the estimator's 50 m cap; a fix inside the gate that the movement gate held back (jitter under the track threshold, an implausible hop) when the estimator took it | `RunSnapshot.track` is the line alone, so the live map, elevation gain, route progress, the resume's route replay and the blue dot never see one. `RunSnapshot.storedTrack` is the stored track: the crash checkpoint persists it, `stop()` saves it. On the finish screen the map, moving time, the route auto-link and the recent-run sparkline take `trackLine(...)`; the embedded bests replay the whole track through the estimator on purpose |
| Wear OS (`RunRecordingService`) | a fix `SourceVerdict.track` refuses (past 30 m, within 50 m) | the overlay, the latest point, the route match (the off-track branch returns before them, as before); the post-run map (`trackLineLatLngs`) |
| watchOS (`WorkoutManager`) | a fix at or past `trackAccuracyGateM` (30 m), within 50 m | the mini-map trail and position, route guidance, and the trail rebuilt on a continued run |

- **The flag.** Dart `Waypoint.offTrack` (`offTrack` in both the local store's JSON and the uploaded blob, through `ApiClient`'s codec), Kotlin `TrackWriter.append(point, distM, offTrack)`, Swift `TrackPointRecord.offTrack`. It is written only when true and never as `false`, so every track recorded before it, every import and every point on the line reads as on-track. Every stored point, off-track ones included, carries `distM`.
- **`metadata.track_complete: true`** ([metadata.md](../backend/metadata.md)) says the stored track holds every fix the estimator took. Written by the phone's `stop()` on a GPS run with a non-empty track, by Wear OS and watchOS on every run with one, and passed through by the phone's watch ingest. It is not written on a treadmill run, on a phone run resumed from a crash checkpoint that did not carry it (`resumeSession(trackComplete:)`, the checkpoint writes the recorder's `storedTrackComplete`), or on a Wear OS / watchOS run recovered or continued from a checkpoint an older build wrote.
- **Readers.** Anything that draws, matches, clips, measures elevation or climb on, or projects the line takes `trackLine(track)` (`packages/core_models/lib/src/waypoint.dart`), which returns the list unchanged when nothing is flagged. Only a distance replay reads the stored track whole.
- **The custom watch is outside the contract.** Its flash track is a movement-gated breadcrumb decimated to 253 points per 4 KiB slot (`run_store.rs`), its recorder applies no accuracy gate to that track, it stamps no `distance_estimator`, and the recompute trigger never queues it (decisions § 1991). It writes neither the flag nor the key, and its 253-point cap is unaffected.
- **Size.** Under canopy the stored track gains one point per fix the estimator took past the gate, so it is bounded by the run's fix rate (1 Hz) and by the 50 m cap, past which nothing is stored. The watches already stored every open-sky fix at 1 Hz, so they grow only by their canopy fixes. The phone also stores the fixes its movement gate held back, and it opens its streams with `distanceFilter: 0` at 1 s, so its stored track becomes one point per second recording rather than one per 3 m moved: at an easy running pace (under 3 m/s) that is up to about twice the points it stored before, and a stop now stores a point a second where it stored none. A stored point is about 245 bytes of JSON and about 45 bytes gzipped, so even a 100-hour run stored at a full 1 Hz is about 16 MB in the `runs` bucket, inside its 25 MiB `file_size_limit` (`StorageBuckets.runsBucketMaxBytes`); the phone's local store and its crash checkpoint hold the uncompressed JSON. The phone's smoother event log is unchanged, since it already logged every fix the estimator took.

## Waypoint fields

So the server can recompute distance from a stored track with the same Doppler input, each waypoint carries four optional keys alongside `lat` / `lng` / `elevationMetres` / `timestamp` / `bpm`:

| Key | Unit | Source |
|---|---|---|
| `accuracyMetres` | m | horizontal accuracy |
| `speedMps` | m/s | Doppler speed (omit when invalid / negative) |
| `speedAccuracyMps` | m/s | speed accuracy (omit when not reported) |
| `bearingDeg` | degrees clockwise from north | course over ground (omit when invalid) |
| `smoothedLat` / `smoothedLng` | degrees | the smoother's position for that fix, written by the phone at save; both or neither, raw `lat` / `lng` never altered |
| `distM` | m | the run's distance credited up to and including this fix: the estimator's cumulative figure (forward on the watches, moved onto the smoother's at `stop()` on the phone), never decreasing. Dart `Waypoint.cumulativeDistanceMetres` (the same name in the local store's JSON), web `TrackPoint.distM`, Go `TrackPoint.DistM`, Kotlin `TrackWriter.append(point, distM)`, Swift `TrackPointRecord.distM`. Read only by splits and moving time ([Splits and moving time](#splits-and-moving-time)). **Owner-only**: never served to a non-owner (see below) |
| `offTrack` | — | `true` on a fix the estimator took that failed the recorder's track gate ([Stored track](#stored-track)); absent otherwise, never `false`. Dart `Waypoint.offTrack`, Kotlin `TrackWriter.append(..., offTrack)`, Swift `TrackPointRecord.offTrack` |
| `baroEle` | m | the phone barometer's altitude, anchored to GPS altitude over a long window ([run_recording.md § Barometric altitude](run_recording.md#barometric-altitude)); `ele` stays the GPS altitude. Dart `Waypoint.baroElevationMetres` (`baroElevationMetres` in the local store's JSON), web `TrackPoint.baroEle`. Omitted on a phone with no barometer and before the anchor has a GPS altitude to level against |

Old tracks have none of them and recompute through the position-only path, with post-hoc stop detection. `baroEle` plays no part in distance; climb, the elevation profile and grade-adjusted pace read it through `runAltitude` ([run_recording.md § Barometric altitude](run_recording.md#barometric-altitude)).

Readers that draw the line, route-match or match pace segments prefer the smoothed pair when both halves are present and finite (web `lib/runs/track_line.ts`, Dart `Waypoint.lineLat` / `lineLng`, Go `parseTrack`); the estimator always reads raw.

Privacy-zone clipping therefore tests both positions: a leading or trailing fix is dropped when its raw OR its smoothed position is inside a zone, so no drawn endpoint can sit inside one. The server applies it for non-owners in `clip_track_for_user` (migration `20270719000005`); the client copy is the `privacy` parity pair (`isFixInAnyZone` / `clipPointsToZones` in web `routes/privacy.ts` and Dart `lib/privacy.dart`), which the run share image applies to the owner's track before drawing it on both platforms (mobile `runShareCardTrack`, web `share/share_card_track.ts`). Both fail closed on the zones: a list that is not known — the settings bag not loaded, or offline on a cold cache (web `LoadedSettings.universalUnknown` / `knownEffective`) — is never read as "no zones"; Share, Share as image and the mobile export sheet refuse with a retryable message instead (`runDetailShareZonesUnknown` / `runDetail.shareZonesUnknown`), and the web share card draws no map until the zones are known.

**`distM` never reaches a non-owner.** It measures the run from its first fix, so on the first point a privacy-zone clip leaves it states how far the runner went inside the start zone, and its gap to `distance_m` on the last point states the same for an end zone. `clip_track_for_user` removes it from every point it returns, on every path including a user with no zones (`20270829000021`), and `clip-public-track` removes it again from its non-owner response (`NON_OWNER_WITHHELD_POINT_KEYS`); the owner's own track keeps it. Dropping, not rebasing to the first served point: no non-owner surface computes splits or moving time, `trackCumulativeMetres` falls back to the line's hop-sum from 0 when the key is absent, and a rebased figure would still carry the credit of every stretch between two served points, including one a future interior clip removes. **A new per-point key that measures the run from its start (a cumulative count, a run-relative offset) is withheld the same way**: add it to the function and to `NON_OWNER_WITHHELD_POINT_KEYS` in the change that adds the key. A privacy-boundary change: CISO / Security Analyst sign-off before deploy.

**Off-track fixes are distance input, never line.** A stored point flagged `offTrack: true` (a fix the recorder's estimator took that failed its track gate) is read by the distance replay and by nothing that draws, matches, clips or measures the line. The server replay reads every point (`RecordedTrackPoint.OffTrack` is decoded and ignored by `replayRecordedTrack`), so a canopy stretch replays from its own fixes and Doppler: the shared `canopy_20_50` vector with its 60 fixes stated 35 m flagged replays to the recorder's 476.441 m, and the same track without them reads 462.549 m (-2.9%, `reference.py` and `TestDistanceRecompute_ReplaysOffTrackCanopyFixesToTheRecordersFigure`). Every other reader skips them, one shared helper per platform: web `trackLine` / `isOffTrack` (`lib/runs/track_line.ts`, beside `lineLat`) and Dart `trackLine` (`core_models`). On the server: the Go `parseTrack` (the `map_match` OSRM input and the GPX data export), `onTrackRaw` (the road matcher and road classifier inside the recompute and the watch sidecar step), the smoothed sidecar (`null` at an off-track index, so no reader draws one), `clip_track_for_user` (drops them before the zone walk, `20270829000032`), `clip-public-track` (`isOffTrackPoint`, again on the non-owner response) and the Edge GPX export (`buildGpx`). On web: the run map, replay scrubber and elevation chart (`baseTrack`), `runAltitude` (climb, profile, grade-adjusted pace, save as route), race phases, segment efforts, the GPX download, the share card and the make-public zone check, route auto-link (`fetchRoutesIntersectingTrack`), and every owner fetch that draws (`fetchTrackByPath`: the runs-list thumbnail, the personal heatmap, the owner's share page). On mobile: the run-detail map, replay, route suggestion, race phases, segments, best efforts and make-public check, `runAltitude`, the share card and its GPX / TCX / FIT exports, the run-list thumbnail, the heatmap, the dashboard's offline PB scan and the owner's public run page. Splits, moving time and heart rate keep every point: they measure on `distM`, which every point carries, and an off-track fix's heart rate is still a heart rate. **Exports are the line**: the GPX (web, mobile, Edge, Go), TCX and FIT exports carry on-track fixes only, because a 30-50 m fix is not a place the runner was, and the GDPR backup format keeps the stored blob byte for byte, flags included. A non-owner never receives an off-track fix in or out of a privacy zone; a privacy-boundary change, CISO / Security Analyst sign-off before deploy.

**Smoothed-position sidecar.** Watch tracks arrive without the pair (the watches keep the forward filter), and old runs the server recomputes never had it. The worker cannot write it into the track: Supabase Storage has no conditional upload and clients overwrite `{user_id}/{run_id}.json.gz`, so a rewrite could clobber a concurrent re-upload unseen. It writes a sidecar beside it instead, `{user_id}/{run_id}.smoothed.json.gz` (`apps/job_worker/internal/smoothed_sidecar.go`): `{"version": 1, "track": {"points": N, "sha256": "<hex>"}, "positions": [[lat, lng] | null, ...]}`, one position per **stored** waypoint index (null where the smoother placed none — a waypoint without a coordinate or timestamp — and on every off-track waypoint, which no reader draws), rounded to 1e-7 degrees, plus the fingerprint of the exact track it was computed from: the waypoint count and the lower-case hex SHA-256 of the track's decompressed JSON bytes. It is written after a distance recompute that kept the smoothed pass (a forward-pass recompute keeps its raw line, Server recompute step 3, and removes any sidecar an earlier recompute of the same track left, whose fingerprint would still match), and by the `map_match` job for a `watch` run, under the same rule (a watch track with no Doppler gets one only when `roadDistanceFor` accepts it as a road run). A track that already carries a pair on any waypoint (a phone save) gets none. The worker records the sidecar's track hash on the run as `metadata.smoothed_sidecar_sha256` ([metadata.md](../backend/metadata.md)) while the sidecar is stored: the recompute uploads it and names it in its own conditional distance write (removing the key on a forward pass, or when it stored none), and the `map_match` step names it through a `track_url` + `metadata` CAS after the upload, so the key never names an object the worker did not store; `runs_keep_distance_recompute` carries it past a stale client copy (`20270719000016`). A reader requests the sidecar only when that key equals the SHA-256 of the track bytes it holds, so a run with no sidecar (every phone save, every import) or a re-uploaded track costs no Storage request. Readers then merge it only when the version, the count and the hash all match the track they hold, and only onto a waypoint without both halves of its own; `lat` / `lng` are never touched: web `fetchRunById` (`lib/runs/smoothed_sidecar.ts`), Dart `ApiClient.fetchTrack` (`packages/api_client/lib/src/smoothed_sidecar.dart`, the mobile run detail for a track it downloads), Dart `ApiClient.smoothedLocalTrack` (the mobile run detail for a track the phone holds — its own recording, or a watch run relayed through the phone — which hashes the blob `_uploadTrack` would store for that track, `ApiClient.localTrackSha256`: the upload is `jsonEncode` of the finite waypoints through one codec and the local store's `Run.toJson` / `fromJson` round-trip keeps every field it writes, so the reloaded copy hashes to the uploaded bytes; the merged line is display-only and is never persisted, so it cannot ride the next upload), and `clip-public-track` (`_shared/smoothed_sidecar.ts`, reading the key off the `public_runs` row), which merges **before** the owner return and the non-owner clip so `clip_track_for_user`'s either-pair-in-zone rule (`20270719000005`) sees every position a viewer will draw. A re-upload changes the hash and the sidecar is ignored until a later replay rewrites it; a sidecar that is missing, unreadable or stale is the raw line, which is what the track always was. One shared fixture, `fixtures/smoothed_sidecar_vectors.json`, pins the hash and the merge in Go, TS, Deno and Dart, including a stored track entry that is not an object (`nonObjectTrack`): the web and Deno readers keep it as stored and merge onto the rest, the Go writer counts it as a point with no position, and the Dart decoder drops it, after which the sidecar no longer matches and the raw line is drawn. No reader throws on it, since a throw costs the whole track. Storage access, deletion and export: [api_database.md § Storage](../backend/api_database.md). A privacy-boundary change: CISO sign-off is a pre-prod deploy checklist item ([followups.md § Deploys](../product/followups.md)). **Known gaps:** two replays of one run that race can leave the older sidecar last, which readers then ignore by its hash; and a phone-held track whose timestamps were recorded without a UTC offset, viewed after the device's time zone changed, re-encodes to different bytes and keeps its raw line (the safe failure).

## Splits and moving time

Splits and moving time used to sum haversine over the raw stored fixes, so under canopy, where raw jitter lengthens the line, the split table could run several percent past the run's `distance_m`, and the stored track dropped every fix stated worse than 20 m (30 m on the watches) that the estimator still credited (it now keeps them, flagged `offTrack`: [Stored track](#stored-track)). They now measure on one axis, `trackCumulativeMetres` (web `lib/runs/run_stats.ts`, Dart `run_stats.dart`, a parity pair), decisions § 1997:

1. **Every point carries `distM`, finite and never decreasing** (a recording since this key): `distM`, scaled by `distance_m / distM[last]` when the caller passes the run's distance. The scale closes two gaps with one rule: what the estimator credited after the last stored fix (a canopy tail, the pedometer's last steps), and a server recompute, which rewrites `distance_m` and leaves the stored track and its `distM` as the recorder wrote them (the worker cannot rewrite the track safely, see the sidecar note above). Only the owner's surfaces pass it, because a privacy-clipped track ends short of the run and would be stretched.
2. **Otherwise** (an older recording, an import, a track mixing stamped and unstamped points): the hop-sum over the line position, the smoothed pair when the fix carries both halves, else the raw fix, unscaled. A phone run saved since v1.2 therefore measures on the smoother's line; anything older reads exactly as before.

`computeRealSplits(track, tick, distance_m)` on web and `computeSplitDurations(track, tick, startedAt, totalDistanceMetres:)` on mobile take the run's distance; moving time takes none (a uniform scale does not move a 0.5 m/s floor enough to matter). So a new run's split table ends on `distance_m`, apart from the deliberate tail rule (a remainder under `SPLIT_TAIL_MIN_M`, 50 m, is not a split of its own). The custom watch's firmware port of these stats still reads raw positions.

**Speed caps.** Every port builds its estimator with the activity's `maxSpeedMps`, and the one table is [`fixtures/activity_speed_caps.json`](../../fixtures/activity_speed_caps.json): run 10, walk 5, cycle 25, hike 6, stroller 9 m/s, and an unknown or missing activity takes the run cap. It transcribes `ActivityType.maxSpeedMps` (`packages/core_models/lib/src/activity_type.dart`, held to it by `core_models/test/activity_speed_caps_test.dart`), and every other table is a test reader of the fixture: web `maxSpeedMpsForActivity` (`garmin-fit.ts`, `activity_speed_caps.test.ts`), Deno `_shared/strava.ts` (`_shared/activity_speed_caps.test.ts`), Go `maxSpeedMpsForActivity` (`handler_distance_recompute_test.go`), Wear OS `GpsDistanceEstimator.maxSpeedMpsFor` (`ActivitySpeedCapsTest.kt`), watchOS `WorkoutManager.maxSpeedMps(for:)` (`WorkoutManagerDistanceTests.swift`, over the four activities its picker offers), and the custom watch's `MAX_SPEED_MPS` (`record.rs`, the run row, because that firmware only records runs). Before issue #1172 watchOS capped walk and hike at 10 and Wear OS capped stroller at 10.

The rolling embedded bests (`estimatorCumulativeMetres`: Dart `apps/mobile_android/lib/embedded_bests.dart`, TS `apps/web/src/lib/integrations/garmin-fit.ts`, Go `apps/job_worker/internal/embedded_bests.go`) replay a stored track (`t` in seconds since the first timestamped waypoint, `expectedIntervalS` the median positive fix interval, the activity's `maxSpeedMps`) and, from v1.2, run the fastest-window search over the smoother's `cumulative_m`.

An importer whose file carries its own per-point distance stream measures the bests on that stream instead (`deviceCumulativeMetres`, in `garmin-fit.ts`, `_shared/strava.ts` and `embedded_bests.dart`): FIT `record.distance` from the web Garmin / Strava-ZIP importers and the mobile Strava-ZIP importer (`FitParser.parseWithDistances`), and Strava's `distance` stream in the Deno importer. It is what the device measured, and it is what Strava does. The stream falls back to the estimator when it is absent, misaligned with the track, or has any missing, non-finite, negative or backward sample, or no distance at all. Note that Strava's stream is Strava's own figure: for an activity uploaded without one it is Strava's outlier-trimmed straight-line sum, not a device measurement.

A road run that the OSRM `map_match` job matched end to end also gets `metadata.distance_map_matched_m`, its length along the foot graph, shown read-only on web `/runs/[id]` beside `distance_m` and never replacing it. Trails, a running track, indoor runs and anything the matcher could not measure whole get none ([metadata.md](../backend/metadata.md) lists the rules). The figure is stamped with the Storage version of the track bytes it was measured on (`distance_map_matched_track_version`) and the database keeps it only while that is the stored object's version, so a track re-uploaded in place (same `track_url`, new bytes) loses it, and its matched track, at once and is queued for a fresh match ([api_database.md § `run_matched_tracks`](../backend/api_database.md), migration `20270719000020`). The smoothed sidecar needs no such help: its readers compare a fingerprint of the bytes they downloaded.

**What the matcher sends OSRM.** Each `/match/v1/foot` chunk (100 points, OSRM's default `--max-matching-size`) carries `radiuses` from every waypoint's `accuracyMetres`, rounded to whole metres and clamped to 5-50 m, with OSRM's own 5 m default where a waypoint has none (imports, older recordings), so an accuracy-less track matches as it always did. Without them OSRM searched 5 m around every point, so a canopy fix 20 m off its path snapped to nothing, carried through raw, and cost the run its road distance (every point must snap). When every point in the chunk has a `ts` and the whole-second values never go backwards, the chunk also carries `timestamps` (Unix seconds) and `gaps=ignore`: a decreasing sequence is a 400 `InvalidValue` from OSRM, which would fail the job rather than the chunk, so such a chunk is sent without them, and `gaps=ignore` stops an auto-pause longer than OSRM's 60 s split threshold from breaking the chunk into several matchings, which would also cost the road distance. A 100-point chunk with all three is about 4 KB of URL. The matcher's version moved to `v2` with this (`run_matched_tracks.algorithm_version`); older matches are not re-run. Display and road distance only; `distance_m` is unaffected (`apps/job_worker/internal/matcher_osrm.go`, issue #1176).

## Server recompute

Runs recorded before v1 keep their inflated hop-sum distance until something re-derives it, and a Wear OS or watchOS run arrives with its forward-filter figure. The server re-derives both from the stored track:

0. **Automatic, watch runs** (issue #1172, decisions § 1991). The `runs_enqueue_watch_distance_recompute` trigger (migration `20270828000001`, AFTER INSERT or UPDATE OF `track_url` on `runs`) queues the same `distance_recompute` job, with the same payload and tier-aware `scheduled_at` as the RPC, for a `source = 'watch'` run once it has a `track_url` and carries a recorder `distance_estimator` stamp and `track_complete: true` (the JSON boolean, since `20270829000031`) with no `distance_recomputed_at`, unless it is in progress, manual, indoor or tagged with a `distance_source`. Wear OS and watchOS stamp every run, and since `track_complete` store every fix their forward filter took, with Doppler and the canopy fixes flagged `offTrack`, so the job keeps the smoothed pass and replays to the wrist's figure. A watch build from before `track_complete` stored only fixes inside its 30 m gate, which a replay reads short under canopy (3.7-4.5% on the bench), so the trigger leaves it on its wrist figure; Recalculate distance still offers it when its stamp predates v1.4 (below). The custom watch syncs as `watch` too but stamps nothing: its flash track is a decimated breadcrumb a replay would under-read, so it keeps its own figure. A watch row that lands before its track queues when `track_url` is set; an UPDATE naming an unchanged `track_url` (an upsert retry) queues nothing, `jobs_dedupe_distance_recompute` makes a second insert while one is queued or running a no-op, and a recomputed run is never queued again. Existing runs are not backfilled; Recalculate distance still offers them. The trigger's insert sits in its own exception block, so it never fails the run's write. pgtap `runs_enqueue_watch_distance_recompute_test.sql`.
1. **UI.** On `/runs/[id]` the owner sees **Recalculate distance** under the key stats when `canRecomputeDistance` (`apps/web/src/lib/runs/distance_recompute.ts`) holds: they own the run, it has a `track_url`, its `source` is `app` or `watch` (an import's distance belongs to the system that recorded it), `metadata.distance_source` is not `pedometer` (no GPS to recompute from), a recorder's live stamp is not the phone's (below), a live `kalman_v4` stamp comes with `track_complete: true` (`TRACK_GATED_ESTIMATORS`: such a recorder feeds its estimator fixes its track gate refuses, so without the flag its stored track omits them), and a recompute has not already applied the **current** estimator, `kalman_v4`. The Wear OS and watchOS builds before the flag stamp `kalman_v1` and stored every fix their estimator took, so they stay offered. The action opens a ConfirmDialog saying the distance will be recomputed with the improved GPS filter and the original kept, then calls the RPC. Success shows "Recalculating — refresh in a minute" and hides the action; a refusal (not the owner, no track) or any other failure is shown as an error toast and the action stays offered.
2. **RPC.** `request_distance_recompute(p_run_id uuid) returns void` (migration `20270719000001`) is SECURITY DEFINER, `authenticated`-only, raises `42501` unless the caller owns the run and `22000` when it has no track, and inserts a `distance_recompute` job with payload `{run_id, user_id}`. A partial unique index (`jobs_dedupe_distance_recompute`) makes a second request while one is queued or running a no-op. See [api_database.md](../backend/api_database.md).
3. **Job.** The Go worker (`apps/job_worker/internal/handler_distance_recompute.go`) downloads the track, replays its waypoints through the **smoother** (`internal/gpsdistance/`; the Doppler path when the waypoints carry `speedMps` and friends, position-only with post-hoc stop detection otherwise) with the activity's speed ceiling and the track's median fix interval as `expectedIntervalS`, and rewrites `runs.distance_m` (the stored track file itself is left as it is). It skips sources other than `app` / `watch`, and a phone run its recorder stamped (`distance_estimator` with no `distance_recomputed_at`), whose movement-gated track holds fewer fixes than the save saw; a watch run's stamp is no bar, unless it is a live `kalman_v4` stamp without `track_complete` (`trackGatedEstimators`), whose track omits the canopy fixes its estimator took. The replay reads every stored point, off-track ones included; the road matcher it consults reads only the line (`onTrackRaw`). **Pedometer gap fill:** the recorder credited each GPS gap `max(chord lower bound, steps x stride)` (Algorithm, item 9) and saved the steps' share of the run as `metadata.distance_step_filled_m`. The track carries no steps, so the replay credits each gap its chord lower bound alone (`SmoothResult.GapM` in total, the same in both passes), and the worker credits the pair `max(GapM, distance_step_filled_m)` on the pass it keeps (`gapStepTopUpM`). That is the recorder's figure exactly when every gap's steps fall on the same side of its chord (one gap, or an honest stride), and short, never long, when they do not, because the steps arrive only as a run total. Adding the step-filled metres on top of the replay, as the worker did before, counted every step-filled gap twice: `gap_with_steps` recomputed to 522.1 m against the recorder's 417.2 m. `TestDistanceRecompute_GapWithStepsMatchesTheRecorder` replays every shared vector whose pedometer filled a gap from its fixes alone and holds the recompute to the smoother's figure over the full stream. The bests stay on the replay's cumulative, which holds the chords only and so can only make them slower. **Which pass it keeps:** the smoothed figure for every track that carries Doppler, and for a position-only track that is a road run. A position-only track that is **not** a road run keeps the smoother's **forward pass** (the forward filter over the same events, with the same post-hoc stop hints), because off road the smoother cuts more corners than the forward filter (Bench, Known limit). "Road run" is the map_match step's own classifier, `roadDistanceFor` (`internal/road_distance.go`, the rules in [metadata.md § `distance_map_matched_m`](../backend/metadata.md)): the run already carries `distance_map_matched_m`, or the OSRM matcher measures the track now and the classifier accepts it against the smoothed figure (an old run's stored `distance_m` is the inflated hop-sum, so it is not the yardstick). A **transient** match failure (an engine 5xx, 408 / 425 / 429, a timeout, by the worker's `isTransient`) decides nothing: the job is deferred and retried, and nothing is written, because a run stamped `kalman_v4` is no longer offered Recalculate and an outage would otherwise pin a road run to the forward pass for good. No matcher configured, a non-transient match failure, or any rule the classifier refuses on (a hike, a trail route, a `sub_sport` of `trail`, a track-sized footprint, a run not matched end to end) keeps the forward pass. The bests in step 4 are measured on the same pass, and step 5 records it as `distance_estimator_pass`.
4. **Embedded bests.** The same replay's smoothed cumulative distance re-derives the four rolling bests (`runs.fastest_5k_s` / `_10k_s` / `_half_marathon_s` / `_marathon_s`, `internal/embedded_bests.go`), written in the same conditional PATCH as `distance_m`. All four are written: a best the inflated hop-sum produced on a run the estimator now measures short of that distance is cleared to null rather than left behind. The `personal_records` statement trigger re-derives on any change to `distance_m` or a `fastest_*` column ([derived_state.md](../backend/derived_state.md)), so the owner's PRs follow.
5. **Metadata.** The worker writes `distance_estimator = "kalman_v4"` (spec v1.4 smoother; `"kalman_v3"` was the spec v1.3 smoother, `"kalman_v2"` the spec v1.2 one and `"kalman_v1"` the v1 / v1.1 forward filter) and `distance_recomputed_at`, and copies the recorder's figure into `distance_recorded_m` (only when absent, so a second recompute never loses the original). The page shows it as "Originally recorded: X" in the viewer's unit. All keys are registered in [metadata.md § Distance estimator](../backend/metadata.md). **A run already recomputed as `kalman_v1` is eligible again**: the recompute gate compares against the current value, so the owner can re-run it and pick up the gate, the cross-check and the smoother; `distance_recorded_m` still holds the original recorder figure.
6. **Badges.** The same write takes back any distance badge (`distance_single`, `distance_lifetime`) the corrected distance no longer earns, via the `runs_achievements_revoke_on_distance_recompute` trigger; every other badge family stays durable ([achievements.md](achievements.md)).
7. **Stale copies.** A client that loaded the run before the recompute (the screen the owner tapped Recalculate on, an unsynced local row) cannot write the inflated figure back: the `runs_keep_distance_recompute` BEFORE UPDATE trigger (`20270719000003`) recognises a write whose metadata lacks `distance_recomputed_at` on a row that has it, carries the recompute's keys forward, keeps the recomputed `fastest_*` columns, and keeps the recomputed `distance_m` when the incoming figure is the original `distance_recorded_m`. A distance the owner deliberately typed is kept.

## Ground-truth corpus

`fixtures/gps_corpus/` holds tracks recorded on courses of measured length, each with a manifest giving the known distance, course type, device and an error budget; `scripts/gps_distance/replay_corpus.py` replays every entry through `reference.py` in CI and fails outside budget, printing the signed error, the mean NIS and the residual autocorrelation for tuning. It holds one synthetic entry until the owner's real tracks land; [its README](../../fixtures/gps_corpus/README.md) lists what to record.

Ground truth is a measured or surveyed course (a 400 m track in lane 1, a wheel-measured road loop, a tree-covered trail), never a watch reading: sport watches are themselves 3-6% off and under-read by up to 9% in forest and urban areas (Gilgen-Ammann 2020). The corpus is what every constant in this spec waits on; each course states an error budget and CI asserts the reference stays inside it. It must check **under**-counting under trees and between buildings as well as over-counting, because heavy smoothing cuts corners (the position-only rows of the bench above). It is also where the open device questions get answered: the fused provider against raw `GPS_PROVIDER` on Android, the error autocorrelation *C* (Ranacher 2015), how honest each platform's `speedAccuracy` is (which decides the debias fade), and the Android pedometer batching lag (which decides `ZUPT_NO_STEP_S`).

## Q_ACCEL is still unvalidated

`Q_ACCEL = 0.6 m^2/s^3` is the one number every part of the filter depends on — how fast the filter believes velocity can change — and it has never been checked against a real track. No published process-noise value for GPS running exists (research note 12); a pedestrian pace-estimation patent uses a separate value per motion class. v1.2 deliberately leaves it alone: tuning it on synthetic noise would fit the bench, not runners. The bench shows what it costs: too low a value cuts corners on twisty position-only tracks (forest trail -1.2% forward, -3.1% smoothed; 12 s switchbacks -20% / -31%), too high a value lets jitter through (raising it to 2 moves the open-course position-only rows from +0.8% to +2.2% forward). On the corpus it should be tuned per activity type with innovation (NIS) and NEES consistency checks, and a maneuver-adaptive variant (inflating Q when normalised innovations stay high) evaluated as the durable fix for the switchback case. Any change goes through `reference.py`, regenerates the vectors and bumps the spec version.

## Tuning

The constants are in the fixture's `constants` block. Do not tune a port independently — the vectors will fail, which is the point.

Known limits: position-only input (live forward filter) still drifts ~15 m over 90 s of standing still (the `stationary_position_only` vector) unless the pedometer drives a ZUPT; the smoother's stop detection removes it in the saved figure. Doppler input does not drift. Twisty position-only tracks under-read (above). A Doppler bias below the cross-check's threshold is corrected by the v1.3 scale only while running above 1.5 m/s; at walking pace it passes through.

**Position-only recompute off road keeps the forward figure.** Until the corpus retunes `Q_ACCEL`, the server recompute of a track with no Doppler that the road classifier does not accept keeps the forward pass (Server recompute, step 3). Measured on the bench inputs with the smoother's own forward pass, stop hints included (mean of 5 seeds, worst in brackets): canopy switchbacks forward -21.4% [-25.3] against smoothed -31.3%, forest trail -1.2% against -3.1%, and on the open course with two stops +1.0% [+1.5] against -0.1%. The stop hints cost the switchbacks 1.9 points against the plain forward filter's -19.5% (stop detection reads some 12 s legs that double back as stationary) and buy back the stationary drift (+2.3% to +1.0% on the two-stops course), so they are kept. The importers do **not** apply this rule: the Strava fallback in `_shared/strava.ts` (it passes no speed at all), the web FIT fallback in `garmin-fit.ts` and the phone's `embedded_bests.dart` still measure embedded bests on the smoothed cumulative. Their headline distance is the provider's, the estimator only feeds the bests there, they have no road matcher, and a second road definition would drift from `roadDistanceFor`; on every position-only bench row the smoothed figure is the lower of the two, so it gives the slower best, the safe side for a PR, while the forward figure on a road run nobody could classify would give a too-fast one.

### New and changed signatures (Python names; ports keep their own casing)

- `GpsDistanceEstimator(max_speed_mps=10.0, expected_interval_s=1.0, initial_stride_m=None, record=False, learn_stride=True)`. `record` is only needed by a port that implements the smoother (it can be an internal constructor). `learn_stride` (v1.4) is false for a stretch on a source whose speed is not its own Doppler; Go spells it `Options.NoStrideLearning` so the zero value learns, Rust `without_stride_learning()`.
- `add_fix(t, lat, lng, accuracy_m=None, speed_mps=None, speed_accuracy_mps=None, bearing_deg=None, stopped_hint=False) -> float` (metres credited). `stopped_hint` is new; live recorders always pass false.
- `add_steps(t, cumulative_steps)`, `finish(t)` — unchanged signatures.
- New read-only state: `r_scale` (float, starts 1.0), `rejected_fixes` (int), `zupt_fixes` (int), `doppler_trusted` (bool, starts true), and from v1.3 `doppler_scale` (float, starts 1.0).
- `unproject(x, y) -> (lat, lng)` (smoother ports).
- `detect_stops(fixes: [(t, x, y)], expected_interval_s) -> [bool]` (smoother ports).
- `smooth_distance(events, max_speed_mps=10.0, expected_interval_s=1.0, initial_stride_m=None, learn_stride=True) -> {distance_m, gps_distance_m, step_distance_m, cumulative_m[], positions[], stopped_fixes}`. Events are `fix {t, lat, lng, acc, speed, speedAcc, bearing}` / `steps {t, count}` / `finish {t}`; a port may take a typed event list. `cumulative_m` and `positions` have one entry per input event.

### New estimator state

`rScale = 1`, `rejectedFixes = 0`, `rejectStreak = 0`, `dopplerTrusted = true`, `xcDoppler = xcPos = 0`, `xcTime = 0`, `xcPersistS = 0`, `xcLast = (x, y, t)` (none until the first anchor), `stepsSeen = false`, `lastStepIncreaseT = none`, `zuptReleased = false`, `zuptAnchor = (x, y)` or none, `zuptFixes = 0`; v1.3 adds `dopplerScale = 1`, `dsPos = dsDop = 0`, `dsTime = 0` and `dsLast = (x, y, t, dop, bearing)`, set wherever `xcLast` is set (with that fix's usable `dop` and finite bearing, either possibly none) and after every accepted fix. The v1.1 per-axis filters are unchanged; there is no second (shadow) filter. That is about 15 scalars more than v1.1, which a fixed-size port (the Rust `no_std` one) must budget for.

### Doppler helper

`dopplerSpeed(speed, sa_in, maxSpeed) -> (s, sa) or none`: none unless `speed` finite and `0 <= speed <= maxSpeed`; `reported = sa_in finite and > 0`; `sa = reported ? sa_in : 0.5`; none if `sa > 1.5`; if `reported` and `speed < 1.0`: `w = speed <= 0.5 ? 1 : (1.0 - speed) / (1.0 - 0.5)`, `s = sqrt(max(0, speed^2 - w * sa^2))`; else `s = speed`. `sa` (not the debiased speed) feeds the velocity-update variance.

### Order of operations in `add_fix`

1. Invalid `t`, `lat` or `lng` (non-finite or missing): return 0, nothing recorded. v1.4: so is a finite stated accuracy `> 50`, before the origin is set.
2. First valid fix sets `lat0`, `lng0` (even if it later turns out to be ignored — it cannot be, it is the first).
3. Project with the wrapped longitude difference.
4. `sigma = accuracy if finite and > 0 else 3`; `r_stated = max(sigma, 3)^2`; `r = max(r_stated * rScale, 9)` (using `rScale` before this fix's update).
5. `t <= last t`: return 0 (ignored).
6. `(dop, sa) = dopplerSpeed(...)`.
7. First fix or `t - last t > gapWindow`: if this is a gap (not the first fix), commit pending steps, then (v1.4) `lower = min(hypot(zx - px, zy - py) - sqrt(ax + ay + 2r), maxSpeed * (t - last t))` from the previous filter's posterior `p` / `a`, and when `lower > pending` add `lower - pending` to `gpsDistance` (the anchor's credit and its recorded `chord`); clear the buffer; `strideOk = strideGrade(accuracy, dop usable, sa)` and empty the stride window when it is false; new axes at `(zx, zy)` with variance `r`, set last t, `xcLast = (zx, zy, t)`, `dsLast = (zx, zy, t, dop, bearing)`, `rejectStreak = 0`, `zuptAnchor = none`; `zupt = stoppedHint or zuptDue(t, dop)` (recorded only); record an anchor (its `dop` is `dop * dopplerScale` if trusted); return 0.
8. Clear the pending step buffer; `dt = t - last t`; set last t; predict both axes; snapshot the predicted states.
9. Gate: `yx = zx - px`, `yy = zy - py`, `ax`, `ay` = predicted position variances, `nis = yx^2/(ax + r) + yy^2/(ay + r)`; `accepted = nis <= 13.8155`.
   - Accepted: `rejectStreak = 0`; position update both axes with `r`; `sample = clamp(((yx^2 - ax) + (yy^2 - ay)) / (2 r_stated), 0, 9)`; `rScale = clamp(0.95 rScale + 0.05 sample, 1, 9)`.
   - Rejected: `rejectedFixes += 1`, `rejectStreak += 1`; if `rejectStreak > 5`: `resetPos(zx, r)` / `resetPos(zy, r)` (`p = z`, `a = r`, `b = 0`), `rejectStreak = 0`, `xcLast = (zx, zy, t)`, `dsLast = (zx, zy, t, dop, bearing)`, mark a chain break.
10. Pedometer ZUPT: `pedZupt = zuptDue(t, dop)`, where `zuptDue` is false unless `stepsSeen`, not `zuptReleased`, and `t - lastStepIncreaseT > 6`, and is also false when `dop` is usable, `dopplerTrusted` (its value before step 11) and `dop >= 1.0`. If `pedZupt`: when `zuptAnchor` is none set it to the current filtered `(px, py)`; otherwise `moved = hypot(px - ax0, py - ay0)` and if `moved > 40`: `zuptReleased = true`, `zuptAnchor = none`, `pedZupt = false`, `chord = moved`. If not `pedZupt` (on entry): `zuptAnchor = none`. Then `zupt = stoppedHint or pedZupt`; if `zupt`: `chord = none`, `zuptFixes += 1`, velocity update `0` with variance `0.01` on both axes.
11. Cross-check, only if `accepted` and (v1.4) the fix's finite stated accuracy is not `> 20`: `(lx, ly, lt) = xcLast`, `span = t - lt`; if `dop` usable, not `zupt`, bearing finite, `dop >= 0.8`, `span <= 5`: `u = ((zx - lx) sin b + (zy - ly) cos b) / span`; if `xcTime == 0` set `xcDoppler = xcPos = dop`, else `alpha = min(1, span / 60)`, `xcDoppler += alpha (dop - xcDoppler)`, `xcPos += alpha (u - xcPos)`; `xcTime += span`; if `xcTime >= 120`: `diff = |xcDoppler - xcPos|`, `ref = |xcPos|`, `flip = trusted ? diff > max(0.4, 0.15 ref) : diff < max(0.2, 0.08 ref)`; `xcPersistS = flip ? xcPersistS + span : 0`; if `xcPersistS >= 60`: toggle `dopplerTrusted`, `xcPersistS = 0`. Then (still only if accepted) `xcLast = (zx, zy, t)`.
11b. Doppler scale (v1.3), under the same condition as 11, after the cross-check: `(lx, ly, lt, ldop, lb) = dsLast`, `span = t - lt`, `d = |bearing - lb| mod 360` when both bearings are finite. If not `zupt`, `dop` and `ldop` usable and both `>= 1.5`, both bearings finite, `span <= 5` and `min(d, 360 - d) <= 45`: `ux = sin b0 + sin b1`, `uy = cos b0 + cos b1` (b0 = `lb`, b1 = this fix's bearing, radians), `n = hypot(ux, uy)`, `w = exp(-span / 600)`, `dsPos = w dsPos + ((zx - lx) ux + (zy - ly) uy) / n`, `dsDop = w dsDop + 0.5 (ldop + dop) span`, `dsTime += span`; if `dsTime >= 60` and `dsDop > 0`: `dopplerScale = clamp(dsPos / dsDop, 0.8, 1.25)`. Then `dsLast = (zx, zy, t, dop, bearing)`.
12. `useDop = dop * dopplerScale if usable and dopplerTrusted else none`. If `useDop`, not `zupt`, bearing finite, `useDop >= 0.4`: velocity update with `useDop * sin(b)`, `useDop * cos(b)`, variance `max(sa, 0.3)^2`.
13. Credit: `chord` if set; else 0 if `zupt`; else `speed = useDop` (floor 0.4) or `hypot(vx, vy)` (floor 0.8), `inc = speed < floor ? 0 : min(speed, maxSpeed) * dt`. Add to `gpsDistance`. v1.4: `strideOk = strideGrade(accuracy, useDop present and no chord, sa)`, where `strideGrade` is false without `learnStride`, else `sa <= 1.0` for Doppler credit, else not (finite accuracy `> 20`); when true add `inc` to the stride window's metres, else empty the window (steps and metres).
14. Record (smoother ports) and return `inc`.

### `add_steps` change

After the existing early returns (missing / non-finite `t`, missing count, first call, count decreased, `t <= previous step t`), when `d = cumulative - previous > 0`: `stepsSeen = true`, `lastStepIncreaseT = t`, `zuptReleased = false`. v1.4: inside the fresh-fix window, return without counting the steps when the last fix's `strideOk` is false; the rest of the stride logic is unchanged.

### Smoother specifics

- `hasDoppler` = any **accepted** fix whose `speed` is finite (any finite value, even one later rejected as out of range).
- Stop detection runs only when `hasDoppler` is false; the hints are keyed by event index and passed as `stopped_hint`.
- Record per accepted fix: `anchor` (gap / first fix), `chainBreak` (anchor or lock-out), `dt` (0 at an anchor), `pred` (per axis `(p, v, a, b, c)` after predict, none at an anchor), filtered `(p, v, a, b, c)` per axis after all of the fix's updates, `zupt`, `dop` (= `useDop`, or at an anchor `dop` if trusted), `chord`, `stepDistance` after the fix.
- RTS per chain (`[s, e]`, a chain starts at every `chainBreak`), x and y independently, formulas above. Smoothed position = `unproject(ps_x, ps_y)`.
- `cumulative_m[i]`: running sum of credits over accepted fixes up to event `i`, plus the step distance recorded after the latest accepted fix; at a `finish` event the final step distance is used instead.
- `distance_m = sum(credits) + finalStepDistance`; note the last `cumulative_m` equals it only when the last event is the finish.

### What the fixture contains

Top level: `spec` (`"gps-distance-estimator v1.4"`), `reference`, `tolerance_m` (0.001), `position_tolerance_deg` (1e-8, about 1.1 mm), `constants` (every constant above plus v1.1's, by reference name), `scenarios` (35: the 16 v1.1 ones with **unchanged events**, 11 for v1.2, 2 for v1.3, a Doppler 8% low and 10% high, then 6 for v1.4: a 20-50 m canopy stretch, a stretch past 50 m, canopy Doppler too poor to teach stride, a gap whose steps fall short of its chord, and two fused stretches with and without a seeded stride). - `expected` (forward estimator): `distanceAfterEachEventM` (after every event, including steps and finish), `gpsDistanceM`, `stepDistanceM`, `strideM` (null when none), and new `rejectedFixes`, `zuptFixes` (ints), `rScale` (float), `dopplerTrusted` (bool), and from v1.3 `dopplerScale` (float), all read after the `finish` event.
