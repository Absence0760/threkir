# Sub-processors

Every external service that touches user data. This is both:

- The **Privacy Policy** sub-processor disclosure (Art 13(1)(e) + 14(1)(e) GDPR).
- The **GDPR Art 30 Record of Processing Activities** input.

**Status**: scaffold based on the codebase. Verify against actual prod config + each provider's current DPA before publishing.

**Email-transport split (audit/third-party-data-flows + audit/gdpr 2026-05-30; corrected 2026-06-14):** there are TWO email paths, with different transports. **(1) Auth mail** (confirm-signup, password-reset): `supabase/config.toml` declares no custom `[auth.email.smtp]` block, so this is sent by Supabase's own managed email service — a Supabase sub-processor, covered by the Supabase DPA already linked above. Before publishing, the operator must still confirm the production project's dashboard (Auth → Emails → SMTP Settings) has no custom SMTP host configured; if one *is* set there, add it as its own row with that provider's region + DPA (the dashboard setting is invisible to this repo). **(2) Application transactional/engagement mail** (notification / lifecycle / safety / weekly-digest jobs): this goes via the Go `job_worker`'s own SMTP transport (`internal/mailer.go`), whose prod transport the mailer documents as "Resend / SES SMTP in prod" — i.e. a separate provider, captured as the **SMTP email provider** row above. An earlier draft of this note affirmatively denied any "separate Resend / Postmark / in-house provider"; that statement was false — Supabase handles only the auth mail, and the app's transactional/engagement mail goes through the job_worker SMTP transport.

**Self-hosted routing engines (OSRM + GraphHopper + graph_cycle) are NOT new third-party sub-processors.** All three run on **our own Fly.io infrastructure** — the only sub-processor in the chain is Fly.io (the hosting provider, already a row above), not the engine projects themselves. OSRM serves map-matching (`apps/job_worker/`) + manual-waypoint snapping; **GraphHopper** (added 2026-06-09, decisions §575) and the **graph_cycle map sidecar** (added 2026-06-10, decisions §575 amendment — our own Go service, `apps/graph_cycle`) both serve distance-targeted loop generation (`/api/routes/generate`). The user's start coordinates reach these engines only *inside* our infra — `GRAPHHOPPER_URL` + `GRAPH_CYCLE_URL` are server-only envs (never `PUBLIC_`), so the browser never calls an engine directly and no coordinate egresses to a third party (same posture as the self-hosted OSRM map-matcher). No engine DPA exists or is required — there is no third party processing the data; we are. Logged here for completeness, not because a new processor relationship was created.

**Removed 2026-11-10: parkrun and UltraSignup (results).** The parkrun results import sent a runner's athlete number to parkrun's site and scraped the results page; the UltraSignup results import sent the runner's first and last name to UltraSignup's internal `historybyname` feed. Both were removed with every other integration that scraped a third party's website ([decisions § SCRAPER_ADR](../architecture/decisions.md), [sub-processor-changelog.md](sub-processor-changelog.md)), and migration `20271216170001` deletes the `integrations` rows they wrote. No request now reaches either site from our infrastructure on a runner's behalf. The parkrun barcode stays and contacts no one: it draws the runner's own stored number on their own device.

## Sub-sub-processors

Each row above is itself a top-level provider. Their sub-processors (e.g. AWS for Sentry's hosting, GCP for Anthropic's hosting) propagate down. The Privacy Policy should point readers to each provider's own sub-processor list rather than enumerate the entire chain.

## Notification of changes

GDPR Art 28(2): we must notify users of "any intended changes concerning the addition or replacement of sub-processors". Mechanism we commit to in the Privacy Policy:

- Committed mechanism: the maintained **[`sub-processor-changelog.md`](sub-processor-changelog.md)**, which declares itself the Art 28(2) disclosure surface — every addition, replacement, or material region change must land there **at least 30 days before** activation in production. A user who objects may email the privacy contact before the activation date or delete their account. The in-app notice supplements this for active registered users; the changelog is the canonical history (this file remains the current snapshot).

## Cross-border transfer mechanisms

For EU-data-subject flows landing in non-adequacy countries (most of the above are US):

- **Standard Contractual Clauses (SCCs)** under the European Commission's 2021 module 2 (controller → processor). Every provider above publishes these in their DPA.

Retention is the default 30 days (no zero-data-retention agreement), the Development Partner Program is not joined, and user feedback is off. AI disclosure v6's "deletes it within 30 days" rests on this; re-check it if any of these change.
- **Transfer impact assessment**: for the US-hosted ones, document our reliance on EU-US Data Privacy Framework (EUDPF, replacing Privacy Shield post-Schrems II). Each provider's DPA states their certification status.
